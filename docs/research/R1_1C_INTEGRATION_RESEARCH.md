## 1. Что НЕ известно и как определить фактическую конфигурацию

Конфигурация и версия платформы у магазина неизвестны. Кандидаты (без приоритета): «1С:Управление торговлей 11» (УТ 11.x), «1С:Розница 2.x/3.0», «1С:Управление нашей фирмой» (УНФ 1.6/3.0), «1С:Бухгалтерия 3.0» (БП 3.0), «1С:ERP 2» / «Комплексная автоматизация 2». Отдельный риск: в Кыргызстане распространены **локализованные** конфигурации («…для Кыргызстана»), у которых состав объектов, версии и наличие подсистем БСП могут отличаться от российских типовых `[НЕ ПОДТВЕРЖДЕНО]`. Все имена объектов в этом отчёте — для российских типовых редакций и требуют сверки.

Как определить фактическую конфигурацию (простым языком, без программирования):

1. В режиме «1С:Предприятие» нажать кнопку «i» (или меню «Сервис и настройки» → «О программе»). В окне: первая строка — версия платформы (например, `8.3.2x.xxxx`), ниже — название конфигурации и её релиз (например, «Управление торговлей, редакция 11.5 (11.5.xx.xx)»), а также признак «базовая» в скобках для базовых версий `[ТИПОВО: интерфейс «Такси», требует проверки]`.
2. Там же видно, файловая база или клиент-серверная (строка «Каталог» с путём к файлу `1Cv8.1CD` — файловый вариант; строка «Сервер / Информационная база» — клиент-серверный).
3. В Конфигураторе: «Справка → О программе» даёт то же; «Конфигурация → Открыть конфигурацию» → корень дерева → свойства: Имя, Синоним, Поставщик, Версия; «Конфигурация → Поддержка → Настройка поддержки» показывает, снята ли конфигурация с поддержки (т. е. менялась ли типовая).
4. «Конфигурация → Расширения конфигурации» — список уже установленных расширений.
5. Версия БСП: «Администрирование → Обслуживание → (Сведения о программе)» либо запрос у 1С-специалиста `[ТИПОВО]`.

Результат этих шагов — обязательный вход для выбора варианта интеграции (разд. 10).

## 2. Стандартный интерфейс OData платформы 8.3

### 2.1. Общие факты

| Утверждение | Статус |
|---|---|
| Платформа предоставляет автоматически генерируемый REST-интерфейс по протоколу **OData версии 3**; форматы ответа Atom/XML и JSON | `[ПОДТВЕРЖДЕНО: https://1c-dn.com/1c_enterprise/rest_interface/]` |
| Механизм доступен с платформы 8.3.5 | `[ТИПОВО: Habr 865798 (Modus BI), Infostart 1570140; требует проверки версии платформы заказчика]` |
| Через OData доступны: справочники, документы, константы, перечисления, планы обмена, планы счетов, планы видов характеристик/расчёта, бизнес-процессы, задачи, журналы документов, регистры (накопления, сведений, бухгалтерии, расчёта), виртуальные таблицы регистров | `[ПОДТВЕРЖДЕНО: 1c-dn.com/1c_enterprise/rest_interface/; kb.1ci.com FAQ «How to use the oData protocol…»]` |
| Через OData **недоступны**: отчёты, команды, критерии отбора, регламентные задания, внешние источники данных, пользователи, журнал регистрации | `[ТИПОВО: Habr 865798; совпадает с официальным списком допустимых типов]` |
| Операции: чтение списков с отбором, чтение одного объекта по ссылке, запись/изменение/создание/удаление объектов, запись наборов записей; для документов — проведение и отмена проведения; для регистров сведений — срез первых/последних; для регистров накопления и бухгалтерии — остатки, обороты, остатки и обороты | `[ПОДТВЕРЖДЕНО: 1c-dn.com/1c_enterprise/rest_interface/]` |
| При чтении и записи выполняются стандартные проверки прав доступа и обработчики событий объектов; **проверка заполнения не выполняется** | `[ПОДТВЕРЖДЕНО: 1c-dn.com/1c_enterprise/rest_interface/]` |
| Аутентификация — такая же, как у веб-сервисов (имя/пароль пользователя ИБ; Basic-аутентификация на уровне HTTP) | `[ПОДТВЕРЖДЕНО (общая формулировка): 1c-dn.com/1c_enterprise/rest_interface/]`; Basic — `[ТИПОВО]` |
| Ошибки: 4xx — ошибка клиента (может содержать внутренний код и текст ошибки 1С), 5xx — ошибка сервера | `[ПОДТВЕРЖДЕНО: 1c-dn.com/1c_enterprise/rest_interface/]` |

Официальная структура описания в «Руководстве разработчика 8.3.26», глава 17.4 «Стандартный интерфейс OData» (оглавление публично): 17.4.3 Представление данных; 17.4.4 Правила формирования имени ресурса; 17.4.5 Правила формирования условия отбора (`$filter`, `$top`, `allowedOnly`, `$skip`); 17.4.6 Параметры запроса (`$count`, `$inlinecount`, `$orderby`, `$expand`); 17.4.7 Способы получения описания; 17.4.9 Выполнение функций и действий; 17.4.10 Ошибочные ситуации; 17.4.12 Публикация; 17.4.13.1.5 Оптимистическая блокировка данных; 17.4.13.1.6 Запись объекта в режиме загрузки данных; 17.4.13.1.7 Проведение и отмена проведения документа; 17.4.13.3 Работа с планами обмена (формирование сообщения обмена, уведомление о получении изменений) `[ПОДТВЕРЖДЕНО (существование главы 17 «Интеграция с внешними системами»: https://its.1c.ru/db/v8326doc/content/56/1; существование разделов — по оглавлению ИТС из поисковых фрагментов, номера разделов могут отличаться по версиям; прямо подтверждены фрагментами 17.4.5.4 allowedOnly и 17.4.13.3 «Работа с планами обмена» (v851/v854); тела разделов требуют входа)]`.

Важный вывод из оглавления: **стандартный OData умеет работать с планами обмена** (разд. 17.4.13.3) — то есть инкрементальный обмен через регистрацию изменений доступен даже без собственного HTTP-сервиса, если в конфигурации есть подходящий план обмена (см. разд. 4).

### 2.2. Включение

| Шаг | Статус |
|---|---|
| Конфигуратор → «Администрирование → Публикация на веб-сервере» → флажок «Публиковать стандартный интерфейс OData» → «Опубликовать» (имя публикации — латиницей) | `[ПОДТВЕРЖДЕНО: kb.1ci.com FAQ «How to use the oData protocol when publishing an infobase to web server»; Habr 865798]` |
| Состав публикуемых объектов задаётся из встроенного языка: `УстановитьСоставСтандартногоИнтерфейсаOData(<МассивОбъектовМетаданных>)` / `SetStandardODataInterfaceContent(...)`; текущий состав — `ПолучитьСоставСтандартногоИнтерфейсаOData()` / `GetStandardODataInterfaceContent()`. Доступно на сервере, толстом клиенте, внешнем соединении. По источнику дословно: `GetStandardODataInterfaceContent` «returns all configuration objects available … in the mode of configuration compatibility with v. 8.3.4» | `[ПОДТВЕРЖДЕНО: kb.1ci.com FAQ, там же пример кода]`; вывод, что в режиме совместимости 8.3.4 **и ниже** все допустимые объекты публикуются **без настройки состава**, — `[ТИПОВО, экстраполяция; требует проверки]`. **Примечание о расхождении с заданием:** в задании метод назван `НастроитьСоставСтандартногоИнтерфейсаOData`; официальное имя — `УстановитьСоставСтандартногоИнтерфейсаOData` / `SetStandardODataInterfaceContent` (kb.1ci.com FAQ); в ТЗ использовать официальное имя |
| В конфигурациях на БСП есть интерфейсная настройка: «Администрирование → Синхронизация данных → Настройки стандартного интерфейса OData»: вкладка «Авторизация» (отдельный пользователь/пароль для OData), вкладка «Состав» → «Загрузить метаданные» → отметить основные и подчинённые объекты | `[ТИПОВО: БСП 2.4+/3.x, Habr 865798; требует проверки]` |
| В БСП при этом создаётся/используется пользователь с ролью вида «Удалённый доступ через OData» (только чтение); для записи нужны дополнительные роли | `[ТИПОВО: Infostart 2714438 (БП 3.0, 2026); имя роли требует проверки в конкретной конфигурации]` |
| Пользователь ИБ для OData должен иметь: пароль, снятый флажок «Показывать в списке выбора», право «Аутентификация 1С:Предприятия»; роли с правами «Чтение»/«Просмотр» на нужные объекты (и «Изменение/Добавление/Проведение» — только если запись через OData разрешена) | `[ТИПОВО]` |

### 2.3. Формат URL и именование ресурсов

Базовый адрес: `http(s)://<host>/<имя_публикации>/odata/standard.odata/` `[ПОДТВЕРЖДЕНО: пример `/OData_Tests_Infobase/odata/standard.odata/Catalog_Goods` на 1c-dn.com/rest_interface; пример `http://host/base/odata/standard.odata/Catalog_Goods(guid'…')` в kb.1ci.com 17.4.13]`.

Описание сервиса (метаданные): `…/odata/standard.odata/$metadata` — стандарт OData 3; ответ EDMX/CSDL с перечнем EntityType, EntitySet и FunctionImport `[ПОДТВЕРЖДЕНО: 1c-dn.com/rest_interface — «клиент может запросить метаданные, описывающие доступные объекты»; имя `$metadata` — стандарт OData, подтверждено фрагментом `$metadata` в 1c-dn.com/forum/forum11/topic1878/]`.

Правила имён (раздел 17.4.4 документации; подтверждённые примеры + типовая практика):

| Объект 1С | Имя ресурса OData | Статус |
|---|---|---|
| Справочник `Имя` | `Catalog_Имя` | `[ПОДТВЕРЖДЕНО: Catalog_Goods, kb.1ci.com 17.4.13]` |
| Документ `Имя` | `Document_Имя` | `[ТИПОВО: общее правило `<ТипОбъекта>_<Имя>`; подтверждается клиентскими библиотеками (packagist odata-1c: Document_АктВыполненныхРабот)]` |
| Табличная часть `ТЧ` справочника/документа | `Catalog_Имя_ТЧ` / `Document_Имя_ТЧ` (отдельный EntitySet, строки с `Ref_Key` владельца и `LineNumber`) ; в составе родителя — навигационное свойство `ТЧ` с типом `…_ТЧ_RowType` | `[ТИПОВО: требует проверки по $metadata]` |
| Регистр сведений `Имя` | `InformationRegister_Имя`; подчинённый регистратору — набор записей `InformationRegister_Имя_RecordType`; срезы — `InformationRegister_Имя/SliceLast(...)`, `/SliceFirst(...)` | `[ПОДТВЕРЖДЕНО: пример `InformationRegister_CurrencyRates_RecordType/SliceLast` с параметром Condition, kb.1ci.com 17.4.13]` |
| Регистр накопления `Имя` | `AccumulationRegister_Имя`; виртуальные таблицы вызываются как функции ресурса: `AccumulationRegister_Имя/Balance(Period=datetime'…',Condition='…')`, `/Turnovers(...)`, `/BalanceAndTurnovers(...)`. Параметры функции Balance в `$metadata`: `Condition` (Edm.String), `Dimensions` (Edm.String), `Period` (Edm.DateTime). Обращение к `AccumulationRegister_Имя_Balance` как к отдельной сущности даёт «Entity not found» | `[ПОДТВЕРЖДЕНО: 1c-dn.com/forum/forum11/topic1878/ (фрагмент $metadata и ответ поддержки 1С)]` |
| Регистр бухгалтерии `Имя` | `AccountingRegister_Имя/Balance(Period=…, AccountCondition='…', Condition='…')`, `/Turnovers(...)`, `/RecordsWithExtDimensions(...)` | `[ПОДТВЕРЖДЕНО (Balance с AccountCondition): kb.1ci.com 17.4.13]`; периодичность в Turnovers не поддерживается — `[ТИПОВО: forum.infostart.ru topic214553, ответ поддержки 1С 2019 г.]` |
| Перечисление | `Enum_Имя` | `[ТИПОВО]` |
| План обмена | `ExchangePlan_Имя` | `[ТИПОВО]` |
| Константа | `Constant_Имя` | `[ТИПОВО]` |

Имена ресурсов и полей — **кириллические имена метаданных как есть** (например `Catalog_Номенклатура`), поэтому URL должны percent-кодироваться в UTF-8 `[ТИПОВО]`.

| `$orderby`, `$expand`, `$count`, `$inlinecount=allpages` | да (разделы 17.4.6.1–17.4.6.4) | `[ПОДТВЕРЖДЕНО (существование раздела по оглавлению ИТС; номер раздела может отличаться по версиям): https://its.1c.ru/db/v8326doc/content/56/1]` |
| `allowedOnly=true` | 1С-специфичный параметр: вернуть только записи, разрешённые RLS, вместо ошибки доступа | `[ПОДТВЕРЖДЕНО (существование): раздел 17.4.5.4 по поисковому фрагменту оглавления ИТС]`; семантика — `[ТИПОВО]` |
| `$format=json` / `application/json` (или заголовок `Accept: application/json`); по умолчанию Atom/XML | `[ПОДТВЕРЖДЕНО: форматы Atom/XML и JSON — 1c-dn.com; синтаксис `?$format=application/json` — Habr 865798]` |
| `odata=nometadata` в `$format` (сокращённый JSON) | `[ТИПОВО]` |
| Серверная пагинация (`@odata.nextLink`, `$skiptoken`) | **нет**: 1С не возвращает ссылку «следующая страница»; клиент обязан сам итерировать `$top/$skip` (или `$filter` по ключу) | `[ТИПОВО; на основании OData v3 и практики; требует проверки на платформе заказчика]` |

Ограничения `$top/$skip`: при больших `$skip` запрос выполняется как «выбрать N и отбросить», что на справочниках 10–50 тыс. элементов терпимо, на регистрах движений — медленно; страницы нестабильны при изменении данных между запросами `[ТИПОВО: общее свойство skip-пагинации; Habr 865798 — «большие объёмы медленно, разбивайте на порции»]`. Рекомендуется ключевая пагинация: `$orderby=Ref_Key&$filter=Ref_Key gt guid'<последний>'&$top=1000` `[НЕ ПОДТВЕРЖДЕНО: сортировка по GUID в OData 1С требует проверки]`.

| Удаление | `DELETE …/Catalog_Имя(guid'…')` — **физическое** удаление (не пометка!). Для пометки — `PATCH {"DeletionMark": true}` | `[ТИПОВО; раздел 17.4.13.1.4]` |

| Запись в регистры накопления/бухгалтерии напрямую | формально поддерживается запись наборов записей; на практике для типовых конфигураций **не рекомендуется** (движения формирует документ) | `[ТИПОВО: forum.infostart topic282541 — запись через OData не удалась, сделали HTTP-сервис]` |

**Критическое замечание.** При записи через OData не выполняется проверка заполнения, но выполняются обработчики `ПередЗаписью/ПриЗаписи` и проверки прав `[ПОДТВЕРЖДЕНО: 1c-dn.com/rest_interface]`. Это значит, что документ, созданный через OData, может быть записан с нарушением бизнес-правил типовой конфигурации (не заполнено соглашение, склад, не рассчитаны суммы/НДС, не заполнены служебные реквизиты, не отработали «действия при проведении» формы). Поэтому для создания заказов рекомендуется HTTP-сервис расширения (разд. 5).

### 2.7. Производительность и лицензии

- Нагрузка: каждый HTTP-запрос OData — отдельный вызов сервера 1С; без повторного использования сеансов каждый запрос создаёт/закрывает сеанс. Платформа поддерживает «повторное использование сеансов интернет-сервисов» с настройкой в `default.vrd` и отдельной настройкой для стандартного OData (глава 17.6, 17.6.3.3 «В файле default.vrd», 17.6.3.4 «Для стандартного интерфейса OData») `[ПОДТВЕРЖДЕНО (существование раздела по оглавлению ИТС; номер раздела может отличаться по версиям): https://its.1c.ru/db/v8326doc/content/56/1]`. Атрибуты вида `reuseSessions`, `sessionMaxAge`, `poolSize`, `poolTimeout` для `<ws>`/`<httpServices>` — `[ТИПОВО: имена атрибутов из примеров публикаций в сети (yandex.ru/support/marketplace-module-1c/service.html); требует проверки по документации 8.3.x]`.
- Лицензии: по п. 10.2.5.8 «Лицензионных правил» (в пересказе форумов) «для работы интернет-сервисов (web-сервисы, http-сервисы, запросы к OData) и фоновых заданий не требуется клиентских лицензий», но для клиент-серверного варианта нужна серверная лицензия сервера 1С:Предприятия `[ТИПОВО: forum.infostart.ru topic256122, topic264212 — цитата взята по поисковым фрагментам, сами страницы не открывались (HTTP 429); номер пункта и редакция правил не верифицированы; первоисточник на its.1c.ru требует входа; подтвердить у франчайзи — открытый вопрос 9]`. Для **файловой** базы, опубликованной через веб-сервер, OData/HTTP-сервисы работают через модуль расширения веб-сервера без сервера 1С `[ПОДТВЕРЖДЕНО (архитектура): 1c-dn.com/1c_enterprise/web_services/ — «в файловом варианте модуль расширения веб-сервера выполняет процедуры»]`; вопрос о лицензии в этом случае — `[НЕ ПОДТВЕРЖДЕНО, проверить у франчайзи]`.
- Для файловой базы одновременная работа веб-публикации и пользователей ведёт к блокировкам на уровне файла — для магазина с несколькими рабочими местами это существенный риск `[ТИПОВО]`.

## 3. HTTP-сервисы, веб-сервисы (SOAP), расширения

### 3.1. HTTP-сервисы конфигурации/расширения

| Утверждение | Статус |
|---|---|
| HTTP-сервис — объект конфигурации (ветка «Общие»); содержит шаблоны URL (с параметризованными сегментами `{param}`) и методы (GET/POST/PUT/DELETE/любой) с обработчиком на встроенном языке; если URL не сопоставлен шаблону — 404; обработчик получает `HTTPСервисЗапрос` (тело, заголовки, параметры URL) и возвращает `HTTPСервисОтвет` | `[ПОДТВЕРЖДЕНО: https://1c-dn.com/1c_enterprise/http_services/]`; раздел 17.3.2 «Создание собственных HTTP-сервисов» — `[существование по оглавлению ИТС; номер раздела может отличаться по версиям]` |
| Публикация — так же, как веб-сервисов (диалог публикации, закладка «HTTP-сервисы»; утилита webinst) | `[ПОДТВЕРЖДЕНО: 1c-dn.com/http_services]`; разделы Руководства администратора 8.3.2.2.3, 8.7 — `[существование по оглавлению ИТС; номер раздела может отличаться по версиям]` |
| Адрес: `http(s)://<host>/<публикация>/hs/<КорневойURL сервиса>/<шаблон>` | `[ТИПОВО: сегмент `hs` — устоявшаяся практика; в официальном тексте 1c-dn явно не приведён]` |
| Поддерживается JWT-аутентификация для HTTP-сервисов (раздел 17.3.1.4) и работа через защищённое соединение (17.3.1.3) | `[ПОДТВЕРЖДЕНО (существование разделов по оглавлению ИТС из поисковых фрагментов, 8.3.26; номера разделов могут отличаться по версиям); доступность JWT зависит от версии платформы — требует проверки]` |
| HTTP-сервисы можно создавать **в расширении конфигурации**; при публикации расширений управляет атрибут `publishExtensionsByDefault` элемента `<httpServices>` в `default.vrd` (или явное описание `<service name=… rootUrl=… enable="true"/>`) | `[ТИПОВО: its.1c.ru/db/intgr83/content/40/hdoc «HTTP-сервисы в конфигурациях расширения» (тело требует входа); yandex.ru/support/marketplace-module-1c/service.html; forum.infostart topic250439]` |
| Для HTTP-сервиса в расширении может потребоваться явно устанавливать привилегированный режим/безопасный режим расширения | `[ТИПОВО: forum.infostart topic250439]` |

Что даёт HTTP-сервис в сравнении с OData:
- произвольный JSON-контракт, спроектированный под POS (один запрос — все данные карточки товара, остатки по складам, цены по виду цен);
- серверная логика на стороне 1С: типовые API конфигурации (программные интерфейсы БСП и конфигурации для создания заказа, расчёта скидок, проверки остатков), корректное заполнение документов «как из формы»;
- **инкрементальная выгрузка**: сервис может читать таблицу регистрации изменений своего плана обмена, отдавать пакет «изменения с номера N» и принимать подтверждение; собственный регистр сведений с версией/хэшем объектов;
- идемпотентность по внешнему идентификатору (разд. 5);
- контроль нагрузки (ограничение размера пакета, кэш).
Цена: разработка и сопровождение расширения силами 1С-специалиста; при обновлении типовой конфигурации расширение нужно проверять на применимость.

### 3.2. Веб-сервисы SOAP/WSDL

Платформа поддерживает создание веб-сервисов в конфигурации (объект «Web-сервис», операции и параметры описываются через XDTO, публикация на веб-сервере; WSDL генерируется платформой), а также потребление сторонних (WS-ссылки) `[ПОДТВЕРЖДЕНО: https://1c-dn.com/1c_enterprise/web_services/]` (раздел 17.2 — существование по оглавлению ИТС; номер может отличаться по версиям). Для нового backend на Dart/Node/Go SOAP не даёт преимуществ перед HTTP-сервисом JSON; рекомендация — не использовать, кроме случая, когда у заказчика **уже** есть опубликованный веб-сервис `[ТИПОВО]`.

### 3.3. Расширения конфигурации как способ не менять типовую

| Утверждение | Статус |
|---|---|
| Расширение — отдельная конфигурация, «подключаемая» к типовой без снятия её с поддержки; типовая продолжает обновляться автоматически, платформа заново объединяет расширение; у расширения есть назначение (Патч/Адаптация/Дополнение); расширение проверяет, что заимствованные объекты не изменились | `[ПОДТВЕРЖДЕНО: https://1c-dn.com/1c_enterprise/extensions/]` |

Типовая конфигурация не снимается с поддержки.

- У товаров с характеристиками `Ид` вида `GUIDНоменклатуры#GUIDХарактеристики` `[ТИПОВО: forum.infostart topic205212]`.

Что даёт для «Оптомстрой» и ограничения:
- Плюсы: типовой механизм есть в УТ 11, УНФ, Рознице (раздел «Обмен с сайтами» в документации УТ 11.5 `[ПОДТВЕРЖДЕНО (существование раздела 8.1): https://its.1c.ru/db/utbase115doc/content/52/hdoc]`), в БП 3.0 — отсутствует `[ТИПОВО]`; выгружает товары, группы, свойства, характеристики, цены по видам цен, остатки по складам, картинки файлами; поддерживает «только изменения» через узел плана обмена «Обмен с сайтом» (регистрация изменений) `[ТИПОВО: forum.infostart topic264008 — изменения появляются после регистрации для узла]`; принимает заказы с сайта и возвращает статусы.
- Минусы: pull-модель «1С толкает на сайт» по расписанию регламентного задания 1С; backend должен реализовать серверную часть протокола `1c_exchange.php`-совместимую; данные о клиентах, долгах, истории продаж, резервах **не передаются**; настройки отбора «куцые» `[ТИПОВО: forum.infostart topic301806]`; выгружаются все склады `[ТИПОВО: qna.habr 1325962]`; заказы ищут контрагента по ИНН/наименованию (нет телефона); не подходит как единственный канал.
- Вариант использования: как **готовый канал первичной загрузки каталога и картинок** (разовая выгрузка в каталог на диске без сайта), если OData/HTTP недоступны в первые недели `[ТИПОВО]`.

### 4.4. Версионирование объектов (БСП) и «История данных» (платформа)

- БСП «Версионирование объектов»: хранит версии объектов в регистре сведений (типично `ВерсииОбъектов`), настройки хранения — регистр `НастройкиВерсионированияОбъектов`, перечисление `СрокиХраненияВерсий` (неделя…бессрочно); заметно увеличивает размер базы; включается по объектам администратором `[ТИПОВО: infostart 2594357, 237921, 1803149]`. Для интеграции полезен косвенно (кто/когда менял), но не как механизм выборки изменений.
- Платформенная «История данных» (с 8.3.11): версионирование на уровне платформы, настраивается в Конфигураторе и программно `[ТИПОВО: infostart 1882953, 1318777]`. Содержит дату изменения версии и может служить источником «что изменилось после T» через встроенный язык (в HTTP-сервисе), но не через OData `[НЕ ПОДТВЕРЖДЕНО как практика]`.
- Журнал регистрации (`ЖурналРегистрации`): фиксирует события «Данные. Изменение» с ссылкой на объект; через OData недоступен `[ТИПОВО: Habr 865798]`, доступен через встроенный язык (`ВыгрузитьЖурналРегистрации`) — возможен как резервный источник изменений в HTTP-сервисе, но дорог и зависит от настроек журнала `[ТИПОВО]`.

## 6. Создание заказа клиента из backend в 1С

### 6.1. Документ и статусы

- УТ 11: `Документ.ЗаказКлиента`. Статусы задаются перечислением (типично `НеСогласован`, `КВыполнению`, `Закрыт`; при включённой функциональной опции согласования появляются состояния «На согласовании»/«Согласован») `[ТИПОВО: forum.infostart topic309074 подтверждает существование статуса «На согласовании» в УТ 11.5.15; точный состав перечисления — требует проверки в Конфигураторе]`. Состояние заказа (оплата/обеспечение/отгрузка) вычисляется отчётом «Состояние выполнения» и не является реквизитом `[ТИПОВО: infostart 2733201]`. Макет IMG_7090.PNG («Заказ будет создан в 1С и отправлен на согласование») согласуется с этим сценарием: POS создаёт заказ в статусе «Не согласован» → менеджер в 1С переводит «К выполнению» → резерв/отгрузка.
- УНФ: `Документ.ЗаказПокупателя` с реквизитом `Состояние` (справочник состояний заказов, настраиваемый) `[ТИПОВО]`.
- БП: заказов нет; эквивалент — «Счёт на оплату покупателю» без складских движений `[ТИПОВО]`.
- Розница 2.x: работа POS «Оптомстрой» с заказами в Рознице 2 ограничена; для Розницы 3.0 — требует проверки `[НЕ ПОДТВЕРЖДЕНО]`.

### 6.2. OData vs HTTP-сервис для записи документов

| Критерий | OData POST `Document_ЗаказКлиента` | HTTP-сервис расширения |
|---|---|---|
| Заполнение документа | только переданные поля; служебные реквизиты, суммы, НДС, соглашение, статусы, «Обеспечение» могут остаться незаполненными; проверка заполнения **не выполняется** `[ПОДТВЕРЖДЕНО: 1c-dn.com/rest_interface]` | полное заполнение через типовые процедуры (`ЗаполнитьПоУмолчанию`, пересчёт сумм, `ЗаказКлиента.ЗаполнитьТоварыПоЦенам`-подобные API) `[ТИПОВО]` |
| Скидки | не рассчитываются | рассчитываются типовым движком |
| Проведение | отдельный вызов `Post`; ошибки проведения — общий текст | проведение в той же транзакции с понятным JSON-ответом (код ошибки, строка ТЧ) |
| Идемпотентность | нет встроенной; нужен предварительный `GET …?$filter=<поле_внешнего_ид> eq '…'` — а у типового документа нет поля внешнего идентификатора (кроме `Комментарий`/доп. реквизита) | расширение добавляет регистр `ВнешниеИдентификаторыPOS (ВнешнийИд → Документ)` и возвращает тот же документ при повторе |
| Права | пользователю OData нужны права «Добавление/Проведение» на документы — риск при компрометации | можно дать права только HTTP-сервису через привилегированный режим, а пользователю — минимум |
| Трудоёмкость | 0 на стороне 1С | 2–5 дней работы 1С-разработчика на MVP `[НЕ ПОДТВЕРЖДЕНО, оценка]` |

**Рекомендация:** чтение — OData (быстрый старт, без доработок 1С) + HS для картинок/цен/остатков «одним вызовом» по мере готовности; **запись** (заказы, клиенты, платежи) — только HS. Если 1С-разработчика нет, допустим временный режим «OData POST + Post» с обязательным ручным контролем заказов в 1С и обязательным внешним ID в реквизите `Комментарий`/дополнительном реквизите `[ТИПОВО]`.

### 6.3. Идемпотентность

1. Backend генерирует `order_external_id` (UUID v4) до вызова 1С и сохраняет его вместе с состоянием `pending_1c`.
2. HS `POST /orders` принимает `external_id`; если в регистре `ВнешниеИдентификаторыPOS` запись есть — возвращает `200` с существующим `Ref_Key`/номером, иначе создаёт документ в транзакции вместе с записью регистра и возвращает `201`.
3. При таймауте backend повторяет вызов с тем же `external_id` (экспоненциальная пауза); при двойном создании (режим OData) — сверка по `Комментарий` и пометка дубликата на удаление администратором.
4. Номер документа 1С (`Number`) и `Ref_Key` сохраняются в backend; POS показывает номер 1С только после подтверждения.

## 8. Оценка частоты синхронизации 30 минут и нагрузки

| Категория данных | Объём (оценка для магазина: 1,5–3 тыс. SKU по макету каталога; реальные цифры неизвестны) | Нужная частота | Способ | Нагрузка на 1С |
|---|---|---|---|---|
| Номенклатура, группы, виды, характеристики, доп. реквизиты, упаковки, штрихкоды | 2–10 тыс. записей | 30 мин достаточно; критичные правки (новый товар) — ручной запуск | OData `$select` минимума полей, страницы по 1000; diff по `DataVersion` | низкая (несколько запросов, секунды) |

| Заказы из POS → 1С | единицы–десятки в час | немедленно (онлайн), очередь с повторами | HS | низкая |
| Статусы заказов 1С → POS | по открытым заказам | 5–10 мин | OData: цепочка `$filter=Ref_Key eq guid'…' or Ref_Key eq guid'…' or …` пакетами по 20–50 ссылок (ограничение длины URL). Оператор `in` в `$filter` **неприменим**: его нет в OData v3 (появился в OData 4.01), а 1С использует OData v3 `[ПОДТВЕРЖДЕНО: https://1c-dn.com/1c_enterprise/rest_interface/ — «The platform uses OData version 3»]`; допустимая длина цепочки `or`/URL — `[ТИПОВО, требует проверки на платформе заказчика]`. Альтернатива — HS по списку ID | низкая |

Инкрементальный обмен без даты изменения — варианты по убыванию надёжности:
1. **План обмена в расширении** (узел «POS»; авторегистрация по Номенклатура, Характеристики, Цены (регистратор), Партнёры/Контрагенты, Склады, Штрихкоды, ЗаказКлиента) + HS `GET /changes?since=<номер сообщения>` и `POST /changes/ack`. Ловит создание, изменение, пометку и **физическое удаление**. Требует 1С-разработчика `[ПОДТВЕРЖДЕНО (механизм): 1c-dn.com exchange plans]`.
2. **DataVersion-сравнение через OData**: периодически читать только `Ref_Key,DataVersion` (и `DeletionMark`) всех записей сущности, сравнивать с кэшем backend, дочитывать изменённые полностью. Не видит физических удалений (отсутствующий Ref_Key = удалён — выводится по полному списку ключей, поэтому список ключей читается целиком). Для 10 тыс. SKU — 10 запросов по 1000 строк `[ТИПОВО: qna.habr 1348438]`.
3. **Хэш-сравнение**: backend считает хэш нормализованной записи — защищает от «ложных» изменений (DataVersion меняется при любой записи, даже без изменения полей).
4. **Журнал регистрации / История данных** — только через HS; резерв.
5. **«Обмен с сайтом» с флагом «только изменения»** — использует типовой план обмена; подходит для каталога/цен/остатков/картинок, не для клиентов и долгов.

Контроль целостности: при каждой полной сверке (ночью) сравнивать `$count`/`$inlinecount=allpages` сущности с количеством в backend; расхождение → полная перезагрузка сущности. Монитор: время последней успешной синхронизации по каждой сущности, число ошибок, длительность, число изменённых записей.

## 9. Выбор стратегии (резюме для архитектора)

| Этап | Канал | Условие |
|---|---|---|
| Пилот / первые недели | **OData (чтение)**: номенклатура, группы, характеристики, упаковки, штрихкоды, цены (SliceLast), остатки (Balance), партнёры/контрагенты + телефоны, долги (Balance), история продаж | платформа ≥ 8.3.5, веб-сервер, VPN; доработок 1С нет |
| Пилот (запись) | OData POST `ЗаказКлиента` + `Post` **только** если 1С-разработчик недоступен; иначе HS | внешний ID в документе, ручной контроль |
| Релиз 1 | **Расширение «Оптомстрой POS»**: HS (`/catalog/changes`, `/images/{id}`, `/prices`, `/stock`, `/customers/by-phone`, `/orders`, `/orders/{id}/status`, `/customers/{id}/debt`), план обмена «POS», регистр внешних ID | 1С-разработчик, тестовая копия базы |
| Резерв | «Обмен с сайтом» CommerceML для первичной загрузки каталога и картинок | если УТ/УНФ/Розница и OData пока не опубликован |

Источник истины: мастер-данные (товары, цены, остатки, клиенты 1С, документы продаж, долги) — **1С**; POS-операционные данные (корзины, избранное, профили, привязка телефонов к партнёрам, статусы POS-заказа до подтверждения 1С) — backend.

## 10. Чек-лист проверок для заказчика / его 1С-специалиста

Простым языком; ожидаемый результат указан в скобках.

1. **Версия платформы и конфигурации.** 1С:Предприятие → кнопка «i» / «О программе». (Записать: версия платформы `8.3.x.y`; название и релиз конфигурации; «базовая» или ПРОФ; файловая или клиент-серверная база; имя ИБ.) Критично: платформа ниже 8.3.5 — OData нет; базовая версия — ограничения на доработку (расширения в базовых версиях ограничены `[НЕ ПОДТВЕРЖДЕНО]`).
2. **Локализация.** Указано ли в названии «для Кыргызстана»? (Да/нет; если да — приложить скриншот окна «О программе» и список разделов главного меню.)
3. **Типовая или доработанная.** Конфигуратор → Конфигурация → Поддержка → Настройка поддержки. (Ожидается «Конфигурация находится на поддержке» с правилом «Объект поставщика не редактируется»; если «снята с поддержки» — есть доработки, нужна их опись.) Конфигуратор → Конфигурация → Расширения конфигурации. (Список расширений: имена, назначение.)
4. **Веб-публикация уже есть?** На сервере 1С: открыть в браузере `http://<сервер>/<имя_базы>/` (если появляется окно входа веб-клиента — публикация есть); проверить `http://<сервер>/<имя_базы>/odata/standard.odata/` (ожидается XML со списком коллекций или запрос пароля; `404` — OData не опубликован). Ожидаемый ответ `$metadata` — большой XML, начинающийся с `<edmx:Edmx …>`.
5. **Какой веб-сервер.** Windows: «Службы» — есть ли «World Wide Web Publishing Service» (IIS) или «Apache2.4». Linux: `systemctl status apache2|httpd`. (Записать тип и версию.)
6. **Лицензии и сервер.** Есть ли сервер 1С:Предприятия (клиент-серверный вариант) и серверная лицензия; сколько клиентских лицензий. (По форумным цитатам для OData/HTTP-сервисов клиентские лицензии не нужны, но нужна серверная; уточнить номер пункта Лицензионных правил (по фрагментам — п. 10.2.5.8, не верифицировано) и актуальную редакцию на its.1c.ru или у франчайзи.)
7. **Состав OData (БСП).** 1С:Предприятие → Администрирование → Синхронизация данных (или «Интернет-поддержка и сервисы») → «Настройки стандартного интерфейса OData». (Ожидается форма с вкладками «Авторизация» и «Состав»; если пункта нет — состав задаётся кодом `УстановитьСоставСтандартногоИнтерфейсаOData`.)
8. **Пользователь интеграции.** Администрирование → Пользователи → создать `pos_integration`, сложный пароль, снять «Показывать в списке выбора», группы доступа: «Удалённый доступ через OData» (если есть) + чтение торговых данных. Проверка: `curl -u pos_integration:*** "http://<сервер>/<база>/odata/standard.odata/Catalog_Номенклатура?$top=1&$format=json"` → JSON с одной записью, в ней `Ref_Key`, `DataVersion`, `DeletionMark`, `Code`, `Description`. (`401` — неверный пароль/нет права аутентификации; `403`/«Нарушение прав доступа» — нет ролей; «Entity not found» — объект не включён в состав OData.)
9. **Имена объектов.** Скачать `$metadata` и прислать файл (нужно проверить наличие: `Catalog_Номенклатура`, `Catalog_ХарактеристикиНоменклатуры`, `Catalog_Партнеры` или `Catalog_Контрагенты`, `Catalog_Склады`, `Catalog_ВидыЦен`/`Catalog_ТипыЦенНоменклатуры`, `Catalog_УпаковкиЕдиницыИзмерения`, `InformationRegister_ЦеныНоменклатуры`, `InformationRegister_ШтрихкодыНоменклатуры`, `AccumulationRegister_ТоварыНаСкладах`/`ЗапасыНаСкладах`, `AccumulationRegister_СвободныеОстатки`, `AccumulationRegister_РасчетыСКлиентами`/`AccountingRegister_Хозрасчетный`, `Document_ЗаказКлиента`/`ЗаказПокупателя`, `Document_РеализацияТоваровУслуг`, `Document_ЧекККМ`, `Document_ПриходныйКассовыйОрдер`, `Catalog_НоменклатураПрисоединенныеФайлы`).
10. **Ключевые настройки учёта.** Записать: ведётся ли учёт по характеристикам (НСИ и администрирование → Номенклатура → «Характеристики номенклатуры»); используются ли упаковки; сколько складов и какие (Склады); какие виды цен используются при продаже (CRM и маркетинг/Продажи → Виды цен); включено ли «Согласование заказов клиентов»; ведутся ли партнёры и контрагенты раздельно; используются ли автоматические скидки и какие (Скидки (наценки)); ведётся ли взаиморасчёт по договорам/заказам/накладным; как хранятся картинки (Администрирование → Настройки работы с файлами → «Хранить файлы в томах на диске» или в ИБ) и сколько их.
11. **Объёмы.** Количество элементов Номенклатуры (не групп), характеристик, партнёров/контрагентов, документов продаж за последний год, размер базы (МБ), количество одновременных пользователей. (Через `$count`: `…/Catalog_Номенклатура/$count` `[ТИПОВО]` или отчётами.)
12. **Сеть.** Внешний IP магазина статический? Есть ли роутер с поддержкой VPN (WireGuard/IPsec/OpenVPN)? Кто администрирует сеть? Работает ли сервер 1С круглосуточно? (Для выбора варианта A/B/C/D из разд. 7.)
13. **Процессы.** Кто в 1С будет согласовывать заказы POS; какие документы оформляют на оплату наличными и картой/QR Бакай Банка (ПКО? ЧекККМ? эквайринг?); как оформляется продажа в долг; как оформляются возвраты (нужны названия документов из их 1С).
14. **Тестовая копия.** Готовность предоставить **копию** базы (выгрузка `.dt` или бэкап СУБД) с обезличенными данными либо тестовую ИБ на том же сервере для публикации OData/HS без риска для рабочей базы.
15. **1С-специалист.** Есть ли франчайзи/штатный программист 1С, готовый поставить расширение и опубликовать базу; срок.
16. **Проведение через OData (на тестовой базе).** Выполнить `POST …/odata/standard.odata/Document_<Имя>(guid'<ссылка тестового документа>')/Post` без параметров и затем `…/Unpost`. (Ожидается `200`/`204` и смена `Posted`; записать, принимает ли сервер параметр режима проведения и под каким именем — в отчёте имя `PostingModeOperational` помечено `[НЕ ПОДТВЕРЖДЕНО]`.)
17. **Balance без Period (на тестовой базе).** Выполнить `GET …/AccumulationRegister_<Имя>/Balance()` без параметра `Period` и то же с `Period=datetime'<текущее время>'`. (Записать: отвечает ли сервер без `Period` или требует его; в отчёте допустимость пропуска помечена `[НЕ ПОДТВЕРЖДЕНО]`.)
