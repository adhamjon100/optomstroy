## 0. Главное (для заказчика, коротко)

1. **Сделать вход по лицу технически можно, но только как «удобство», а не как защиту.** На обычной веб-камере кассы или фронтальной камере телефона собственное решение отсекает «ленивые» атаки (распечатанное фото, фото на экране телефона) и частично — повтор видео. От deepfake, анимированного фото, масок и особенно от **подмены камеры** (виртуальная камера OBS на Windows; в Windows 11 виртуальную камеру Media Foundation для текущего пользователя можно создать **без прав администратора**, §3.1) оно не защищает. По классификации Android это уровень не выше **Class 1 (Convenience)** (§3).
2. **Главный правовой риск — не технический.** По Цифровому кодексу КР № 178 (гл. 11, ст. 80) биометрия «для цифровой идентификации» — специальная категория, обработка которой запрещена, а **согласия нет среди 11 исключений**. Дополнительно ст. 48 ч. 5 буквально запрещает обработку биометрии в иных целях, чем у государственной системы. Допустимость модуля для частного магазина решает только юрист, лучше с разъяснением ГАЗПД (§4). До заключения разработку начинать нельзя.
3. **Рекомендуемая архитектура — «гибрид» (вариант В):** шаблон лица и сравнение 1:1 — **только на устройстве**; сервер не хранит биометрию, а ведёт включение, счётчики неудач, отзыв, аудит и сессии; лицо **заменяет PIN только при разблокировке** уже привязанной к устройству сессии; вход на новом устройстве — по SMS-коду, как сейчас; лицо не используется для step-up; PIN сотрудника остаётся обязательным (§5).
4. **«Регистрироваться по лицу» без SMS нельзя** без пересмотра D-08/D-10: номер телефона — идентификатор учётной записи и ключ привязки к клиенту 1С. Лицо «регистрируется» как способ защиты входа **после** подтверждения номера (шаг SCR-04) (§5.4).
5. **Реальная ценность — у сотрудников на общей Windows-кассе:** быстрая смена кассира без ввода PIN. Там нет криптопривязанной системной биометрии (D-13: Windows Hello только UX-гейт), а Windows Hello к тому же регистрирует одно лицо на учётную запись ОС и работает только с ИК-камерой. Для покупателей на iPhone и Android с биометрией Class 3 системная биометрия (D-13) **сильнее** собственной (§3.6, §6).
6. **Технический стек.** Единственная найденная связка с явно разрешающими коммерческое использование лицензиями и на код, и на веса и с одной обвязкой Dart на трёх платформах: **`opencv_dart` 2.2.2 (Apache-2.0) + YuNet (MIT) + SFace (Apache-2.0)**, пассивная PAD — **MiniFASNet (Apache-2.0)** с оговоркой о неизвестных обучающих данных. PAD, прошедший испытания в лаборатории (письмо-подтверждение iBeta или BixeLab для конкретной конфигурации; iBeta сама подчёркивает, что это не сертификация продукта), есть у коммерческих SDK (Luxand FaceSDK, Neurotechnology VeriLook), цены по запросу; **покрывает ли какое-либо письмо Windows с USB-веб-камерой — не подтверждено** (§2.5).
7. **Главное техническое препятствие — камера Windows.** Официальный `camera_windows` не отдаёт поток кадров; `camera_desktop` 2.0.0 (MIT) отдаёт, но требует Dart ≥ 3.11, то есть обновления Flutter относительно утверждённого 3.38.7 (ADR-086). Без потока кадров активная проверка живости на кассе невозможна. Нужен прототип на реальной кассе заказчика (§2.4).
8. **Запасной вариант всегда есть:** системная биометрия + PIN + SMS, как в утверждённом ТЗ. Вариант В выключается настройкой `FACE_LOGIN_MODE=off` без миграции данных и без потери доступа (§7).
9. **Общая учётная запись Windows — главная слабость (редакция 2).** Неизвлекаемый ключ TPM защищён от извлечения, но не от использования: на общей учётной записи им может подписывать любой процесс, а `face_refresh` в Credential Manager (DPAPI) расшифровывается той же учётной записью. Значит, кассир, запустивший скрипт или переносимую программу (права администратора не нужны), откроет кассу под любым коллегой **без лица и без PIN** и скопирует шаблоны (§5.6). Поэтому вход по лицу для сотрудников на Windows возможен только на кассе с изоляцией: режим киоска + WDAC/AppLocker с правилами для exe, dll и скриптов, или отдельные учётные записи Windows (P-001 FLOG-040). Вторая простая атака — коллега нажимает плитку, когда владелец рядом; закрывается обязательной активной проверкой, которую выполняет сам субъект (§3.1 T10).

## 1. Постановка задачи и что на самом деле нужно заказчику

| Что сказал заказчик | Что из этого выполнимо | Почему |
|---|---|---|
| «Регистрироваться по лицу» | Частично: при регистрации (после SMS-кода) можно включить вход по лицу | Номер — идентификатор и ключ привязки к 1С (D-08, D-10); лицо не доказывает владение номером. Регистрация «только по лицу» = вариант Б (сервер), не рекомендуется (§5.2) |
| «Входить по лицу» | Да, как разблокировка уже привязанной к устройству сессии (вместо PIN) | Требование NIST SP 800-63B-4 §3.2.3: биометрия — только вместе с физическим аутентификатором (устройством) (§3.4) |
| «Вход по лицу с любой кассы / телефона без SMS» | Нет (не рекомендуется) | Однофакторный вход, центральная база шаблонов, противоречие SEC-108 (д) (§5.2) |
| (подразумевается) «Несколько кассиров на одной кассе, быстро сменять» | Да, 1:1 по выбранной плитке сотрудника | Это и есть, по всей видимости, реальная причина запроса: системная биометрия на общей учётной записи Windows кассиров не различает (§3.6) |

### 3.1. Модель угроз для POS

Главный нарушитель — **коллега-сотрудник с физическим доступом к кассе** (вход под кассиром со скидками, возвратами, долгами). У него есть время, повторные попытки и фото/видео коллег. Против него RGB-решение слабее всего.

| № | Атака | Активная проверка (моргнуть/повернуть) | Пассивная PAD (MiniFASNet) | Системная биометрия (Face ID / Hello ИК) |
|---|---|---|---|---|
| T1 | Фото коллеги (печать, экран телефона) | В основном да | Вероятно да (проверить тестом) | Да (глубина/ИК) |

### 3.5. Внутренний протокол PAD-теста (по образцу iBeta L1)

Устройства — каждая модель веб-камеры кассы и 2–3 типовых смартфона; ≥ 10 сотрудников-добровольцев — **только после заключения юриста, в котором тестовый набор оценён отдельно** (редакция 2): «отдельное письменное согласие» само по себе не основание (согласия нет среди исключений ст. 80 ч. 2; п. 11 «научные цели» требует обезличивания, невозможного для изображений лиц; зависимость сотрудников от работодателя); материалы атак (фото и видео сотрудников) хранятся до акта уничтожения — это исключение из правила «кадры не сохраняются» и указывается участникам. До заключения — только технические проверки (камера, TPM, скорость) на синтетике или лицензированных наборах. Виды PAI: (1) печать A4, (2) фото на экране телефона, (3) видео на телефоне, (4) видео на планшете/ноутбуке, (5) бумажная маска, (6) анимированное фото, (8) заранее записанная библиотека поворотов; отдельно (7) подмена видеопотока: OBS с правами администратора, виртуальная камера MF `CurrentUser` без прав администратора, внедрение кадров в процесс. На вид — 150 атак и 50 живых предъявлений. Внутренний тест **не является сертификацией** и не даёт права ссылаться на ISO/IEC 30107-3 или iBeta. Ожидание (оценка автора части 2, не факт): (1)–(2) вероятно отсекаются, (3)–(4) неопределённо, (5)–(6) частично проходят, (7) проходит.

| Критерий | Системная (Face ID, Android Class 3, Windows Hello с ИК) | Собственное RGB-распознавание |
|---|---|---|
| Сенсор | Глубина / ИК | RGB, любая веб-камера |

### 3.7. Что честно обещать

- **Обещаем** (после успешного внутреннего теста): вход только выбранного/привязанного сотрудника при живом лице; отказ по распечатанному фото и фото на экране в типичных условиях (без гарантии); PIN/SMS всегда; кадры не сохраняются.
- **Частично:** повтор видео; спящий/отвлечённый человек (если включена проверка открытых глаз).
- **Не защищает:** N1 deepfake/анимация; N2 подмена камеры или кадров, хуки на рутованном Android; N3 маски; N4 близнецы; N5 принуждение и сговор; N6 модифицированный клиент или модели (архитектура не даёт выпустить токены без ключа устройства, но на устройстве лицо тогда ничего не доказывает); N7 не является средством KYC/юридической идентификации; N8 выполнение кода в общей учётной записи ОС без изоляции (вход без лица).
- **Частично (редакция 2):** коллега выбирает плитку владельца, стоящего рядом (T10) — закрывается обязательной активной проверкой и отказом при двух лицах, остаётся социальная инженерия.
- **Запрещённые формулировки** (UI, маркетинг, договор): «защита от подделки», «гарантирует распознавание живого лица», «соответствует ISO 30107», «как Face ID», «сертифицированная биометрия».

### 4.3. Где хранить шаблон — правовое сравнение

| Критерий | Системная биометрия ОС (сейчас) | Шаблон **только на устройстве** | Шаблон **на сервере** |
|---|---|---|---|
| Кто обрабатывает | ОС | Приложение магазина | Приложение + сервер |
| Владелец записей | По позиции ТЗ — магазин биометрию не обрабатывает `[ТИПОВО]` | **Магазин** (ст. 1 п. 6) | Магазин |
| Центральная база | Нет | Нет | **Есть** |
| DPIA | Облегчённая | При > 1000 обязательна; рекомендуется всегда | Фактически всегда |
| Итоговый правовой риск | Низкий | **Высокий**, но наименьший из собственных вариантов; для общей кассы сотрудников — выше, чем для телефона покупателя (см. ниже) | **Очень высокий**, не рекомендуется |
| Ориентир EDPB Opinion 11/2024 | — | «В принципе совместимым» назван сценарий 1 — шаблон «in the hands of the individual… on their individual device, under their sole control», 1:1. **Для общей кассы не подходит**: шаблоны сотрудников лежат на устройстве работодателя под его контролем | Сценарий 2 (централизованное зашифрованное хранение с ключом **только у самого человека**) тоже назван «в принципе совместимым»; хранение под контролем оператора (сценарии 3 и 4) — несовместимым |

`[ПОДТВЕРЖДЕНО: edpb.europa.eu, PDF Opinion 11/2024, принят 23.05.2024, проверено 2026-10-28]` (в первой редакции сводки здесь был неточный пересказ по поисковой выдаче: «единственный вариант, который может пройти тест необходимости»).

**Общая касса (редакция 2).** На общей кассе шаблоны до 10 сотрудников хранятся на кассе работодателя, а по P-001 (редакция 2) часть ключа шифрования (`K_srv`) — на сервере магазина. Это ближе к хранению под контролем оператора (сценарии 3/4), чем к сценарию 1, и сотрудник не может сам проверить удаление; правовой риск режима `staff` **выше**, чем для телефона покупателя. Кроме того, без изоляции ОС любой процесс общей учётной записи может расшифровать шаблоны коллег (§5.6) — это раскрытие специальной категории данных. В DPIA это пишется прямо; влияет ли хранение `K_srv` на квалификацию — `[ТРЕБУЕТ ЗАКЛЮЧЕНИЯ ЮРИСТА]`.

**Обратимость шаблона.** Опубликованы атаки, восстанавливающие узнаваемое изображение лица из эмбеддинга (в т. ч. только по оценкам сходства): https://arxiv.org/pdf/1703.00832 ; https://arxiv.org/pdf/2106.14290v2 ; https://publications.idiap.ch/attachments/papers/2024/OtroshiShahreza_IJCB-2_2023.pdf `[ВТОРИЧНО: по данным рецензии 2026-10-28; полные тексты не изучались; на SFace не проверялось]`. Шаблон считать обратимым.

Важно: «только на устройстве» не значит «закон не применяется». И тест необходимости: при наличии системной биометрии (вариант А) обосновать собственное распознавание перед регулятором трудно — сильнейший довод для узкого применения (общие кассы).

### 4.4. Обязательный минимум (если заказчик сохраняет решение)

## 5. Архитектура (часть 4)

Источники — §12.4. Сверено с кодом: `pos-api/src/auth/sessions/refresh.service.ts` (`RotationMode = 'refresh' | 'unlock_pin' | 'unlock_biometric'`), `pos-api/src/db/schema/enums.ts` (`session_kind` = `standard | biometric`; `consent_kind` уже содержит `face_scan`), `pos-app/lib/core/session/session_controller.dart` (вход другого пользователя очищает данные прежнего, стр. ≈ 203–209), `pos-app/lib/core/biometrics/*` (порт `BiometricAuthenticator`, `windows_hello_gate.dart`).

### 5.1. Ограничение, определяющее всё

Аппаратные хранилища ОС (Android Keystore, iOS Keychain) открывают ключ только по аутентификации самой ОС (экран блокировки или системная биометрия). **Собственное распознавание лица приложения не может быть условием доступа к аппаратному ключу** `[ПОДТВЕРЖДЕНО: developer.android.com/privacy-and-security/keystore, 2026-10-28]`; там же: при скомпрометированном процессе «атакующий может использовать ключи приложения». Значит, «лицо совпало» — это программный результат в процессе приложения, и сервер не должен принимать его как доказательство само по себе.

### 5.2. Три варианта

| Критерий | А — только устройство | Б — шаблон на сервере | **В — гибрид (рекомендуется)** |
|---|---|---|---|
| Где шаблон | Устройство | Сервер (БД, бэкапы) | Устройство |
| Вход на новом устройстве | SMS | Номер + лицо | SMS |
| Факторы при входе по лицу | Программный секрет + лицо | Только лицо (номер — идентификатор) | **Неизвлекаемый ключ устройства** + лицо (лицо — проверка в клиенте, сервер её не проверяет: по сути однофакторное «владение устройством») |
| NIST 800-63B-4 §3.2.3 | Частично (счётчик на клиенте) | Нарушается на новом устройстве | **Не соответствует** как многофакторный (ключ доступен без лица, а NIST требует доступ к ключу «only… through the presentation and verification of an activation factor»); лишь ближе других к требованию «биометрия вместе с физическим аутентификатором» (редакция 2) |
| SEC-108 (д) «без центральной базы» | Да | **Нет** | Да |
| Счётчики неудач | На клиенте (сбрасываются) | Сервер | **Сервер** |
| Утечка при взломе сервера | Нет биометрии | Все шаблоны | Нет биометрии |
| Изменения сервера | Малые | Большие (ML на сервере, нейтральность D-10) | Малые–средние |
| Откат при отрицательном заключении юриста | Флаг | + удаление центральной базы и бэкапов | **Флаг `FACE_LOGIN_MODE=off`** без миграции |

### 5.3. Вариант В — элементы

1. **Ключ устройства**: при включении входа по лицу создаётся неизвлекаемый ключ (Android Keystore, iOS Secure Enclave/Keychain `[ТИПОВО: флаги Apple не проверены]`, Windows TPM через Microsoft Platform Crypto Provider — ключи «не могут быть извлечены» `[ПОДТВЕРЖДЕНО: learn.microsoft.com, cng-key-storage-providers, обновлено 2026-06-23, проверено 2026-10-28]`). Публичная часть — на сервере. **Неизвлекаемый — не значит недоступный**: ключ создаётся без пользовательского жеста, и на общей учётной записи им может подписывать любой процесс этой учётной записи `[ВЫВОД: из модели KSP; проверить в FL-1]` (§5.6). **Аттестация ключа (редакция 2)**: Android — Key Attestation, `attestationSecurityLevel` TrustedEnvironment или StrongBox `[ПОДТВЕРЖДЕНО: developer.android.com/privacy-and-security/security-key-attestation, обновлено 2026-07-09, проверено 2026-10-28]` + Play Integrity; Windows — аттестация ключа TPM описана Microsoft только для RSA-ключей, Platform Crypto Provider и сценария AD CS (доверие по EKPub или EK-сертификату; программный KSP при правах локального администратора можно выдать за TPM) `[ПОДТВЕРЖДЕНО: learn.microsoft.com/windows-server/identity/ad-ds/manage/component-updates/tpm-key-attestation, обновлено 2025-09-23, проверено 2026-10-28]`, проверка на собственном сервере — `[НЕ ПОДТВЕРЖДЕНО]`; iOS — App Attest / DeviceCheck `[НЕ ПОДТВЕРЖДЕНО]`. Программное хранилище ключа — запрещено.
2. **Разблокировка (редакция 2 — сначала nonce)**: при нажатии плитки, до включения камеры, `POST /auth/unlock/nonce` (подписанный `startProof`) → nonce 128 бит, TTL 60 с, привязан к `userId`, `deviceId`, регистрации; в том же ответе — серверная часть ключа шаблона `K_srv`. Затем `POST /auth/unlock {method: "face", refreshToken: face_refresh, deviceProof, result}`, где `deviceProof` — подпись канонического объекта `{ctx: "optomstroy-face-unlock-v1", nonce, sid, userId, deviceId, method, result, ts}` (разделение доменов, результат покрыт подписью). В `RefreshService` добавляется `unlock_face`. Лицо разрешено только в окне `FACE_PIN_WINDOW_HOURS` после разблокировки по PIN в этой смене.
3. **Счётчики на сервере** по (`user_id`, `device_id`): **каждый выданный и не погашенный успехом nonce — неудача**, независимо от сообщения клиента (первая редакция считала только неудачи, о которых сообщил клиент: закрыв приложение, атакующий обходил счёт); лимит выдачи nonce и задержка ≥ 30 с (NIST).
4. **Шаблон привязан** к `user_id` и `enrollmentId` через дополнительные данные AES-GCM; ключ шаблона разделён: `KEK = HKDF(K_dev ∥ K_srv)` — после удаления `K_srv` на сервере шаблон нерасшифровываем (криптографическое стирание). Прежняя формулировка «MAC ключом устройства — нельзя подложить чужой шаблон» защищала лишь от наивной подмены файла: процесс с тем же ключом пересчитает MAC.
5. **Опционально** — проверка живости у вендора при регистрации; по части 3 облачные зарубежные — запретить; on-premise в КР — `[НЕ ПОДТВЕРЖДЕНО]`. По умолчанию выключено.
6. Лицо **не** заменяет OTP на новом устройстве, **не** для step-up (остаются `pin`, `otp`), PIN `staff` обязателен (D-48).

### 5.4. Регистрация лица и вход — где в потоке

- Регистрация лица — **после OTP**: клиент — SCR-04 «Защита входа» (третий способ наряду с PIN и системной биометрией); сотрудник — SCR-04 после обязательного PIN; позже — SCR-42 (step-up). Съёмка — SCR-05 в новом режиме `enroll_face_login`. На сервер уходит только факт и публичный ключ; кадры — только в памяти.
- Разблокировка — SCR-08: (а) один профиль — «Войти по лицу» / PIN; (б) общая касса — **плитки профилей** (имя, роль, без фото) → лицо 1:1 или PIN.

### 5.5. Общая касса: многопрофильность

Сейчас клиент однопользовательский (09 §4.5, SEC-091; `SessionController.establish` очищает данные прежнего пользователя; ключи secure storage общие). Для 1:1 по плиткам нужны профили кассы с отдельными токенами: ключи хранилища по `user_id` (`refresh:<uid>`, `face_refresh:<uid>`, `face_template:<uid>`), «Сменить кассира» = блокировка + выбор плитки, «Выйти» = удаление своего профиля. Сервер менять не нужно: `devices` уже уникален по (`user_id`, `device_key`). **Это крупнейший объём работ на клиенте** и изменение действующих правил 09 §4.5 / SEC-091.

| Платформа | Предложение | Не защищает от |

| iOS | Keychain `WhenUnlockedThisDeviceOnly` `[ТИПОВО]` | То же на jailbreak |

Программный запасной путь без TPM **отменён** (редакция 2). Данные — в `%LOCALAPPDATA%`, при удалении — `NCryptDeleteKey` и скрипт очистки (zip-установка деинсталлятора не имеет, 16 §10.7) | Других кассиров и любых процессов **той же** общей учётной записи ОС: DPAPI расшифровывает, как правило, пользователь с теми же учётными данными `[ПОДТВЕРЖДЕНО: learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata, обновлено 2026-05-15, проверено 2026-10-28]`, а ключом TPM может подписывать любой процесс учётной записи. **Следствие:** скрипт без прав администратора открывает чужой профиль без лица и PIN и расшифровывает шаблоны коллег (через онлайн-запрос `K_srv`). Credential Locker не годится (≤ 20 записей, только пароли) |

## 7. Рекомендации

1. **Порядок:** юридическое заключение (ст. 48 ч. 5, ст. 80) и решения заказчика → прототип на реальной Windows-кассе (камера + стек A + MiniFASNet + TPM-ключ + внутренний PAD-тест) → ADR по результатам → изменение ТЗ → разработка Windows (сотрудники) → Android → iOS (если Q-008 = «да»). Функция не блокирует R1 и пилот этапа I.
2. **Архитектура:** вариант В; только 1:1; многопрофильная касса с плитками; `FACE_LOGIN_MODE = off | staff | all`, по умолчанию `off`.
3. **Стек:** A для прототипа; параллельно запросить коммерческие предложения Luxand и Neurotechnology (офлайн PAD на Windows, цена за кассу, Flutter-обвязка). Переход на C — если внутренний PAD-тест стека A не выполнит пороги по видам PAI (1)–(4).
4. **Камера Windows:** решить на прототипе между `opencv_dart VideoCapture`, собственным плагином Media Foundation и обновлением Flutter ради `camera_desktop` (пересмотр ADR-086).
5. **Изоляция касс (редакция 2):** «кассиры без прав администратора» и «запрет установки ПО» **недостаточны** — переносимые программы, PowerShell и виртуальная камера MF `CurrentUser` работают без установки и без прав администратора. Условие режима сотрудников на Windows — режим киоска (Assigned Access / Shell Launcher) плюс WDAC или AppLocker в принудительном режиме с правилами для exe, dll и скриптов (PowerShell в Constrained Language Mode, запрет cmd, wscript, mshta, переносимых exe), либо отдельные учётные записи Windows на кассира (теряется быстрая смена плитками); каталог приложения недоступен на запись кассиру; хэши моделей проверяются; камера закреплена; проверка тестом «скрипт без прав администратора открывает чужой профиль → невозможно». Применимость к редакции Windows заказчика — `[НЕ ПОДТВЕРЖДЕНО]` (R9-Q19).
6. **Покупатели:** по умолчанию — системная биометрия D-13; собственное лицо для покупателей — только отдельным решением заказчика и **только на устройствах без системной биометрии Class 3 / Face ID** (необходимость при равноценной системной альтернативе обосновать нельзя — §4.3; P-001 FLOG-034, must).
7. **Честная коммуникация:** класс «удобство»; запрещённые формулировки §3.7; письменное принятие остаточных рисков заказчиком.
8. **Запасной вариант:** при отрицательном заключении юриста или провале PAD-теста — текущее ТЗ (вариант 0) и, при желании, вариант 4 (ИК-камеры + отдельные учётные записи Windows).
