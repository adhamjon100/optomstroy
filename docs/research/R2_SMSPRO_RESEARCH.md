## 3. HTTP-XML API: отправка SMS (`/api/message`)

### 3.1. Транспорт
- URL: `http://smspro.nikita.kg/api/message` либо `https://smspro.nikita.kg/api/message` «для работы по защищенному SSL-протоколу». [ПОДТВЕРЖДЕНО: S8 §1]
- Метод: `POST`, тело запроса — XML-документ. [ПОДТВЕРЖДЕНО: S8 §1]
- Кодировка XML: `UTF-8` (декларация `<?xml version="1.0" encoding="UTF-8"?>`; для поля `text` явно: «Формат UTF-8»). [ПОДТВЕРЖДЕНО: S8 §1]
- Content-Type запроса: в PDF не указан; OpenAPI S12 описывает `requestBody` как `application/xml`; официальный Python-пример (S14) шлёт заголовок `Content-Type: application/xml`; PHP-пример (`sendSms.php`, `getDeliveryReport.php`) не задаёт заголовок явно — используется `CURLOPT_POST` + строковый `CURLOPT_POSTFIELDS` без `CURLOPT_HTTPHEADER`, поэтому curl по умолчанию отправляет `Content-Type: application/x-www-form-urlencoded`; сервер принимает и такой запрос (живая проверка 2026-10-18: с `application/x-www-form-urlencoded` и вовсе без заголовка Content-Type тело разобрано как XML, ответ `status=2` «неверная авторизация», а не `status=1` «ошибка формата»). Для нашего адаптера — всегда `Content-Type: application/xml`. Живой ответ при `Content-Type: application/xml` — корректный XML. [ПОДТВЕРЖДЕНО: S12, S14 (unzip PHPexample.zip), S15]
- Content-Type ответа (фактический): `text/xml;charset=UTF-8`, HTTP 200 даже при ошибке авторизации (ошибки передаются полем `<status>`, не HTTP-кодом). [ПОДТВЕРЖДЕНО: S15]
- Таймаут клиента в примере PHP: `CURLOPT_TIMEOUT = 120` c. [ПОДТВЕРЖДЕНО: S14] — ориентир, не требование.

### 3.2. Структура запроса (теги — точно как в документации)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<message>
  <login>login</login>
  <pwd>passwd</pwd>
  <id>A88726</id>
  <sender>My-company</sender>
  <text>Any SMS message text</text>
  <time>20100921235957</time>
  <phones>
    <phone>996550123456</phone>
    <phone>996550123457</phone>
  </phones>
  <test>1</test>
</message>
```
[ПОДТВЕРЖДЕНО: S8 §1, S9 §1, S12 example]

| Тег | Обязательность (по XSD `?xsd=2`) | Описание по документации | Статус |
|---|---|---|---|
| `login` | обязателен (`minOccurs` по умолчанию 1) | «Login партнера, выдаваемый ему при создании аккаунта» | [ПОДТВЕРЖДЕНО: S8, S13] |
| `pwd` | обязателен | «Пароль партнера» — тот же, что для входа в ЛК (EN: «The same as for Personal Area») | [ПОДТВЕРЖДЕНО: S8, S9] |
| `id` | обязателен | Id сообщения: любой набор **латинских букв и цифр длиной до 12 знаков**; должен быть уникальным для каждой отправки; при совпадении id вторая отправка блокируется; используется для защиты от переотправок и для запроса отчётов о доставке | [ПОДТВЕРЖДЕНО: S8 §1] |
| `sender` | обязателен | Имя отправителя: «либо из 11 латинских букв, цифр и знаков точка и тире, либо из 14 цифр»; должно быть валидировано администратором (иначе `status=5`) | [ПОДТВЕРЖДЕНО: S8 §1] |
| `text` | обязателен | Текст; максимум **800 символов**; автоматически делится на части, каждая тарифицируется; 160 символов латиницей / 70 кириллицей на 1 SMS; при разбиении 153 / 67 на часть; UTF-8 | [ПОДТВЕРЖДЕНО: S8 §1] |
| `time` | необязателен (`minOccurs=0`) | Отложенная отправка, формат `YYYYMMDDhhmmss`, время бишкекское (GMT+6); отсутствует/пусто — отправка немедленно | [ПОДТВЕРЖДЕНО: S8 §1, S13] |
| `phones` / `phone` | обязателен; `phone` 1..unbounded | Формат `996555123456` либо `+996555123456`; **максимум 50 номеров в одном пакете** | [ПОДТВЕРЖДЕНО: S8 §1, S13] |
| `test` | необязателен (`minOccurs=0`) | Если `=1` — запрос обрабатывается, но SMS не отправляется и не тарифицируется (ответ `status=11`) | [ПОДТВЕРЖДЕНО: S8 §1] |

Примечание: в XSD `test` объявлен как `xs:string`, в OpenAPI — `integer`; в запросе передавать строку `1`. [ПОДТВЕРЖДЕНО: S12, S13]

### 3.3. Структура ответа

```xml
<?xml version="1.0" encoding="UTF-8"?>
<response>
  <id>A88726</id>
  <status>0</status>
  <phones>2</phones>
  <smscnt>2</smscnt>
  <message></message>
</response>
```
[ПОДТВЕРЖДЕНО: S8 §1]

**Фактический ответ сервера** (живой запрос с фиктивными данными, 2026-10-18) содержит namespace, которого нет в примере документации:
```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?><response xmlns="http://Giper.mobi/schema/Message"><id>T1</id><status>2</status><phones>1</phones><smscnt>1</smscnt></response>
```
Тег `<message>` при отсутствии текста ошибки может отсутствовать вовсе. **Парсер обязан быть namespace-agnostic и терпимым к отсутствию необязательных тегов.** [ПОДТВЕРЖДЕНО: S15]

| Тег ответа | Описание | Статус |
|---|---|---|
| `id` | Id запроса, переданный партнёром | [ПОДТВЕРЖДЕНО: S8] |
| `status` | Статус отправки; `0` — все сообщения приняты, иначе ошибка (таблица ниже) | [ПОДТВЕРЖДЕНО: S8] |
| `phones` | Число распознанных номеров | [ПОДТВЕРЖДЕНО: S8] |
| `smscnt` | Число частей SMS, на которые разделилось сообщение | [ПОДТВЕРЖДЕНО: S8] |
| `message` | Необязательное текстовое описание ошибки (например, некорректный номер из списка) | [ПОДТВЕРЖДЕНО: S8] |

Тарифицируемое количество SMS при успехе = `phones × smscnt`. [ПОДТВЕРЖДЕНО: S8 §1]

### 3.4. Коды `status` ответа `/api/message` (полный список)

| Код | Значение по документации (сокращённо, смысл сохранён) | Статус |
|---|---|---|
| 0 | Сообщения успешно приняты к отправке | [ПОДТВЕРЖДЕНО: S8] |
| 1 | Ошибка в формате запроса | [ПОДТВЕРЖДЕНО: S8] |
| 2 | Неверная авторизация | [ПОДТВЕРЖДЕНО: S8, S15] |
| 3 | Недопустимый IP-адрес отправителя | [ПОДТВЕРЖДЕНО: S8] |
| 4 | Недостаточно средств на счету клиента (не хватает на все части SMS для всех номеров запроса) | [ПОДТВЕРЖДЕНО: S8] |
| 5 | Недопустимое имя отправителя (значение `sender` не валидировано администратором smspro.nikita.kg) | [ПОДТВЕРЖДЕНО: S8] |
| 6 | Сообщение заблокировано по стоп-словам (например, нецензурная лексика) | [ПОДТВЕРЖДЕНО: S8] |
| 7 | Некорректное написание одного или нескольких номеров телефонов получателей | [ПОДТВЕРЖДЕНО: S8] |
| 8 | Неверный формат времени отправки | [ПОДТВЕРЖДЕНО: S8] |
| 9 | Превышение времени обработки запроса (много одновременных запросов). **Повторить запрос с тем же `id` через 5–10 с** | [ПОДТВЕРЖДЕНО: S8] |
| 10 | Отправка заблокирована из-за последовательного повторения `id` (ошибочная переотправка) | [ПОДТВЕРЖДЕНО: S8] |
| 11 | Сообщение обработано, но не принято к отправке и не протарифицировано, т.к. в запросе `<test>1</test>` | [ПОДТВЕРЖДЕНО: S8] |

HTTP-коды 4xx/5xx для прикладных ошибок не используются (OpenAPI описывает только `200`). При `GET` на `/api/info` сервер вернул HTTP 500 — метод должен быть строго `POST`. Следствие: HTTP 5xx возникает и при ошибке на стороне клиента (неверный метод/тело), поэтому 5xx нельзя трактовать как чисто серверный сбой и слепо повторять — см. §11.4. [ПОДТВЕРЖДЕНО: S12, S15]

## 4. Отчёты о доставке

### 4.1. Опрос шлюза: `POST /api/dr`

Запрос:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<dr>
  <login>login</login>
  <pwd>passwd</pwd>
  <id>A88726</id>
  <phone>996550123456</phone>
</dr>
```
| Тег | Описание | Статус |
|---|---|---|
| `login`, `pwd` | как в §3 | [ПОДТВЕРЖДЕНО: S8 §2.2] |
| `id` | id сообщения (транзакции), по которому производилась отправка | [ПОДТВЕРЖДЕНО: S8 §2.2] |
| `phone` | необязателен (по PDF); если не указан — отчёт по всем номерам транзакции. Расхождение: в XSD `?xsd=3` элемент `drType/phone` объявлен без `minOccurs="0"`, т.е. для SOAP обязателен (см. §14 п.4) | [ПОДТВЕРЖДЕНО: S8 §2.2; XSD — S13] |

Ответ:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<response>
  <status>0</status>
  <phone>
    <number>996550123456</number>
    <report>1</report>
    <sendTime>20100921235958</sendTime>
    <rcvTime></rcvTime>
  </phone>
  <phone>
    <number>996550123457</number>
    <report>3</report>
    <sendTime>20100921235958</sendTime>
    <rcvTime>20100921235959</rcvTime>
  </phone>
</response>
```
Фактический ответ (фиктивные данные): `<response xmlns="http://Giper.mobi/schema/DeliveryReport"><status>2</status></response>` — элементы `phone` отсутствуют при ошибке. [ПОДТВЕРЖДЕНО: S15]

| Тег | Описание | Статус |
|---|---|---|
| `status` | 0 — запрос корректен, иначе ошибка (таблица ниже) | [ПОДТВЕРЖДЕНО: S8] |
| `phone/number` | номер | [ПОДТВЕРЖДЕНО: S8, S12] |
| `phone/report` | код отчёта о доставке (таблица §4.3) | [ПОДТВЕРЖДЕНО: S8] |
| `phone/sendTime` | время фактической отправки оператору `YYYYMMDDhhmmss`; пустая строка, если ещё не отправлялось | [ПОДТВЕРЖДЕНО: S8] |
| `phone/rcvTime` | время получения отчёта о доставке `YYYYMMDDhhmmss`; пустая строка, если отчёт не получен | [ПОДТВЕРЖДЕНО: S8] |

Коды `status` ответа `/api/dr`:

| Код | Значение | Статус |
|---|---|---|
| 0 | Запрос корректен | [ПОДТВЕРЖДЕНО: S8] |
| 1 | Ошибка в формате запроса | [ПОДТВЕРЖДЕНО: S8] |
| 2 | Неверная авторизация | [ПОДТВЕРЖДЕНО: S8, S15] |
| 3 | Недопустимый IP-адрес отправителя | [ПОДТВЕРЖДЕНО: S8] |
| 4 | Отчёт для указанных номера телефона и ID не найден | [ПОДТВЕРЖДЕНО: S8] |
| 5 | Переполнение очереди запросами с одним и тем же ID; дождаться ответа на предыдущий запрос с этим ID | [ПОДТВЕРЖДЕНО: S8] |

Расхождение: XSD `?xsd=3` описывает `responseType` как плоскую последовательность `status, report, sendTime, rcvTime` (без `phone/number`), тогда как PDF и живой API возвращают вложенные `<phone>`. XSD относится к SOAP-обёртке; для HTTP-XML ориентироваться на PDF/живой ответ. [ПОДТВЕРЖДЕНО: S13 vs S8/S15]

### 4.2. Push-отчёты на сервер партнёра
- Включается в ЛК: «МОЙ ПРОФИЛЬ → ПАРАМЕТРЫ API», указать URL и отметить флаг «Включить отправку отчетов». URL может быть HTTP или HTTPS, с портом (примеры в документе: `http://mysite.org:8080/report`, `https://securedsite.org/report`). [ПОДТВЕРЖДЕНО: S8 §2.1]
- Один XML-отчёт может содержать несколько `<dr>` (транзакций) и несколько `<phone>` внутри каждой. [ПОДТВЕРЖДЕНО: S8 §2.1]
- Партнёр должен ответить `HTTP 200 OK`; иначе шлюз делает **3 повторные отправки с периодичностью 10 минут**. [ПОДТВЕРЖДЕНО: S8 §2.1]
- Рекомендация вендора по защите: проверять `id` транзакции, использовать HTTPS и Firewall с ограничением по IP-адресу шлюза. **IP-адреса шлюза в документах не опубликованы** — запросить у поддержки. [ПОДТВЕРЖДЕНО: S8 §2.1; IP — НЕ ПОДТВЕРЖДЕНО]
- Аутентификации push-запроса (подпись, секрет) в документации **нет**. [ПОДТВЕРЖДЕНО: S8 — отсутствие]

Формат push-отчёта:
```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<report xmlns="http://Giper.mobi/schema/DeliveryReport">
  <dr>
    <id>A881726</id>
    <phone>
      <number>996550123456</number>
      <report>1</report>
      <sendTime>20110909032815</sendTime>
      <rcvTime>20110909032820</rcvTime>
    </phone>
  </dr>
  <dr>
    <id>A887236</id>
    <phone>
      <number>996550123458</number>
      <report>1</report>
      <sendTime>20110909032817</sendTime>
      <rcvTime>20110909032822</rcvTime>
    </phone>
  </dr>
</report>
```
[ПОДТВЕРЖДЕНО: S8 §2.1]

### 4.3. Коды `report` (отчёт о доставке)

| Код | Значение | Финальный? (вывод автора) | Статус |
|---|---|---|---|
| 0 | В очереди на отправку | нет | [ПОДТВЕРЖДЕНО: S8] |
| 1 | Отправлено (передано оператору) | нет | [ПОДТВЕРЖДЕНО: S8] |
| 2 | Отклонено (не передано; например, из-за несуществующего регионального кода) | да | [ПОДТВЕРЖДЕНО: S8] |
| 3 | Успешно доставлено | да | [ПОДТВЕРЖДЕНО: S8] |
| 4 | Не доставлено | да | [ПОДТВЕРЖДЕНО: S8] |
| 5 | Не отправлено из-за нехватки средств на счету партнёра | да (FAQ: «Не отправлено» — конечный статус) | [ПОДТВЕРЖДЕНО: S8, S4 п.14] |
| 6 | Неизвестный (новый) статус отправки | нет | [ПОДТВЕРЖДЕНО: S8] |
| 7 | Истёк период ожидания отчёта от SMSC; обработка прекращена | да | [ПОДТВЕРЖДЕНО: S8] |

Соответствие статусам в веб-интерфейсе (FAQ, 6 статусов): «Отправлено», «Доставлено», «Не отправлено» (не тарифицируется), «Не доставлено» (тарифицируется), «Отклонено», «Неизвестно». [ПОДТВЕРЖДЕНО: S4 п.13]

## 5. Прочие операции XML API

### 5.1. Баланс и состояние аккаунта: `POST /api/info`
Запрос (с namespace!):
```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<info xmlns="http://Giper.mobi/schema/Info">
  <login>login</login>
  <pwd>passwd</pwd>
</info>
```
Ответ:
```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<response xmlns="http://Giper.mobi/schema/Info">
  <status>0</status>
  <state>0</state>
  <account>20123.12</account>
  <smsprice>0.50</smsprice>
</response>
```
| Тег | Описание | Статус |
|---|---|---|
| `status` | 0 — корректно; 1 — ошибка формата; 2 — неверная авторизация; 3 — недопустимый IP | [ПОДТВЕРЖДЕНО: S8 §4] |
| `state` | 0 — аккаунт активен; 1 — не активен либо блокирован | [ПОДТВЕРЖДЕНО: S8 §4] |
| `account` | положительная сумма, доступная для расходования, без учёта возможного кредита, в валюте счёта | [ПОДТВЕРЖДЕНО: S8 §4] |
| `smsprice` | стоимость одного SMS в валюте счёта | [ПОДТВЕРЖДЕНО: S8 §4] |

Живой ответ при неверных данных: `<status>2</status><state>1</state><account>0</account><smsprice>0</smsprice>`. [ПОДТВЕРЖДЕНО: S15]

### 5.2. Информация об абоненте: `POST /api/def`
Запрос: `<def xmlns="http://Giper.mobi/schema/PhoneDEF"><login/><pwd/><phone/></def>`; ответ: `<response xmlns="http://Giper.mobi/schema/PhoneDEF"><status/><region/><operator/><timezone/></response>`. Только для GSM-сетей Кыргызстана; не тарифицируется. Коды `status`: 0 — ок; 1 — ошибка формата; 2 — неверная авторизация; 3 — некорректный номер; 4 — данные по номеру не найдены. `region`, `operator`, `timezone` присутствуют только при `status=0`; `timezone` = GMT-смещение, `-1` если неизвестно. [ПОДТВЕРЖДЕНО: S8 §3]
Применение в проекте: опциональная серверная проверка «номер принадлежит кыргызскому оператору» перед отправкой OTP (защита от трат на нереальные номера). [ПРЕДЛОЖЕНИЕ]

## 6. OTP API (JSON)

### 6.1. Настройка (в ЛК, вкладка «СЕРВИС OTP» / «OTP-сервис»)
Параметры задаются **в личном кабинете, а не в запросе**: API-ключ; имя отправителя (должно быть зарегистрировано и подтверждено модератором); длина кода; сложность кода (буквы большие/маленькие, цифры, спецсимволы); время жизни в минутах; текст сообщения с шаблонами `%code%`, `%time%`. [ПОДТВЕРЖДЕНО: S10 §1]

### 6.2. Отправка: `https://smspro.nikita.kg/api/otp/send`
- Метод `POST` или `GET`; формат данных JSON. [ПОДТВЕРЖДЕНО: S10 §2]
- Заголовок `X-API-KEY` — ключ авторизации из ЛК. [ПОДТВЕРЖДЕНО: S10 §2]
- Поля: `transaction_id` — уникальный ID транзакции, до 32 символов, буквы и цифры, повтор блокируется; `phone` — номер в международном формате. [ПОДТВЕРЖДЕНО: S10 §2]
- Ответ: `status` (0 — ок), `description`, `token` (уникальный токен транзакции). [ПОДТВЕРЖДЕНО: S10 §2]
- Пример из документа: запрос `{ "transaction_id": "12345678", "phone": "996770123456" }` → ответ `{"token":"<TOKEN_32HEX>","status":0,"description":"Code Sent"}` (в документе на месте `token` — пример из 32 hex-символов; здесь заменён плейсхолдером, см. §13.6). [ПОДТВЕРЖДЕНО: S10 §2]
- Живой ответ с заведомо неверным ключом: HTTP 200, `application/json`, `{"status":2,"description":"Authorisation Error"}` — текст `description` отличается от табличного «Bad Auth», поэтому **решения принимать только по числовому `status`**. [ПОДТВЕРЖДЕНО: S15]

### 6.3. Проверка: `https://smspro.nikita.kg/api/otp/verify`
- Поля: `token` (из ответа send), `code` (введённый пользователем). Ответ: `status` (0 — код корректен), `description`. Пример ответа: `{"status": "0", "description": "Code Valid"}` — обратите внимание, `status` здесь **строка** `"0"`, а в send — число `0`: парсер должен принимать оба варианта. [ПОДТВЕРЖДЕНО: S10 §3]

### 6.4. Коды `status` OTP API (полный список из документа)

| status | description | Комментарий документа | Статус |
|---|---|---|---|
| 0 | Code Sent / Code Valid | при отправке — SMS с кодом отправлено; при проверке — код валиден | [ПОДТВЕРЖДЕНО: S10 §4] |
| 1 | Bad Format | ошибка в формате запроса | [ПОДТВЕРЖДЕНО: S10] |
| 2 | Bad Auth | неверный ключ авторизации | [ПОДТВЕРЖДЕНО: S10; живой текст «Authorisation Error» — S15] |
| 3 | Bad IP-address | недопустимый IP-адрес | [ПОДТВЕРЖДЕНО: S10] |
| 4 | Not Enough Money | недостаточно средств | [ПОДТВЕРЖДЕНО: S10] |
| 5 | Sender or text are not set | не установлено имя отправителя или текст в настройках ЛК | [ПОДТВЕРЖДЕНО: S10] |
| 7 | Invalid Phone | некорректный номер | [ПОДТВЕРЖДЕНО: S10] |
| 10 | Invalid Transaction ID | блокировка из-за повторения ID | [ПОДТВЕРЖДЕНО: S10] |
| 12 | Invalid Token | неверный токен | [ПОДТВЕРЖДЕНО: S10] |
| 13 | Time-Expired | время жизни одноразового пароля истекло | [ПОДТВЕРЖДЕНО: S10] |
| 14 | Invalid Code | неверный одноразовый пароль | [ПОДТВЕРЖДЕНО: S10] |

Коды 6, 8, 9, 11 в документе OTP не описаны. [ПОДТВЕРЖДЕНО: S10 — отсутствие]

**Что OTP API НЕ описывает** (критично для безопасности): лимит попыток `verify` на один `token`, блокировку перебора, возможность повторной отправки того же кода, одноразовость токена после успешной проверки, rate-limit на `send` по номеру. [НЕ ПОДТВЕРЖДЕНО] → при использовании OTP API все эти ограничения всё равно реализуются на нашем сервере.

Отчёт о доставке OTP-SMS: через `https://smspro.nikita.kg/api/dr` по `transaction_id` либо push-URL. [ПОДТВЕРЖДЕНО: S10 §5]

## 7. SOAP (справочно)
- WSDL: `http://smspro.nikita.kg/api/soap?wsdl`; `soap:address location="https://smspro.nikita.kg:443/api/soap"`; service `soap`; targetNamespace `http://ws.api.giper.mobi/`; стиль document/literal. [ПОДТВЕРЖДЕНО: S13]
- Операции: `message` (вход `tns:message` → `ns2:message` из `http://Giper.mobi/schema/Message`; выход `messageResponse/return` типа `ns2:responseType`) и `dr` (вход `ns1:dr` из `http://Giper.mobi/schema/DeliveryReport`; выход `drResponse/return` типа `ns1:responseType`). Операций `info`/`def` в SOAP нет. [ПОДТВЕРЖДЕНО: S13]
- Схема `messageType` (`?xsd=2`): `login, pwd, id, sender, text, time(0..1), phones{phone 1..∞}, test(0..1)`, все `xs:string`. [ПОДТВЕРЖДЕНО: S13]

## 8. Подключение, имя отправителя, лимиты, тарифы

### 8.1. Регистрация и активация
- Регистрация на сайте: обязательные поля — логин, ФИО, название компании, e-mail; пароль генерируется и высылается на e-mail; телефон — для PIN-кода. [ПОДТВЕРЖДЕНО: S6]

[ТИПОВО: по S3/S6, требует проверки у менеджера SMSPro]

### 8.3. Имя отправителя (Sender ID / альфа-имя)
- Регистрируется в ЛК («Мой профиль»), подаётся заявка; согласование с операторами «от 7-10 рабочих дней» (FAQ) / «до 10 рабочих дней», заявка на `names@nikita.kg` (prices.html). [ПОДТВЕРЖДЕНО: S4 п.8, S5]
- Ограничения: только латинские буквы (большие и маленькие), цифры, пробел и некоторые знаки; «Максимальная длина — 11 букв или 14 цифр». В XML API: 11 латинских букв/цифр/точка/тире либо 14 цифр. [ПОДТВЕРЖДЕНО: S4 п.9, S8]

- Кириллические имена отправителя недопустимы. [ПОДТВЕРЖДЕНО: S4 п.9 — только латиница]

### 8.5. Ограничения текста
- Максимум 800 символов; 1 SMS = 160 латиница / 70 нелатиница; при склейке 153 / 67 на часть; «№» считается нелатинским символом; `{}[]^~\|€` занимают по 2 символа (GSM-7 escape). [ПОДТВЕРЖДЕНО: S4 п.5–6, S8]
- Стоп-слова: сообщение может быть заблокировано роботом (`status=6`); список не опубликован. [ПОДТВЕРЖДЕНО: S8; список — НЕ ПОДТВЕРЖДЕНО]
- Email2SMS: лимит 500 символов, кодировки koi8-r / Windows-1251 (к XML API не относится). [ПОДТВЕРЖДЕНО: S11]

### 8.6. Лимиты запросов

## 11. ПРЕДВАРИТЕЛЬНЫЙ дизайн серверного SMS-адаптера

> Пометка: раздел — проектное предложение для ТЗ, не реализованный код. Разработка на этапе 1 запрещена.

### 11.1. Место в архитектуре
Модуль `Authentication` модульного монолита backend. Flutter-клиент никогда не обращается к SMSPro; он вызывает наш API (`POST /auth/otp/request`, `POST /auth/otp/verify`). Весь обмен с SMSPro, хранение OTP, лимиты и журналирование — на сервере.

### 11.2. Два варианта и выбор

| Критерий | A. XML API `/message` + собственный OTP | B. OTP API SMSPro (`/otp/send`, `/otp/verify`) |
|---|---|---|
| Кто генерирует/хранит код | наш сервер (хэш в БД) | SMSPro; наш сервер видит только `token` |
| TTL, длина, алфавит кода | в нашем коде/конфиге | в ЛК SMSPro (не через API) |
| Лимит попыток, антиперебор, одноразовость | реализуем сами (обязательно) | не документировано → всё равно реализуем сами |
| Текст сообщения | наш (возможна локализация ru/ky) | шаблон в ЛК с `%code%`, `%time%` |
| Секрет | login/pwd (= пароль ЛК) | `X-API-KEY` (отдельный ключ — меньше радиус поражения) |
| Проверка кода без сети | да | нет (каждый verify — запрос к SMSPro) |
| Тестовый режим вендора | `<test>1</test>` → `status=11` | не описан |
| Переносимость на другого провайдера | высокая (нужен только «отправь текст») | низкая |

**Рекомендация:** вариант A как основной; интерфейс `SmsGateway` абстрагирует только «отправить текст на номер», `OtpService` — наша логика. Вариант B — отдельная реализация `OtpProvider` на случай, если заказчик захочет снять хранение кодов с нашего сервера. [ПРЕДЛОЖЕНИЕ]

### 11.3. Интерфейсы (псевдокод, язык backend ещё не выбран)

```text
interface SmsGateway {
  SendResult send(SendRequest req)          // одна транзакция = один <message>
  DeliveryReport[] getDeliveryReport(String transactionId, String? phone)
  AccountInfo getAccountInfo()              // /info: balance, smsprice, state
}

SendRequest  { transactionId: String(≤12, [A-Za-z0-9]); sender: String; text: String;
               phones: List<E164Phone>(1..50); scheduledAt?: DateTime(Asia/Bishkek); test: bool }
SendResult   { transactionId; outcome: ACCEPTED | ACCEPTED_TEST | RETRYABLE | PERMANENT | CONFIG_ERROR
               | INSUFFICIENT_FUNDS | INVALID_PHONE | DUPLICATE_ID;
               providerStatus: int; phonesRecognized: int; smsParts: int; providerMessage?: String }

implementations: SmsProXmlGateway (боевой), FakeSmsGateway (dev/test), (опц.) SmsProOtpProvider
```

### 11.4. Маппинг кодов `/message` → поведение

| `status` | Класс | Действие адаптера | Ответ пользователю |
|---|---|---|---|
| 0 | ACCEPTED | сохранить `smscnt`, `phones`; запланировать опрос `/dr` (или ждать push) | «Код отправлен» |
| 11 | ACCEPTED_TEST | как 0, только в режиме `SMSPRO_TEST_FLAG=true`; вне тест-режима — alert (значит, флаг утёк в прод) | как 0 |
| 9 | RETRYABLE | повтор **с тем же `id`** (прямое указание документации) с задержками 5, 10, 10 с (в пределах рекомендованных документацией 5–10 с), всего не более 3 повторов; затем PERMANENT | «Попробуйте позже» |
| 10 | DUPLICATE_ID | если это наш повтор после таймаута/ошибки сети — **не считать отправку принятой**; обязательно опросить `/dr` по этому `id`: `status=0` с `phone/report` → первая отправка состоялась, продолжать как ACCEPTED; `status=4` «отчёт не найден» → первая отправка не состоялась → новая отправка с **новым** `id`; иной `status` `/dr` → «Попробуйте позже» + alert. Если это не наш повтор — ошибка генерации `id`, alert. Семантика потребления `id` вендором не документирована (§9, §12 п.10) [НЕ ПОДТВЕРЖДЕНО] | как 0 либо «Попробуйте позже» |
| 2, 3, 5 | CONFIG_ERROR | не повторять; открыть circuit-breaker на N минут; alert on-call (неверный пароль / IP / имя отправителя) | «Сервис временно недоступен» |
| 4 | INSUFFICIENT_FUNDS | не повторять; alert «пополните баланс»; circuit-breaker | «Сервис временно недоступен» |
| 7 | INVALID_PHONE | не повторять; не должно случаться после нашей E.164-валидации → предупреждение | «Проверьте номер» |
| 1, 8 | PERMANENT (баг у нас) | не повторять; error-лог с запросом без секретов | «Сервис временно недоступен» |
| 6 | PERMANENT (стоп-слова) | не повторять; alert — текст OTP не должен триггерить фильтр | «Сервис временно недоступен» |
| сетевой таймаут / невалидный XML в ответе | RETRYABLE | повтор с тем же `id` (дедупликация по `id`: повтор даст `status=10`, если первая отправка была принята — тогда обработка по строке 10, т.е. через `/dr`); таймаут запроса 10–15 с; не более 3 повторов | «Попробуйте позже» |
| HTTP 5xx | RETRYABLE (ограниченно) | 5xx возникает и при ошибке клиента (воспроизведено: `GET /api/info` → HTTP 500, §3.4), поэтому повторять только 1–2 раза с тем же `id` и с алертом; если 5xx воспроизводится на всех попытках — классифицировать как PERMANENT (баг у нас), error-лог с запросом без секретов | «Попробуйте позже» / «Сервис временно недоступен» |

Маппинг `report` (`/dr` и push): 3 → DELIVERED; 2/4/5/7 → FAILED (финал); 0/1/6 → PENDING. Для пользователя статус доставки не показываем, используем для метрик и для решения «разрешить повторную отправку раньше» при FAILED. [ПРЕДЛОЖЕНИЕ]

### 11.5. Политика OTP (наша, вариант A) — для раздела 09_AUTH_SMS_BIOMETRICS
- Код: 6 цифр, CSPRNG; хранится только `hash(code + salt)` с привязкой к `phone`, `purpose` (login / register), `transactionId`, `expiresAt`, `attempts`.
- TTL: 5 минут (настраиваемо); повторная отправка не раньше 60 с; не более 3 отправок на номер за 15 мин и 10 за сутки; не более 5 попыток ввода на один код; после успеха код помечается использованным (защита от повторного использования); при истечении — новый код.
- Антиперебор номеров: ответ `/auth/otp/request` одинаков для существующего и несуществующего аккаунта по форме и времени ответа; лимиты по IP/устройству; `/api/def` как опциональный предфильтр «номер — кыргызский GSM».
- Текст SMS: короткий, в одну часть, без стоп-слов; пример: `Kod: 123456. Optomstroy` (латиница → 160 символов, дешевле и без риска «№»-кодировки). Финальный текст — согласовать с заказчиком. [ПРЕДЛОЖЕНИЕ]

### 11.6. Тестовый режим
- `SMS_PROVIDER=fake` — `FakeSmsGateway`: не ходит в сеть, пишет код в защищённый dev-лог/таблицу `dev_outbox`, доступную только в dev/test окружении; e2e-тесты читают код оттуда.
- `SMS_PROVIDER=smspro` + `SMSPRO_TEST_FLAG=true` — боевой адаптер с `<test>1</test>`: проверяет авторизацию, имя отправителя, разбор ответа, ожидает `status=11`; SMS не уходит и не тарифицируется. Для smoke-теста после настройки учётных данных.
- `SMS_PROVIDER=smspro` + `SMSPRO_TEST_FLAG=false` — продакшен. Стартовый баланс 15 сом позволяет ~7–9 реальных тестовых SMS.
- Интеграционные контрактные тесты: фикстуры XML-ответов из §3–5 (включая вариант с `xmlns` и без `<message>`), JSON OTP (`status` как число и как строка).

### 11.7. Логирование, метрики, алерты
- Лог отправки: `transactionId`, `phoneMasked` (`996550***456`), `purpose`, `providerStatus`, `smscnt`, `phonesRecognized`, `latencyMs`, `attempt`. Никогда: `text`, OTP-код, `pwd`, `X-API-KEY`, полный номер.
- Метрики: `sms_send_total{status}`, `sms_send_latency_ms`, `sms_retry_total`, `sms_delivery_report_total{report}`, `sms_balance_som` (опрос `/info` раз в 10–30 мин), `sms_circuit_open`.
- Алерты: баланс ниже порога (например, < 300 сом ≈ 150 OTP); доля `status≠0` > 5 % за 5 мин; любой `status∈{2,3,5}`; доля `report∈{2,4,7}` > 20 % за час; `state=1` в `/info`.
- Хранение: таблица `sms_outbox(id, transaction_id, phone_masked, purpose, provider, provider_status, sms_parts, report_code, send_time, rcv_time, created_at)`; `transaction_id` уникален (ограничение БД).

### 11.8. Генерация `transactionId`
12 символов `[A-Za-z0-9]` из CSPRNG (62^12 ≈ 3·10^21) или префикс+base36 от последовательности; уникальность — UNIQUE-индекс в БД до отправки; при OTP API — до 32 символов. [ПРЕДЛОЖЕНИЕ, ограничения — ПОДТВЕРЖДЕНО: S8, S10]

### 11.9. Push-DLR endpoint (опционально)
`POST /integrations/smspro/dlr`: принимает XML `report`, проверяет известность каждого `dr/id` (неизвестные — игнорировать и считать), IP-источник против `SMSPRO_DLR_ALLOWED_IPS`, обновляет `sms_outbox`, всегда отвечает `200 OK` быстро (обработка в фоне). Без этого — опрос `/dr` отложенной задачей через 30 с, 2 мин, 10 мин после отправки (соблюдая `status=5` «не слать параллельно с тем же ID»).

## 14. Расхождения и примечания к документации
1. Пример ответа `/message` в PDF без `xmlns`, фактический ответ — с `xmlns="http://Giper.mobi/schema/Message"`. [S8 vs S15]
2. OTP `verify` возвращает `status` строкой, `send` — числом. [S10]
3. Текст `description` в OTP API не совпадает с таблицей («Authorisation Error» vs «Bad Auth»). [S10 vs S15]
4. XSD `?xsd=3` для `dr`: в ответе (`responseType`) не содержит `phone/number`, PDF и API — содержат; в запросе (`drType`) тег `phone` обязателен (объявлен без `minOccurs="0"`), в PDF — необязателен. Для HTTP-XML ориентироваться на PDF, для SOAP — передавать `phone` всегда. [S13 vs S8/S15; XSD проверен curl 2026-10-18]
5. Нумерация разделов RU и EN PDF различается (в RU §2.1 — push, §2.2 — опрос; в EN наоборот). [S8 vs S9]
6. Срок регистрации имени: «от 7-10 рабочих дней» (FAQ) vs «до 10 рабочих дней» (prices). [S4 vs S5]
7. SwaggerHub-ссылка на techno.html ведёт на `apis-docs/ALEXEYSOLOMAKHIN/...`; путь `apis/nikita_online_sms_api/sms_api/...` — 404. [S2]
8. Документы PDF не датированы; примеры 2010–2011 гг.; примеры кода — 2024 г.
