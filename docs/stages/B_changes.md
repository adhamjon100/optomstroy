## 1. Ответы заказчика и решения

Ответ заказчика 2026-10-21 (по смыслу, ядро §24): «оранжевый; в регистрации — клиент, а продавца добавляет супер-админ; по 1С ничего нет и не знаю, [специалист 1С] сказал, что по запросу выдаст нам API; не совсем ясно по оплате QR — там в 1С есть API-интеграция».

| № | Вопрос | Ответ заказчика | Решение в ТЗ | Ядро | ADR |
|---|---|---|---|---|---|
| 1 | Q-006 — палитра и логотип | «оранжевый» | Основная палитра — **вариант B «Оранжевый»** (03 §5.3). Оранжевая заливка `#FF8700` — только с тёмным текстом `#1B1F2A`; белый текст на оранжевом запрещён. Текст, ссылки и цены — `#B04E00`; фокус и «информация» — синие `#1F5FA8`; оранжевый никогда не обозначает статус. Логотип — оранжевый (`Logo Orange.png`). Синяя схема A+ остаётся только как историческая альтернатива. Макеты — эталон компоновки, а не цвета | §24.1 | ADR-078 (заменяет ADR-016) |
| 2 | Q-001 — кто регистрируется | «в регистрации — клиент, а продавца добавляет супер-админ» | Регистрация по телефону — **для клиентов-покупателей**; режим клиента входит в **R1** (`CUSTOMER_SELF_SERVICE=true` по умолчанию; экраны SCR-03, SCR-04, SCR-06, SCR-50, роль `customer`). **Сотрудники сами не регистрируются**: учётную запись создаёт администратор приглашением по телефону и роли (SCR-45). Сотрудник входит по SMS-коду, сразу получает роль и задаёт PIN. Клиент при регистрации обязательно настраивает защиту входа: биометрию или PIN. Клиент оформляет заявку-заказ («Заказ клиента» в 1С, «Не согласован»), платит при получении или по QR; долг клиентом не оформляется; свои долг и история видны только после подтверждённой привязки к карточке 1С. «Супер-админ» понимается как роль `admin` (вопрос Q-303, не блокирует) | §24.2 | ADR-079 (заменяет ADR-007) |
| 3 | Q-010 / Q-011 — 1С | «по 1С ничего нет и не знаю; специалист 1С выдаст API по запросу» | Основной путь — **API на стороне 1С**: расширение «OptomstroyPOS» с HTTP-сервисом `/pos/v1/*`. Его делает специалист 1С заказчика по новому документу **`18_ONEC_API_REQUEST.md`** — «Техническое задание на API 1С для специалиста 1С». Стандартный OData «только чтение» — запасной путь, если API задерживается. Конфигурация 1С остаётся неизвестной до ответа специалиста | §24.3 | ADR-080 (заменяет ADR-048 и ADR-028 в части порядка внедрения) |
| 4 | Q-014 — QR-оплата | «не совсем ясно; в 1С есть API-интеграция» | Основной вариант R1 — **QR через 1С** (`QR_PROVIDER=onec`): backend запрашивает у 1С динамический QR, а факт оплаты сообщает 1С. Если интеграция 1С этого не умеет — статический QR магазина и **ручное подтверждение кассиром** (`QR_PROVIDER=none`). Прямая интеграция с API Бакай Банка и вебхук банка перенесены в Release 2 | §24.4 | ADR-081 (заменяет ADR-021 в части схемы QR) |

По вопросам без ответа работа идёт на рекомендуемых допущениях 14. Ворота G-B2 закрываются «на жёлтый» с записью последствий в отчёте этапа B (RM-B-013).

## 4. Что не изменилось

- Архитектура (Flutter → собственный backend → PostgreSQL → 1С), стек, роли сотрудников, правила денег, долгов, скидок, возвратов, офлайна, бэкапов — без изменений.
- Автомат статусов платежа не изменился. При QR через 1С «подтверждение банка» читается как «подтверждение оплаты от 1С». Расхождение суммы, неизвестный референс или поздняя оплата ведут на ручную проверку кассиром.
- Тёмная тема, push-уведомления, «сканирование лица» с SDK, прямой API банка — по-прежнему не в Release 1.
