Что проверено:
- инкремент: изменена 1 запись → изменилась 1 строка;
- повтор пакета идемпотентен;
- без ack то же сообщение выдаётся заново;

## 2. Как прогнать приёмку сразу после получения API

**Предусловия** (18 §7.1, этапы 2–3):

1. Специалист 1С опубликовал HTTP-сервис на тестовой копии.
2. Созданы пользователи `pos_hs` (HS) и `pos_integration` (OData, только чтение).
3. Выдан ключ `X-POS-Client-Key`.
4. Есть сеть (VPN/HTTPS) до тест-контура POS.
5. Секреты лежат только в файлах `*_FILE` (16 §4.3), в репозитории их нет.

```sh
# 0. Контракт и набор путей (без сети; RM-E-016 критерий 1 — в части контракта):
python -I -X utf8 scripts/check_onec_paths.py

# 1. Автоматическая часть контрольного примера против тестовой копии (из pos-api/):
APP_ENV=staging ONEC_MODE=extension \
ONEC_BASE_URL=https://<хост тест-копии> ONEC_HS_PATH=<публикация>/hs \
ONEC_HS_USER_FILE=/run/secrets/onec_hs_user ONEC_HS_PASSWORD_FILE=/run/secrets/onec_hs_password \
ONEC_HS_TOKEN_FILE=/run/secrets/onec_hs_token \
MIN_APP_VERSION=… DATABASE_URL_FILE=… \
npm run onec:acceptance -- --steps kp1,kp2,kp5,kp18,kp19 --allow-write \
  --phone +996XXXXXXXXX --image-ref <Ref_Key файла номенклатуры> \
  --out ../docs/stages/E_onec_kp_protocol.md
```

Параметры раннера:
- `--phone` — номер тестового клиента копии;
- `--image-ref` — ссылка присоединённого файла;
- `--allow-write` — нужен для `POST /changes/reregister` (КП-2): он меняет регистрации плана обмена тестовой копии.

```sh
# 2. Переключение тест-контура на расширение (без изменения кода, ONEC-029) — см. §4, затем полная загрузка
#    RM-E-011 настоящим pos-worker: POST /api/v1/sync/runs {entity, mode:"full"} по сущностям в порядке
#    05 SYNC-001 (admin + step-up, SCR-43) или дождаться SYNC_RECONCILE_CRON; итог — GET /api/v1/sync/status,
#    /sync/runs/{id}, /sync/runs/{id}/errors; сверка $count — задание sync.count_check (SYNC_COUNT_CHECK_CRON)
#    в фазе 0 или внутри прогона full/reconcile.

# 3. Регрессия клиента после правок контракта (до и после приёмки):
cd pos-api && npm run test:onec && npm run test:sync-apply && npm run test:sync
```

## 3. Комплект поставки 18 §7.6 — что проверяем при получении

1. Файл `.cfe` и его версия. Сверить с `extensionVersion` из `/health` (КП-1).

## 4. Переключение тест-контура на `ONEC_MODE=extension` (ONEC-029: без изменения приложения)

Код не меняется. Меняются только переменные окружения api и worker (имена — 16 §4.3, `.env.example`).

| Переменная | Значение на тест-контуре |
|---|---|
| `ONEC_MODE` | `extension` (вместо `fixtures`) |
| `ONEC_BASE_URL` | `https://<хост тестовой копии>` (http допускается только при `APP_ENV=dev`) |
| `ONEC_HS_PATH` | `<публикация>/hs` |
| `ONEC_HS_USER_FILE`, `ONEC_HS_PASSWORD_FILE`, `ONEC_HS_TOKEN_FILE` | Секреты `pos_hs` и `X-POS-Client-Key` |
| `ONEC_USER_FILE`, `ONEC_PASSWORD_FILE` | `pos_integration` (OData, только чтение) |
| `ONEC_CA_CERT_FILE` | Если сертификат 1С выдан внутренним УЦ |
| `QR_PROVIDER` | `onec` — только если методы QR приняты (КП-11…КП-13). Иначе `none` (RM-E-016 критерий 3) |
| `ONEC_ODATA_WRITE_ENABLED` | Остаётся `false` |

`ONEC_USER_FILE` и `ONEC_PASSWORD_FILE` нужны:
- для первой загрузки по 18 §4.3 способ 1;
- для срезов цен и остатков (EQ-ONEC-02).

Без них полная загрузка и срезы недоступны: обработчики пишут предупреждение, прогон проходит без загрузки.

Что меняется в поведении:

1. **Нет конфигурации `ONEC_HS_*`.** api и worker не стартуют: `ConfigError`, код 1, в сообщении только имена
   переменных. Проверено тестом фабрики.
2. **Расписание pos-worker.**
   - В режиме `extension` работает одно задание `onec.changes` по плану обмена (D-29, ядро §22.8).
   - Задания по отдельным сущностям каталога выполняются только для `full`/`reconcile` (ночная сверка
     `SYNC_RECONCILE_CRON`) и для срезов `stock`/`prices`.
   - Ручной `incremental` сущности плана обмена в SCR-43 выполняет тот же цикл `/changes`.
3. **Фото.** Скачиваются через `GET /pos/v1/images/{ref}` раз в сутки (`SYNC_IMAGES_CRON`). Регистрация файлов — из
   элементов `Catalog_НоменклатураПрисоединенныеФайлы` плана обмена (`ProductImageFilesHandler`, подключён в worker
   при интеграции).
4. **Ежесуточная сверка `sync.count_check` пропускается** (только фаза 0). Полнота в режиме расширения
   обеспечивается подтверждением пакетов и еженедельной сверкой `full`/`reconcile`.
5. **Критерий RM-E-016 п. 4** — «с `ONEC_MODE=extension` полная загрузка RM-E-011 проходит без изменения кода».
   - Конвейер и источник OData — тот же код, что прошёл загрузку на фикстурах: `CatalogFullLoadService`,
     `ODataCatalogSource` по allow-list.
   - Источник OData проверен на синтетических строках OData (`test/onec/onec-odata.spec.ts`).
   - **Подтвердить на реальной копии пока нельзя.**

## 5. Последствия задержки API (что нельзя закрыть без 1С)

**Чтение (этап E)**
- Реального инкремента по плану обмена, фото через HS и сверки количеств на данных заказчика нет.
- Не проверены фактические имена объектов 1С. Они остаются `[ТИПОВО]` (Q-010) — это риск этапа E «маппинг не
  работает».
- Каталог, поиск и офлайн-API проверены только на синтетике (50 000 SKU — бенчмарк поиска) и фикстурах.

**Запись (этапы F/G)**
- Заказы, оплаты, QR, клиенты и возвраты будут реализованы и протестированы на `FakeOnecGateway`.
- Не будут проверены:
  - идемпотентность по `externalId` на стороне 1С (КП-6, КП-8, КП-12, КП-14);
  - поведение при блокировках (КП-20);
  - автоскидки (КП-9).
- Пилот (этап I) невозможен без принятого API или решения о фазе 0.

**Нагрузка**
- Замер 18 §7.4 не выполнен. Интервалы D-29 — значения по умолчанию.

**Зависимые вопросы к специалисту**
- Передаются через журнал RM-B-014, отдельно от этого протокола:
  - EQ-ONEC-02 — метод среза цен и остатков в HS либо подтверждение OData;
  - EQ-CAT-10 — остатки по списку вариантов для `live=true`;
  - EQ-ONEC-11 — справочник валют в allow-list;
  - EQ-ONEC-10 — контрольная цифра EAN в фикстуре;

## 6. Решение по 13 §3.12 и воротам G-E

1. **G-E — «на жёлтый»** (13 §3.5, ворота G-E: «RM-E-016 — отчёт „API 1С не получен“ с последствиями и решением по
   §3.12»).
   - Этап F начинается на `FakeOnecGateway` и фикстурах.
   - Отчёты этапов F/G по интеграции с 1С помечаются «на фикстурах, не реальная интеграция».
2. **Запасная фаза 0 сейчас не включается.**
   - По §3.12 «Ручное оформление фазы 0 без канала записи» (05 SYNC-066, SYNC-067, SYNC-074…SYNC-076) по умолчанию
     не реализуется. Основание: специалист 1С есть и делает API, ядро §24.3.
   - `ONEC_ODATA_WRITE_ENABLED=false` — временная запись через OData не используется.
   - OData только на чтение остаётся как способ первой загрузки и срезов. Он уже реализован, и включение
     конфигурацией не меняет объём R1.
3. **Когда решение пересматривается.** Если к началу интеграционных тестов этапа F на тестовой копии API не получено
   или не принято (этапы 3–4 из 18 §7.1), владелец магазина решает одно из двух:
   - ждать API — пилот (этап I) сдвигается;
   - принять фазу 0 по §3.12 (ADR в RM-B-002, 5 у.е.: парковка outbox `NO_WRITE_CHANNEL`, ручное оформление
     в 1С).

   Решение оформляется ADR и процедурой 13 §5.3. До него в коде ничего не меняется.
4. **После получения API:**
   - прогнать §2 этого документа;
   - заполнить протокол КП-1…КП-20 (`docs/stages/E_onec_kp_protocol.md`, из раннера плюс ручные шаги);
   - переключить тест-контур по §4;
   - повторить RM-E-011 на копии;
   - при непрохождении — передать замечания специалисту (журнал RM-B-014) и обновить этот документ.
