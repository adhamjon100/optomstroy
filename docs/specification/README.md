## Правила внесения изменений

1. Канонические имена, решения и границы задаёт ядро R0; документ ТЗ ему не противоречит. Несогласие автор записывает в раздел «Замечания к ядру» своего документа и продолжает следовать ядру.
2. У каждого документа один владелец; правка чужого документа — только через владельца. Экраны правятся **только** в `02_SCREEN_SPECIFICATION.md`, матрица трассировки — **только** в `17_TRACEABILITY_MATRIX.md`; файлы `source/02_parts_drafts/` и `source/17_parts_drafts/` не изменяются. Ссылки на части даются на разделы 02 и 17, а не на черновики.
3. Новые идентификаторы — по ядру §10 (префиксы документов-владельцев), новые вопросы — в диапазонах ядра §19.5 и §20.2 п.18 без перенумерации существующих. Каждое требование из промта ссылается на `SRC-…`.
4. Каждое исправление фиксируется в журнале проверки или сверки документа; версия документа повышается.
5. До утверждения ТЗ изменения вносятся по замечаниям заказчика и проверяющих. После фразы «ТЗ УТВЕРЖДЕНО. НАЧИНАЙ РАЗРАБОТКУ» изменение архитектуры или важных бизнес-правил, существенно влияющее на ТЗ, — только после объяснения причины и согласования заказчика, с записью ADR в 15 (SRC-E-248); контракты меняются по процедуре 13 §5.3 (expand-only). Подробно — `00_EXECUTIVE_SUMMARY.md` §14.
6. Ответ заказчика на вопрос Q-xxx переводит требования из `[ТРЕБУЕТ РЕШЕНИЯ ЗАКАЗЧИКА: Q-xxx]` в `[РЕШЕНИЕ]` без перенумерации; ответ, отличный от допущения, — изменение ТЗ (15 §5.1).
7. Секреты (пароли, ключи, токены) в документы, чат и репозиторий не вносятся.
