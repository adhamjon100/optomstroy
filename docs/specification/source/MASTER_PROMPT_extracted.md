4. Синхронизация с 1С
Моя первоначальная идея — синхронизация каждые 30 минут. Проверь, достаточно ли этого для каждой категории данных.
Предложи гибридную стратегию:
первоначальная полная загрузка и сверка;
инкрементальный обмен по времени изменения или журналу изменений, если это поддерживается;
периодическая фоновая синхронизация, ориентировочно каждые 30 минут;
более частое обновление критичных данных, если бизнес этого требует и 1С позволяет;
ручная синхронизация с отображением её статуса;
повторные попытки при временных ошибках;
идемпотентность, контроль версий и обнаружение конфликтов;
мониторинг последней успешной синхронизации и количества ошибок.
Важно: периодические задачи на мобильном устройстве не гарантируют выполнение точно по расписанию. Планировщик должен находиться на сервере или в другом постоянно работающем компоненте.

7. Авторизация — эмоциональный персонаж
Создай белый, минималистичный экран авторизации с дружелюбным анимированным персонажем.
Персонаж должен реагировать на состояние процесса:
ожидание — открытые глаза и спокойное выражение;
ввод данных — взгляд на поле ввода;
проверка — лёгкая анимация ожидания;
успех — улыбка, после чего появляется зелёная галочка;
ошибка — мягкая анимация отрицания и понятное сообщение;
повторная попытка — персонаж возвращается в нейтральное состояние.
Продумай плавные переходы между состояниями. Не используй резкие мигания, раздражающие эффекты и чрезмерную анимацию.
Вход по лицу
Разделяй системную биометрическую аутентификацию и распознавание лица по фотографии.
Предпочтительный вариант:
Пользователь сначала связывает свой подтверждённый номер с аккаунтом.
Приложение предлагает включить биометрический вход через поддерживаемые средства операционной системы.
При следующем входе используй системную биометрию и безопасно хранимый токен сессии.
При успешной проверке открывай аккаунт соответствующего пользователя.
При отказе или ошибке предлагай альтернативный вход по номеру телефона.
Не утверждай, что Flutter самостоятельно предоставляет универсальный Face ID для всех Android-устройств. Исследуй возможности local_auth и системные ограничения.
Если для магазина требуется именно распознавание лица с поворотами головы, оцени необходимость отдельного решения для распознавания и проверки живого присутствия. Не считай серию фотографий полноценной защитой от подделки.
Не храни необработанные биометрические данные без обоснованной необходимости, явного согласия, защиты и установленного срока хранения.
8. Вход по номеру телефона
Сделай удобное поле номера телефона:
форматирование номера;
корректный международный код;
понятное отображение кода Кыргызстана;
валидация;
поддержка изменения номера;
удобное редактирование;
сообщения об ошибках.
Поток авторизации:
Пользователь вводит номер.
Backend проверяет, существует ли связанная учётная запись.
Если аккаунт существует, отправляется OTP через SMSPro, и открывается экран подтверждения.
Если аккаунта нет, открывается регистрация.
После успешного подтверждения кодом существующий пользователь автоматически попадает в свой аккаунт.
Проверку существования аккаунта выполняй на сервере. Предусмотри защиту от перебора номеров и злоупотребления SMS. Не раскрывай посторонним клиентскую информацию.

Вся отправка SMS должна происходить на серверной стороне. Не помещай логин, пароль, API-ключ или другие секреты SMSPro во Flutter-код, приложение или репозиторий.
Подготовь конфигурацию через переменные окружения и файл-пример без секретов. Добавь тестовый режим, журналирование без OTP-кодов, ограничения частоты запросов, время действия кода, лимит попыток и защиту от повторного использования OTP.
Если для реального подключения нужны мои учётные данные, сначала реализуй адаптер по официальной документации, затем попроси только необходимые параметры через безопасный способ настройки. Не запрашивай пароль от личного кабинета в открытом чате.
9. Регистрация пользователя
Создай современный экран регистрации со следующими полями:
ФИО — обязательно.
Номер телефона — обязательно.
Сканирование лица или настройка биометрии — обязательный этап по утверждённому безопасному сценарию.
Год рождения — обязательно.
Сфера деятельности — необязательно.
В оригинальном перечне номера полей пропущен пункт 3. Не создавай лишнее обязательное поле только ради исправления нумерации.
Требования к форме:
форматирование номера;
проверка заполнения обязательных полей;
понятные сообщения об ошибках;
корректная клавиатура для каждого типа данных;
индикатор прогресса;
анимация подтверждения;
защита от повторной регистрации;
сохранение введённых данных при временной ошибке сети.
Регистрация и клиентская база 1С
Сначала ищи существующую клиентскую запись по подтверждённому номеру телефона и другим разрешённым признакам.
Если пользователь уже существует в 1С, не создавай дубликат только потому, что старой записи не хватает одного из новых полей регистрации.
Разделяй профиль пользователя приложения и исходную карточку клиента 1С. Поля, которых нет в 1С, должны храниться отдельно либо передаваться в 1С только по согласованным правилам.
Если найден существующий клиент:
предложи безопасную привязку к существующей записи;
сохрани историю покупок, долги и связанные документы;
не создавай новую клиентскую карточку автоматически;
не раскрывай финансовую информацию до подтверждения владения аккаунтом.
Если совпадение неоднозначное, передай случай на безопасное разрешение конфликта.
После заполнения формы отправь OTP. При правильном вводе кода автоматически заверши регистрацию и открой приложение, не требуя дополнительного нажатия кнопки входа.
Не делай регистрацию завершённой до успешной серверной проверки номера.

Поиск должен работать по названию, артикулу, штрихкоду и другим доступным полям. Предусмотри задержку перед поисковым запросом, обработку пустого результата и возможность сканирования штрихкода, если оборудование поддерживается.
Категории
Под логотипом размести вертикальное меню категорий в виде компактных карточек с изображениями и названиями.
Под строкой поиска и профилем размести горизонтальную полосу категорий или подборок товаров, если это полезно для рабочего сценария.
Подкатегории показывай только тогда, когда они действительно существуют.
Изучи приложенные ручные чертежи и используй их как исходный материал, а не игнорируй ради произвольной компоновки.
Каталог
Добавь переключение представления:
сетка;

компактный список;
сортировка;

диапазон цены, если доступен;

категория;

Карточка товара должна содержать:
фотографию;
название;
артикул;

доступный остаток;
статус наличия;

Если пользователь повторно нажимает на контрол добавления, количество должно увеличиваться без открытия лишних окон. Отдельно предусмотрите быстрый ввод количества.
Учитывай единицы измерения и упаковки: штуки, коробки, метры и другие единицы, если они реально используются в 1С. Не допускай некорректных количеств.
Подробная карточка товара
При открытии товара покажи удобную панель или отдельный экран.
Слева или сверху — крупная фотография товара. Рядом или под ней — миниатюры других изображений и вариантов.
Если товар имеет цвета, размеры или модели:
покажи доступные варианты;
при выборе варианта обновляй фотографии и характеристики;
показывай артикул конкретного варианта;
показывай остаток выбранного варианта по каждому складу.
В основной части размести:
название;
артикул;
описание;
характеристики;
варианты;
цену;
доступность;
выбор количества;
добавление в корзину.
Если у товара нет фотографии, покажи качественную заглушку. Не подставляй изображение другого товара.
Фотографии должны быть связаны с реальными товарами из 1С. Предусмотри кэширование и загрузку по требованию.
11. Корзина и оформление заказа
Корзина должна быть доступна из нижней части интерфейса на мобильных устройствах и из постоянно доступной панели на больших экранах.
Показывай счётчик товаров и количество единиц.
Полноценная корзина должна поддерживать:
изменение количества;
удаление позиции;
выбор варианта;
отображение цены и суммы позиции;
промежуточный итог;
скидку, если она разрешена;
итоговую сумму;
сохранение черновика;
восстановление после перезапуска;
очистку с подтверждением;
понятные предупреждения об изменившихся ценах и остатках.
Сохраняй выбранные товары, варианты и количества между экранами. Не теряй корзину при переходе в карточку товара или обратно в каталог.
Перед подтверждением заказа сервер должен повторно проверить актуальные цены, остатки, права пользователя и правила скидок.
Не списывай складской остаток окончательно при простом добавлении товара в корзину. Резервирование и списание выполняй по согласованному бизнес-процессу.
Различай заказ и продажу
Не предполагай, что добавление товаров в корзину автоматически означает завершённую продажу.
Реализуй отдельные сценарии для оформления заказа, выставления счёта и кассовой продажи, исходя из реальных процессов магазина и возможностей 1С.
Не придумывай способы оплаты и документы, которые магазин не использует. Сначала определи доступные операции, затем реализуй их с корректной синхронизацией.
12. Экран кассира
Создай отдельный интерфейс кассира с быстрым доступом к повседневным операциям.
На главном экране размести:
поиск клиентов;

недавние операции;

скидки и условия продаж;

быстрый доступ к каталогу и кассе;
уведомления об ошибках синхронизации.
Клиенты
Карточка клиента должна показывать только данные, разрешённые его роли:
имя и идентификатор;
подтверждённый номер;
историю покупок;
разрешённые сведения о взаиморасчётах;
доступные скидки;
избранный статус;
связанные заказы и транзакции.
Добавь возможность добавлять клиента в избранное, удалять из избранного и быстро находить его на главном экране кассира.
Избранное должно сохраняться на сервере или в другом подходящем постоянном хранилище, а не исчезать после закрытия приложения.
Долги и скидки
Отображай задолженность на основании данных 1С или утверждённого источника финансовой информации.
Не вычисляй долг только по истории покупок, если отсутствуют сведения об оплатах, возвратах, корректировках и взаимозачётах.
Разделяй:
сумму долга;
дату и статус документа;
платежи;
возвраты;
скидки;
доступный лимит, если он существует;
дату последней синхронизации.
Скидки должны рассчитываться по утверждённым правилам. Запрещай клиенту самостоятельно менять итоговую цену через запросы мобильного приложения.
Транзакции
Добавь список транзакций с фильтрами по периоду, клиенту, статусу и типу операции.
Для каждой операции показывай номер, дату, сумму, статус и связанные документы, если они доступны.
Не разрешай повторно проводить одну и ту же финансовую операцию из-за повторного нажатия или сетевой ошибки. Используй серверную идемпотентность и аудит.
Если кассовое оборудование, фискализация или платёжный терминал нужны магазину, сначала выясни, какие устройства и требования используются. Не объявляй приложение фискальной кассой без необходимой интеграции и проверки требований законодательства.
13. Профили, роли и права доступа
Спроектируй ролевую модель. Как минимум исследуй роли:
продавец;
кассир;
администратор;
руководитель или владелец.
Роли должны иметь разные разрешения.
Например, продавец может искать товары и создавать разрешённые заказы, кассир — выполнять доступные кассовые операции, администратор — управлять пользователями и настройками, руководитель — просматривать разрешённые отчёты.
Это предварительные роли, а не утверждение о текущей структуре магазина. Согласуй их с реальными бизнес-процессами.
Все критические права проверяй на сервере. Скрытие кнопки во Flutter не является механизмом безопасности.
Добавь журнал аудита для чувствительных операций: изменение цен, скидок, прав, отмена транзакций, корректировка остатков и работа с финансовыми данными.

18. План реализации
Выполняй работу по этапам.
Этап A — Discovery. Изучить рабочую папку, документы, чертежи, текущий код и доступные системы. Выявить неизвестные параметры.
Этап B — Architecture. Утвердить архитектуру, модель данных, контракты API, роли, стратегию синхронизации и дизайн-систему.
Этап C — Foundation. Подготовить структуру Flutter, backend, конфигурацию окружений, миграции, логирование и тестовый контур.
Этап D — Authentication. Реализовать регистрацию, OTP, интеграцию SMSPro, привязку клиента и безопасный биометрический сценарий.
Этап E — Catalog. Реализовать синхронизацию товаров, категории, варианты, фотографии, поиск и складские остатки.
Этап F — Cart and POS. Реализовать корзину, проверку цен, заказ, разрешённые кассовые операции и обработку ошибок.
Этап G — Cashier. Реализовать клиентов, избранное, долги, скидки, историю и транзакции.
Этап H — Verification. Выполнить интеграционные тесты, независимый аудит, исправление ошибок и проверку сборок.
Этап I — Pilot. Подготовить тестовое внедрение на копии данных 1С, инструкции и план отката. Реальные продажи включать только после проверки финансовых сценариев и согласования с магазином.
После каждого этапа зафиксируй готовые файлы, проверки, известные проблемы и условия перехода дальше.

ОБЯЗАТЕЛЬНОЕ ДОПОЛНЕНИЕ: ULTRA-DETAILED UI/UX SPECIFICATION
Мои первоначальные требования к экранам являются обязательной частью проекта. Не сокращай их, не заменяй общими формулировками и не исключай детали, даже если считаешь их несущественными.
До начала разработки создай ультрадетальную спецификацию всех экранов приложения «Оптомстрой».
Для КАЖДОГО экрана обязательно опиши:
1. Назначение экрана и роль пользователя.
2. Полную структуру экрана сверху вниз и слева направо.
3. Каждый UI-элемент, его расположение, размер, отступы, выравнивание и визуальную иерархию.
4. Цвета, типографику, иконки, радиусы, тени и состояния компонентов со ссылками на утверждённую дизайн-систему.
5. Поведение каждого поля, кнопки, карточки, переключателя, меню, фильтра и элемента управления.
6. Все анимации: начальное состояние, триггер, последовательность, конечное состояние, длительность и реакцию на ошибку.
7. Все переходы между экранами, включая передачу выбранного товара, пользователя, варианта, количества и других необходимых данных.
8. Состояния загрузки, успеха, ошибки, пустого результата, отсутствия интернета, отсутствия разрешений и повторной попытки.
9. Правила валидации, сообщения пользователю и ограничения ввода.
10. Источники данных, API, состояния приложения и бизнес-правила, от которых зависит элемент.
11. Доступные действия по ролям и ограничения безопасности.
12. Поведение при повторном нажатии, двойном запросе, возврате назад и повторном запуске приложения.
13. Требования к мобильным устройствам, планшетам и другим согласованным платформам.
14. Критерии приёмки, позволяющие проверить правильность реализации.
Не ограничивайся описанием в один абзац. Для сложных экранов используй отдельные подразделы, таблицы элементов, диаграммы переходов и последовательности действий.
Особые требования к анимации персонажа авторизации
Подробно опиши каждое состояние персонажа: нейтральное лицо, реакция на ввод телефона, ожидание проверки, успешная авторизация, отказ, неправильный OTP, повторная попытка и переход в приложение.
Не подменяй реальное распознавание лица простой анимацией. Визуальная реакция и результат проверки должны быть независимыми слоями.
Особые требования к сканированию лица при регистрации
Опиши последовательность направлений: прямо, влево, вправо и вверх. Для каждого шага укажи подсказки, индикатор выполнения, условия успешного захвата, повторную попытку, отмену и обработку неподдерживаемого устройства.
Отдельно укажи, какие функции подтверждены выбранной технологией, а какие требуют дополнительного SDK. Не заявляй полноценную защиту от подделки без соответствующей технологии.
Особые требования к каталогу
Опиши отдельно главный каталог, поиск, результаты поиска, категории, подкатегории, фильтры, сетку, список и карточку товара.
Для каждого варианта товара укажи связь с артикулом, изображениями, ценой, единицей измерения и остатками по складам.
Продумай, как интерфейс ведёт себя при большом количестве товаров, длинных названиях, отсутствии фото, нескольких расцветках и большом количестве характеристик.
Особые требования к корзине
Опиши состояния пустой корзины, корзины с товарами, изменения количества, удаления позиции, изменения цены, недостаточного остатка, устаревших данных и ошибки оформления.
Определи, как сохраняется корзина и как предотвращаются повторные операции.
Особые требования к кассиру
Опиши отдельно главную панель, поиск клиентов, профиль клиента, историю покупок, задолженности, скидки, транзакции, избранное, детали операции и подтверждение критических действий.

ОБЯЗАТЕЛЬНОЕ ТРЕБОВАНИЕ: CLEAN ARCHITECTURE И АРХИТЕКТУРА ДЛЯ БУДУЩЕГО РАЗВИТИЯ
Ты должен проектировать «Оптомстрой» как профессиональную коммерческую POS-систему, которая сначала выпускается в виде первого рабочего релиза (MVP / Release 1), а в дальнейшем будет расширяться новыми функциями, модулями и интеграциями.
Clean Architecture
Спроектируй приложение на основе принципов Clean Architecture, SOLID, разделения ответственности и слабой связанности компонентов.
Для Flutter-приложения рассмотри следующую структуру:
- Presentation: экраны, UI-компоненты, состояния, обработка пользовательских действий.
- Domain: бизнес-сущности, правила, интерфейсы репозиториев и Use Cases.
- Data: реализации репозиториев, модели передачи данных, источники данных, API-клиенты и локальное хранилище.
- Core: общие утилиты, обработка ошибок, конфигурация, сетевой слой и общие компоненты, не привязанные к конкретной бизнес-функции.
Выбери подходящий способ управления состоянием и обоснуй выбор. Не смешивай бизнес-логику с UI, не обращайся к API напрямую из экранов и не помещай всю систему в огромные файлы или универсальные классы.
Это ориентир, а не требование создавать ненужные абстракции. Структура должна соответствовать реальному масштабу проекта.
Модульная структура
Раздели систему на логические функциональные модули, например:
- Authentication — авторизация, SMS OTP и биометрический вход.
- User Profile — профиль и регистрационные данные.
- Catalog — товары, категории, подкатегории и варианты.
- Search & Filters — поиск, сортировка и фильтрация.
- Inventory — остатки и склады.
- Cart — корзина и сохранённые черновики.
- POS / Sales — оформление и проведение продаж.
- Customers — клиентская база и история покупок.
- Debts & Discounts — задолженности, скидки и связанные правила доступа.
- Favorites — избранные товары.
- OneC Integration — интеграция и синхронизация с 1С.
- Notifications — уведомления и системные сообщения.
- Settings — настройки приложения и пользователя.
Сначала проверь, какие модули действительно нужны для первого релиза. Не создавай пустые модули ради списка, но предусмотрите понятный способ добавлять их в дальнейшем.
Backend и база данных
Спроектируй серверную архитектуру с чётким разделением API, бизнес-логики, доступа к данным, авторизации, синхронизации с 1С и фоновых задач.
Определи, какие операции должны выполняться на сервере, а какие допустимы на устройстве. Секреты SMS-сервиса, критичные финансовые операции, проверка прав доступа и доверенные бизнес-правила не должны зависеть исключительно от Flutter-клиента.
Схема данных должна поддерживать дальнейшее развитие без нарушения существующей истории покупок, задолженностей, идентификаторов клиентов и связей с 1С. Продумай миграции базы данных, версии API, обработку повторных запросов, журналирование и восстановление после ошибок синхронизации.
Не выбирай микросервисную архитектуру автоматически. Для первого релиза предпочти хорошо структурированный модульный монолит, если анализ требований не докажет необходимость другого решения.
Правила развития проекта
Будущие версии могут включать дополнительные функции, роли пользователей, отчёты, аналитику, новые склады, расширенные финансовые инструменты, интеграции, уведомления и другие бизнес-модули.
Поэтому:
- Новая функция не должна требовать переписывания несвязанных модулей.
- Изменения в одном модуле должны минимально затрагивать остальные.
- Контракты API и схемы данных должны изменяться контролируемо.
- Существующие продажи, клиенты, задолженности и история операций должны сохранять целостность.
- Критические операции должны поддерживать идемпотентность и защищаться от дублирования.
- Для интеграции с 1С необходимы устойчивые внешние идентификаторы и документированная стратегия разрешения конфликтов.
- Зависимости, конфигурация окружений, секреты, логирование и обработка ошибок должны быть организованы профессионально.
- Архитектура должна поддерживать автоматизированное тестирование и CI/CD в дальнейшем.
Не переусложняй первый релиз
Не пытайся реализовать все возможные функции будущих версий сразу. Сначала создай надёжную основу и реализуй только утверждённый объём Release 1.
Не добавляй технологии, библиотеки, серверы, очереди сообщений и абстракции без обоснованной необходимости. Для каждого существенного архитектурного решения укажи его пользу, стоимость сопровождения и альтернативы.
В техническом задании отдельно зафиксируй:
1. Что входит в первый релиз.
2. Что намеренно не входит в первый релиз.
3. Какие архитектурные решения обеспечивают расширяемость.
4. Какие ограничения первого релиза допустимы.
5. Как добавлять новые функции в последующих версиях.
6. Как обновлять приложение и базу данных без потери данных.
7. Как тестировать совместимость новых версий с существующими данными и интеграцией с 1С.
