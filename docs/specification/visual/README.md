## 2. Как читать материалы

### 2.1. Порядок чтения

1. `screen-map.md` §2 — убедиться, что перечень экранов совпадает с R0 §9 (45 ID, маршруты не менялись); затем §4 — связи экранов по зонам.
2. `navigation.md` §2–§4 — как экраны собраны в оболочку (`StatefulShellRoute`), какие ветки видит каждая роль и как работают guards; §5 — какие параметры передаются при переходах.
3. `responsive-spec.md` §1 — общие правила классов окна (compact < 600, medium 600–1023, expanded 1024–1599, large ≥ 1600 lp), затем таблица нужного экрана в §3–§8.
4. `components-states.md` §2 — состояния компонента, который используется на экране; §4 — обратная проверка, на каких экранах компонент встречается.
5. HTML-файлы — открыть в браузере локально (двойной щелчок); внешних ресурсов и CDN нет, интернет не нужен.

### 2.2. Правила интерпретации

- **Статус «wireframe, не финальный интерфейс».** Все схемы, таблицы и HTML-страницы фиксируют *структуру* (какие элементы, где, в каком состоянии), а не финальную графику. Пропорции, иконки, иллюстрации и точные цвета определяются `03_UX_UI_DESIGN_SYSTEM.md`; попиксельные требования к каждому экрану — `02_SCREEN_SPECIFICATION.md`.
- **Идентификаторы.** Экраны — `SCR-xx` (R0 §9), компоненты — имена из R0 §8.5 (`AppButton`, `CartPanel` …), токены — `ds.color.*`, `ds.text.*` (R0 §8.1–8.4; в HTML — CSS-переменные `--ds-color-primary` и т. п.), решения — `D-xx` (R0 §2), вопросы — `Q-NNN` (R0 §12). Новых `SCR-`/`Q-` папка не вводит (R0 §16 п. 9).
- **Пометки.** `[РЕШЕНИЕ: D-xx]` — зафиксировано ядром; `[ТИПОВО]` — проектное значение по умолчанию, требует подтверждения; `[НОВОЕ ИМЯ]` — предложение нового идентификатора в ядро; «условно» — экран/функция включается решением заказчика (Q-003 сканирование лица). Режим клиента-покупателя условным **не является**: Q-001 закрыт ответом заказчика 2026-10-21, SCR-03, SCR-04, SCR-06, SCR-50 и роль `customer` — R1 (`CUSTOMER_SELF_SERVICE=true` по умолчанию); сотрудники сами не регистрируются — их учётные записи создаёт `admin` приглашением на SCR-45; SCR-07 показывается только при `CUSTOMER_SELF_SERVICE=false` — `[РЕШЕНИЕ: ядро §24.2]`. Заявка на возврат SCR-39 условной **не является**: это R1 must, включена по умолчанию (`app_settings.returns_enabled = true`), отключается только ответом Q-018 «возвраты полностью в 1С» без изменения кода; условна лишь автоматическая передача заявки в 1С (`RETURNS_FROM_POS_ENABLED`, по умолчанию `false`) — `[РЕШЕНИЕ: ядро §21 п.1]`.
- **Mermaid.** Диаграммы `flowchart`, `sequenceDiagram`, `stateDiagram-v2` рендерятся в GitHub/GitLab/VS Code (расширение Markdown Preview Mermaid). Подписи рёбер `flowchart` всегда в кавычках (`A -->|"подпись"| B`), чтобы скобки и спецсимволы в подписи не ломали разбор. Без рендера они читаются как текст: `A --> B` — переход, `A -.-> B` — условный переход, узлы в `[...]` — экраны.
- **Палитра.** Основной вариант R1 — **B «Оранжевый»** (выбран заказчиком 2026-10-21; D-16 в редакции ядра v1.9 §24.1; Q-006 закрыт, кроме векторного логотипа; таблица токенов — 03 §5.3); логотип — оранжевый «C + шестиугольник + стрелка». Схема A+ и вариант A «Синий» — историческая альтернатива (03 §5.2, §5.7) и используют те же имена токенов с другими значениями, поэтому матрица состояний и wireframes от варианта не зависят. Ограничения варианта B излагает владелец — 03 §5.3, §5.8–§5.9: оранжевая заливка `primary` — только с тёмным `onPrimary`; текст, ссылки, цены — `primaryText`; фокус и `info` — синие; оранжевый не означает статус. Макеты заказчика — эталон компоновки, а не цвета.
- **Замечания к ядру.** В конце каждого документа есть раздел «Замечания к ядру» — расхождения и предложения, адресованные оркестратору/владельцу R0; они не являются решениями.
- **Дополнения и журналы.** Поправки ядра v1.1/v1.2 и замечаний проверяющего внесены **прямо в основные таблицы** (их можно использовать как чек-листы без оговорок «читается с уточнением»); разделы «Дополнения по ядру» и «Журнал» в конце документов — краткая история изменений со ссылками на исправленные строки и подробности механизмов.

## 5. Контроль целостности

- Все Markdown-файлы — UTF-8 без BOM, переводы строк LF.
- Каждый `SCR-xx` из R0 §9 присутствует в `screen-map.md`, `navigation.md`, `responsive-spec.md`; каждый компонент R0 §8.5 — в `components-states.md` §2 и §4. В `components-states.md` §4 столбец «Экраны» содержит полные ID `SCR-xx` (пригодно для автоматической проверки), в столбце «Примечание» допускается сокращение NN = `SCR-NN`.
- HTML-файлы самодостаточны (inline CSS/SVG, без внешних ресурсов), содержат `<title>` и пометку «Wireframe / структурная схема для ТЗ — не финальный интерфейс».
