## 0. Слова владельца и как мы их поняли

> «est ispravki selat dizayn na telefon i chtobi vv verhu estje znachok profilya pust budet tam istoriya zakazov izbnniy i nujno chtobi sms i bank integratsii bili u sebya i chtobi bilo v servere beken tuda zapustim»

Прочтение `[ВЫВОД]` и ответы пользователя 2026-11-23 — `docs/customer/P-004_OWNER_DECISIONS.md` §2, §3. Коротко: (1) дизайн прототипа — на телефон; (2) справа в шапке — значок профиля, в нём «История заказов» и «Избранное»; (3) SMS и банк — на нашем сервере, не через 1С; (4) бэкенд — на сервер заказчика, сначала тестовый стенд. Банк — «другой», не Бакай, название неизвестно. Шапка — для всех ролей. Решение 21.11.2026 «QR через 1С» отменено в части QR.

## A. Телефон: дизайн прототипа и значок профиля — 15 ADR-122

- Класс окна compact (< 600 lp), все роли. Шапка основных экранов режима: логотип → поиск со сканером (второй строкой, если не помещается) → кнопка корзины с числом позиций (у ролей с корзиной) → колокольчик → аватар с инициалами справа. Статус синхронизации не убирается.
- Аватар открывает меню профиля нижним листом: «История заказов» (SCR-25; при `order.read.all` — «Мои / Все»), «Избранное» (SCR-40: товары; клиенты — по роли), затем прежние пункты SCR-41. Тот же порядок — на экране SCR-41.
- `BottomNavBar` остаётся без изменений; профиль — второй вход к тем же разделам (дубли не убираем, функции не теряются).
- Корзина: `CartFab` над нижней навигацией на SCR-10/11/12 — закрывает PRT-KI-06.
- Каталог: сетка 2 колонки в портрете (по R-8), категории и подкатегории — чипами с иконками (ADR-114, compact). Оформление — по шагам (02 SCR-21 compact, 4 экрана).
- Не меняются: планшет магазина (`kiosk`), medium и шире — их golden-снимки прежние.

## B. Банк на нашем сервере — 15 ADR-123

- QR — напрямую от банка через наш сервер. Переменная `QR_PROVIDER` получает нейтральное значение `bank`; `bakai` — устаревший синоним (принимается, при старте предупреждение, внутри приводится к `bank`). Новая переменная `BANK_QR_ADAPTER` — пока только `sandbox` (песочница банка). Коды хранения и контрактов не меняются: `bakai` и `qr_bakai` — исторические коды «прямой API банка», независимо от банка.
- Адаптер — за существующим портом `PaymentProvider`: динамический QR с суммой с сервера, срок жизни и перевыпуск на том же `payment_id`, отмена, опрос статуса, вебхук банка по 08 §4.9.5 (подпись, `QR_WEBHOOK_ALLOWED_IPS`, идемпотентность по референсу банка, `payment_webhook_events`, `review_reason`), ежедневная сверка QR.
- 1С получает только документ оплаты через `onec_outbox` (`payments-create`) после `received`. Методы QR 1С (`/pos/v1/payments/qr…`) при `bank` не используются; контракт 1С не ломается — методы помечены «не нужны при `QR_PROVIDER=bank`». Двойные документы оплаты недопустимы (14 Q-383).
- Банк `[НЕ ПОДТВЕРЖДЕНО: Q-381]`; что взять у банка — 14 Q-381, Q-382. API банка не выдумываем: адаптер настоящего банка — после документации.

## C. SMS на нашем сервере — 15 ADR-124

- SMS отправляет только наш pos-worker в SMSPro (pos-api → `sms_outbox` → pos-worker). `OTP_HMAC_SECRET_FILE` — один и тот же у api и worker (EQ-AUTH-08).
- Стенд — тестовый режим без трат: `SMS_STAGING_ALLOWED_PHONES`, тестовые номера `+99670000000x`. Тестовый код `246810` — только dev и демо; на стенде с настоящим шлюзом выключен.
- Настоящая SMS — только когда заказчик сам внесёт логин и ключ SMSPro в секреты (14 Q-385) и после письменного «да» пользователя.
- Пути не через наш сервер (1С, браузерное демо, Firebase) в рабочем контуре выключены; демо остаётся с пометкой «только для показа».

## D. Бэкенд на сервере: тестовый стенд — 15 ADR-125

- Стенд `optomstroy-test` — на Windows-комплекте `infra/windows` (15 ADR-121), а не на Linux с Docker и Caddy (раздел D задания переводится на Windows): Docker и Hyper-V на сервере нет, 80 и 443 — у Apache заказчика.
- Адрес — `https://api-test.37.114.51.144.sslip.io` (временное имя до домена заказчика; постоянное — `api-test.optomstroy.kg` `[ПРЕДЛОЖЕНИЕ]`). Сертификат — у Apache заказчика, способ выпуска — 14 Q-384.
- Только вымышленные данные (ADR-119). `ONEC_MODE=fixtures`, `QR_PROVIDER=bank` с `BANK_QR_ADAPTER=sandbox`, SMS — в тестовом режиме.
- Ставит администратор заказчика по нашему листу; мы проверяем под `posdeploy`. Любая команда, меняющая сервер, — только после явного «да» пользователя. 23.11.2026 SSH с машины разработчика не отвечает (порт 22) — 14 Q-386.

## E. Сборки с адресом стенда

- APK и пакет Windows с `API_BASE_URL=https://api-test.37.114.51.144.sslip.io`, в `D:\optomstroy\.tmp\builds\P-004\`. Подпись release — только если есть ключ (иначе debug; 14 Q-324). ## F. Запасной вариант: ELQR, сгенерированный нашим сервером

ELQR — единый национальный стандарт QR-платежей КР; оператор взаимодействия — ЗАО «Межбанковский процессинговый центр» (МПЦ, «Элкарт»), есть «Мерчант Платформа» со статическим и динамическим QR (R7 §3.1). Схема «C» ADR-021: наш сервер сам кодирует QR по стандарту ELQR с суммой и назначением платежа.

| | Оценка |
|---|---|
| Плюсы | не зависит от мерчант-API конкретного банка: QR оплачивает приложение любого банка — участника ELQR; сервер сам задаёт сумму и назначение (номер заказа); нет входящего маршрута, если зачисление сверяется по выписке; работает уже с одним расчётным счётом магазина |
| Минусы | **автоотметки нет**: о зачислении сервер узнаёт только из API выписки или уведомлений банка (их тоже нужно получить у банка) — иначе каждое QR-поступление подтверждает кассир (`confirm-manual` со step-up, как `QR_PROVIDER=none`); формат полезной нагрузки, контрольная сумма и поля назначения `[НЕ ПОДТВЕРЖДЕНО]` — публичной спецификации у нас нет; связать платёж с заказом можно только через поле назначения, которое плательщик может изменить `[НЕ ПОДТВЕРЖДЕНО]`; ошибки суммы ловятся только сверкой |
| Что нужно | спецификация ELQR от НБКР или МПЦ (формат, поля, контрольная сумма, правила динамического QR); идентификатор мерчанта (мерчант-ID) и реквизиты торговой точки от банка магазина; для автоотметки — API выписки или уведомлений банка (тот же вопрос, что Q-381, Q-382) |
| Стоимость сопровождения | средняя: свой кодировщик стандарта и его обновления; сверка по выписке |
| Вывод | **Запасной вариант, не основной.** Основной — API банка с вебхуком (ADR-123). ELQR берём, если банк магазина не даёт мерчант-API для динамического QR, но даёт спецификацию ELQR и мерчант-ID. Тогда отдельный адаптер за тем же портом `PaymentProvider` (например, `BANK_QR_ADAPTER=elqr`) с ручным подтверждением, пока нет API выписки. Решение — после ответа на 14 Q-381 |
