# Что изменилось и уточнилось в обмене с 1С после первой версии запроса API

Первая версия запроса на API 1С («Техническое задание на API 1С для специалиста 1С», 2026-10-21) написана до начала разработки. За время разработки серверной части POS (каталог и план обмена, заказы и QR-оплата, клиенты, долги, скидки и возвраты) появились уточнения: как POS читает и применяет данные 1С, какие поля ему нужны дополнительно, где в первой версии было неточно.

В этом разделе собраны только такие изменения и вопросы. Методы, адреса, аутентификация, формат ошибок и правила защиты от дублей остаются как в первой версии и в машинном контракте `onec-http-service.v1.yaml` (версия 1.0.0).

Важно:

- всё описанное проверено только на тестовом имитаторе 1С и тестовых данных, **не** на вашей базе: API и тестовой копии базы у нас пока нет;
- имена объектов 1С приведены как в типовых «Управление торговлей 11» / «Комплексная автоматизация 2» / ERP — **типово, уточнить** по вашей конфигурации (Q-010);
- поля и методы с пометкой **«предложение»** в контракте v1 отсутствуют: это просьба, а не готовое требование, нужен ваш ответ;
- пометка **«к сведению»** означает, что от 1С ничего нового не требуется — это описание того, как POS обрабатывает ваши данные.

## 1. Главное кратко

1. **Цены и остатки после изменений в 1С.** В API v1 нет метода срезов цен и остатков. Сейчас POS читает срезы через OData только на чтение. Нужно выбрать: методы HTTP-сервиса или OData (Q-319, см. раздел 2.2).
2. **Платёжные документы.** В первой версии POS **не вызывает** `POST /pos/v1/payments`: ПКО и поступления вводятся в 1С. Документ поступления по QR создаёт ваша банковская интеграция (Q-012, см. раздел 2.4).
3. **QR: перевыпуск с тем же `externalId`.** Перед новым QR POS синхронно отменяет прежний. В статусе и событиях `reference` должен указывать на тот QR, по которому пришли деньги (Q-014, см. раздел 2.4).
4. **Розничный покупатель.** В `POST /pos/v1/orders` POS передаёт `customer.ref = null` (Q-026, см. раздел 2.3).
5. **Скидка в строке заказа.** `discountPercent` — только ручная скидка продавца, а `amount` строки — итог после всех скидок (см. раздел 2.3).
6. **Новые поля по клиентам и скидкам (предложения).** Вид клиента, процент скидки клиента, параметры правил скидок, связь документа возврата с заявкой POS (см. разделы 2.5 и 2.6).
7. **Статусы заказов и QR сейчас читаются опросом.** Методы опроса обязательны и должны отвечать быстро. Элементы заказов, оплат и QR в `/changes` POS пока не применяет (см. раздел 2.1).

Передавайте `valueType` в нотации стандартного OData. Свойства характеристики — в её `attributes[]`: набор каждый раз заменяется целиком. | Этап E: применение данных |
| Вариант по умолчанию | `variantRef = null` в штрихкодах, ценах, остатках | Для каждого товара POS держит служебный «вариант по умолчанию». | Штрихкоды | `InformationRegister_ШтрихкодыНоменклатуры`: `ref` = `barcode`, `productRef`, `variantRef`, `packagingRef`, `barcodeType` | Значение — 4–64 символа: цифры, латиница, дефис, точка, пробел. Одно значение — одна привязка (товар, характеристика, упаковка). Если в обмене одно значение привязано к разным товарам — конфликт: остаётся текущая привязка POS (или с наименьшей ссылкой), администратору — ошибка. | Бренд (предложение) | `Catalog_Номенклатура` | Поля бренда в контракте v1 нет, поэтому фильтр по бренду в приложении пуст. Предложение: строковое поле `brand` — значение реквизита «Производитель» или «Марка», если он ведётся. | Этап E: поиск и каталог; Q-010 |
| Главная картинка (предложение) | `Catalog_Номенклатура.imageFileRef`, `Catalog_НоменклатураПрисоединенныеФайлы` | Сейчас POS выбирает главное фото по порядку файлов, а `imageFileRef` не сохраняет. Предложение: признак главного файла в элементе файла (например логическое `isMain`). Другой вариант — подтвердить, что `imageFileRef` всегда заполнен и указывает на файл того же товара. | Этап E: фото |

При замене файла обновляйте `ДатаМодификацииУниверсальная`. `size` должен совпадать с числом байт ответа `/images`, а `ETag` в виде SHA-256 — с хешем тела, иначе файл отклоняется. При запасном `ETag` («дата модификации, дефис, размер») хеш считает POS. | Этап E: фото |
| Переход с разовой выгрузки картинок (к сведению) | `GET /pos/v1/images/{ref}` | Если до готовности API картинки загружались разовой выгрузкой из папки, то после подключения метода POS снимет такие фото у товаров, где есть фото из 1С. Дубли в галерее не появятся. | Этап E: фото |
| Изменение цен | `Document_УстановкаЦенНоменклатуры`: `posted`, `priceListRefs` | Документ — только сигнал: POS перечитывает **полный** срез цен каждого вида цены из `priceListRefs`. Метода среза цен в API v1 нет. Сейчас срез читается через OData (`InformationRegister_ЦеныНоменклатуры`, `SliceLast`) учётной записью только для чтения. Без OData цены после документа не обновятся, администратору — предупреждение. | Этап E: план обмена; Q-319 |
| Срезы остатков | регистры остатков (в план обмена не входят) | Остатки POS читает полным срезом по складу (OData `Balance`, каждые 5–10 мин). Срез должен быть полным: строки, исчезнувшие из успешного среза, POS обнуляет. По товару, у которого строки на складе не было никогда, остаток считается «неизвестен», и в корзину его не добавить (Q-317). Отрицательные количества POS принимает как есть (Q-318). | Этап E: каталог; Q-317, Q-318, Q-319 |
| Остатки по списку товаров | `POST /pos/v1/check` | Метода «остатки по списку характеристик» нет. Запрос «живых» остатков в приложении сейчас отвечает последним загруженным срезом. Предложение — в вопросе Q-319. | Этап E: каталог; Q-319 |

Если для срезов будут методы HTTP-сервиса (Q-319), POS ожидает строки той же формы, что `prices` и `stock` в карточке `GET /pos/v1/catalog/{ref}`, плюс поле `productRef`:

| Срез | Параметры (предложение) | Поля строки |
|---|---|---|
| Цены | `GET /pos/v1/prices?priceListRef={ref}&limit={M}&cursor={c}` | `priceListRef`, `productRef`, `variantRef` (или `null`), `packagingRef` (или `null`), `price` (строка «0.00») |
| Остатки | `GET /pos/v1/stock?warehouseRef={ref}&limit={M}&cursor={c}` | `warehouseRef`, `productRef`, `variantRef` (или `null`), `onHand`, `reserved`, `available` (строки «0.000») |
| Остатки по списку | `POST /pos/v1/stock` с перечнем `productRef` и `variantRef` | как у среза остатков, по всем складам |

Постраничность — как в `/changes`: `hasMore` и `cursor`. Срез — на один момент времени.

### 2.4. QR-оплата и платёжные документы

| Что уточнено | Где в API (метод, тип элемента, поле) | Суть для 1С | Источник |
|---|---|---|---|
| Перевыпуск QR | `POST /pos/v1/payments/{externalId}/qr/cancel` (`reason=reissue`), затем `POST /pos/v1/payments/qr` | Перед перевыпуском POS **синхронно** (одна попытка, до 6 с) отменяет прежний QR и сразу запрашивает новый с **тем же** `externalId` платежа. Ответ — `201` с новым `reference` и новым `expiresAt` (см. раздел 3.3). Если отмена вернула `status=paid`, оплата засчитывается, и новый QR не запрашивается. Ошибка отмены перевыпуск не блокирует. | Этап F: QR; Q-014 |
| История референсов | `reference` в ответе статуса и в элементе `QrPaymentStatus` | POS хранит все прежние референсы платежа. Оплата по прежнему референсу (после перевыпуска) уходит кассиру на ручную проверку как поздняя оплата. Поэтому `reference` в статусе и в событии должен указывать на тот QR, по которому пришли деньги, а не всегда на последний. | Этап F: QR; Q-014 |
| Срок жизни QR | `QrCreateResponse.expiresAt` | Срок принимается, только если он позже момента выдачи. Иначе POS ставит «выдача + 15 мин» (`requestedTtlSeconds` = 900). Нужна гарантия, что метод возвращает будущий срок. | Этап F: QR; Q-014 |
| Отмена без запроса POS | `status = cancelled` в статусе или событии | Если QR отменён в 1С или банком без запроса POS, POS сразу считает QR истёкшим. Кассир перевыпускает QR или меняет способ оплаты. | Этап F: QR |
| Оплата после аннулирования | `status = paid` у отменённого QR | Возвращайте `paid` с фактической суммой, как в первой версии. Деньги POS автоматически не засчитывает: администратору — ошибка «оплата по аннулированному QR», возврат или аванс оформляется в 1С. | Этап F: QR; Q-014 |
| Сумма и поздняя оплата | `paidAmount`, `paidAt`, `expiresAt` | Если сумма отличается от суммы QR или оплата пришла после `expiresAt`, платёж уходит на ручную проверку. POS опрашивает статус до `expiresAt` + 60 с. Автоматического перевода «нет ответа — ручное подтверждение» нет: QR просто истекает по сроку. | Этап F: QR |
| Документ поступления | `QrPaymentStatus.documentRef`, `documentType` в ответе статуса | Документ поступления по QR создаёт ваша банковская интеграция. POS сохраняет `documentRef` у своего платежа. | Этап F: QR; Q-012 |
| Платёжные документы из POS | `POST /pos/v1/payments` | В первой версии POS **не вызывает** этот метод: ни ПКО за наличные, ни поступление за QR, ни оплату долга без заказа. В POS платёж отмечается «не отражён в 1С», ПКО оформляется в 1С. Метод остаётся в контракте и включится после ответов на Q-012, Q-124, Q-152. | Этап F: платежи; Q-012, Q-124, Q-152 |
| Причины отмены QR | `QrCancelRequest.reason` | `reissue` — перевыпуск, `method_changed` — смена способа оплаты, `voided` — аннулирование кассиром, `order_cancelled` — отмена заказа. Кроме перевыпуска, при ошибке POS повторяет отмену через 1, 2 и 5 мин до `expiresAt`. | Этап F: QR |
| Назначение платежа | `QrCreateRequest.purpose` | «Оплата заказа <номер заказа POS>». | Реализация backend |

## 3. Примеры

Все примеры — тестовые данные, поля и типы — по контракту `onec-http-service.v1.yaml`.

### 3.1. Штрихкод с верной контрольной цифрой

В тестовых примерах первой версии был штрихкод `4600000000017` с неверной контрольной цифрой EAN-13. POS принимает такое значение, но тип ставит «прочий». Верное значение — `4600000000015`:

```json
{
  "type": "InformationRegister_ШтрихкодыНоменклатуры",
  "ref": "4600000000015",
  "barcode": "4600000000015",
  "productRef": "a1b2c3d4-0000-4000-8000-000000000001",
  "variantRef": "a1b2c3d4-0000-4000-8000-000000000101",
  "packagingRef": null,
  "barcodeType": null
}
```

### 3.2. Событие оплаты QR в `/changes`

`ref` и `externalId` — UUID платежа POS. `reference` — референс того QR, по которому пришли деньги:

```json
{
  "type": "QrPaymentStatus",
  "ref": "0192f5a1-2b3c-7d4e-8f50-6a7b8c9d0e1f",
  "externalId": "0192f5a1-2b3c-7d4e-8f50-6a7b8c9d0e1f",
  "status": "paid",
  "reference": "QR-7F3A9C21",
  "paidAmount": "16007.50",
  "paidAt": "2026-10-21T14:07:12+06:00",
  "bankReference": "BK-20261021-000123",
  "documentRef": null
}
```

### 3.3. Перевыпуск QR с тем же `externalId`

Шаг 1 — `POST /pos/v1/payments/0192f5a1-2b3c-7d4e-8f50-6a7b8c9d0e1f/qr/cancel`:

```json
{
  "reason": "reissue"
}
```

Ответ, если деньги по прежнему QR ещё не пришли:

```json
{
  "externalId": "0192f5a1-2b3c-7d4e-8f50-6a7b8c9d0e1f",
  "status": "cancelled",
  "reference": "QR-7F3A9C21",
  "paidAmount": null,
  "paidAt": null,
  "bankReference": null,
  "documentRef": null
}
```

Шаг 2 — `POST /pos/v1/payments/qr` с тем же `externalId` (тело как при первом выпуске). Ответ `201` — новый `reference` и срок в будущем:

```json
{
  "externalId": "0192f5a1-2b3c-7d4e-8f50-6a7b8c9d0e1f",
  "status": "pending",
  "qrPayload": "TEST-QR-PAYLOAD-0192f5a1-2",
  "reference": "QR-8B4D0E32",
  "amount": "16007.50",
  "createdAt": "2026-10-21T14:12:00+06:00",
  "expiresAt": "2026-10-21T14:27:00+06:00"
}
```

Если на шаге 1 деньги уже пришли, 1С отвечает `status=paid` с данными оплаты. Тогда POS засчитывает оплату, и шага 2 не будет.

### 3.4. Поиск заказа по номеру через `/external-ids`

Запрос POS (сейчас без `since`):

```text
GET /pos/v1/external-ids?type=Заказ&limit=500
GET /pos/v1/external-ids?type=Заказ&limit=500&cursor=<cursor из предыдущей страницы>
```

Ответ — как в контракте. POS ищет в `items` запись с нужным `number` и датой, затем запрашивает `GET /pos/v1/orders/{externalId}/status`:

```json
{
  "items": [
    {
      "externalId": "0192f5a0-7c2e-7d3b-9a1f-3c4d5e6f7a8b",
      "objectType": "Заказ",
      "ref": "b2c3d4e5-0000-4000-8000-000000000010",
      "number": "ОС00-004512",
      "date": "2026-10-21T13:40:00+06:00",
      "deletionMark": false
    }
  ],
  "hasMore": false,
  "cursor": null
}
```

## 4. Вопросы, которые появились у разработки к программисту 1С

Номера Q-NNN — из реестра вопросов проекта. Пока ответа нет, POS работает по указанному допущению.

1. **Q-319. Срезы цен и остатков: методы HTTP-сервиса или OData?** Добавите ли вы постраничные срезы цен по виду цены, остатков по складу и остатков по списку характеристик (см. раздел 2.2)? Или POS читает их через OData учётной записью только для чтения?
  - Зачем: без метода или OData POS не перечитает цены после документа «Установка цен номенклатуры», а остатки в приложении устареют. Сейчас — OData.
2. **Q-317. Нет строки в срезе остатков.** Регистры остатков обычно не хранят нулевые остатки. Можно ли после успешного полного среза склада считать отсутствие строки нулём («нет в наличии»)?
  - Зачем: сейчас такой товар считается «остаток неизвестен», и продавец не может добавить его в корзину.
3. **Q-318. Отрицательные остатки.** Допускает ли ваша база продажу «в минус»?
  - Зачем: от этого зависит, как показывать остаток. Сейчас POS принимает значения как есть.
4. **Q-026. Розничный покупатель в заказе.** Можно ли передавать `customer.ref = null` в `POST /pos/v1/orders`, чтобы 1С подставила розничного контрагента и соглашение по умолчанию? Если нет — сообщите ссылку (`Ref_Key`) розничного контрагента.
  - Зачем: продажи без идентификации клиента оформляются на системного «Розничного покупателя», у которого в 1С нет своей карточки.
5. **Q-014 (срок жизни QR).** Гарантирует ли `POST /pos/v1/payments/qr` значение `expiresAt` в будущем? Можно ли задать срок при создании?
  - Зачем: POS показывает кассиру таймер. Срок в прошлом POS заменяет на «выдача + 15 мин».
6. **Q-014 (отмена QR и перевыпуск).** Отменяет ли `/qr/cancel` конкретный QR или «текущий» QR платежа? Что вернёт метод статуса, если после перевыпуска оплатили прежний QR? Можно ли добавить в тело отмены поле `reference`?
  - Зачем: у прежнего и нового QR один `externalId`. Без привязки к референсу запоздалая отмена может погасить новый QR, а оплата прежнего — потеряться.
7. **Q-014 (событие QR в плане обмена).** Можно ли включить регистр `POS_ОплатыQR` в план обмена? Выдержит ли интеграция опрос статуса каждые 5 с с ответом до 1 с?
  - Зачем: сейчас POS узнаёт об оплате только опросом. От скорости ответа зависит, когда кассир увидит «Оплачено».
8. **Q-012, Q-124, Q-152. Платёжные документы.** Подтвердите, что в первой версии ПКО за наличные и поступления вводят сотрудники в 1С, а поступление по QR создаёт банковская интеграция. Нужно ли позже создавать их из POS, проводить ли их (Q-124), принимать ли оплату долга без заказа (Q-152)? Нужна ли в журнале операций POS лента ПКО и реализаций, оформленных в 1С вне POS?
  - Зачем: от ответа зависит, включать ли вызовы `POST /pos/v1/payments` и обработку платёжных документов из `/changes`.
9. **Q-010, Q-012. Значения статуса заказа.** Пришлите фактические значения перечисления статусов «Заказа клиента» и правила согласования в вашей базе.
  - Зачем: POS распознаёт «НеСогласован», «НаСогласовании», «КВыполнению», «Согласован», «Закрыт». С другим значением заказ «зависнет» в состоянии «Отправляется в 1С».
10. **Q-015. Скидки.** Где хранится процент скидки клиента (соглашение, вид клиента, иное)? Можно ли передать его полем `discountPercent` соглашения? Можно ли передать параметры правил скидок (вид, значение, период, условия — см. раздел 2.5)? Нужно ли в строке заказа отдельное поле скидки клиента или суммы скидки строки?
  - Зачем: продавец должен видеть скидку клиента до отправки заказа, а 1С — различать ручную скидку и скидку клиента.
11. **Q-025. Клиенты.** Можно ли передавать вид клиента (`kind`: физлицо, ИП, юрлицо) у контрагента в `/changes` и у кандидата поиска по телефону? Что делать 1С при `failOnDuplicate=false`: создавать новую карточку при совпадении телефона или всё равно отвечать `409 POS_E_DUPLICATE`?
  - Зачем: без вида клиента POS ставит «юрлицо». Решение кассира «всё равно создать» сейчас может противоречить правилу «при совпадении не создавать».
12. **Q-017. Лимит и отсрочка долга.** Где задаются лимит и отсрочка (соглашение, договор, иное)? Совпадают ли они в соглашении и в ответе о долге? Можно ли добавить в строки детализации долга признак проведения документа?
  - Зачем: решение о продаже в долг принимается по снимку долга. Признак «не проведён» POS сейчас не получает.
13. **Q-018. Возвраты.** Можно ли передавать в «Возврате товаров от клиента» UUID заявки POS (`returnRequestExternalId`)? Какую реализацию указывать в заявке, если заказ отгружен несколькими реализациями?
  - Зачем: без связи POS сопоставляет документ возврата с заявкой только по товарам, а при частичных отгрузках можно выбрать не ту реализацию.
14. **Q-121. Виды цен.** Как называется розничный вид цены в вашей базе? Есть ли виды цен не в сомах?
  - Зачем: вид цены по умолчанию связывается по имени «Розничная», а цены не в KGS не загружаются.
15. **Q-010. Бренд и главная картинка.** Ведётся ли реквизит «Производитель» или «Марка»? Можно ли передавать его полем `brand`? Как определить главную картинку товара: всегда заполненный `imageFileRef` или признак у файла?
  - Зачем: для фильтра по бренду и правильного главного фото в каталоге.
16. **Q-129. Сотрудник POS в документе.** В `createdByUserCode` и `cashierUserCode` приходит UUID пользователя POS. Подходит ли это вам? Нужно ли сопоставление с пользователями 1С?
  - Зачем: от ответа зависит, что 1С пишет в реквизит «Менеджер» и что выводят отчёты по продавцам.
17. **Поиск заказа по номеру (номер вопроса не присвоен).** Можно ли сделать параметр `since` у `GET /pos/v1/external-ids` необязательным или добавить метод `GET /pos/v1/orders?number={номер}`?
  - Зачем: администратор привязывает заказ, оформленный в 1С вручную, по номеру документа. Сейчас POS листает весь перечень без `since`.
18. **Пустое сообщение плана обмена (номер вопроса не присвоен; проверяется при приёмке на тестовой копии, Q-011).** Корректно ли работает повторный `ВыбратьИзменения` с тем же номером, если регистраций нет? POS такое сообщение не подтверждает.
  - Зачем: иначе номера сообщений POS и 1С могут разойтись.
19. **Q-020. Нагрузка и скорость.** Допустимы ли частоты: `/changes` — раз в 5 мин; срезы остатков — каждые 5–10 мин; статусы заказов — пакетами до 200 каждые 5 мин; долги — раз в 30 мин по активным клиентам; заявки на возврат — раз в 30 мин; статус QR — каждые 5 с, пока QR на экране? Укладывается ли создание заказа в 6 с?
  - Зачем: эти значения настраиваются без изменения программы, но их нужно согласовать с возможностями сервера 1С.
20. **Q-123. Глубина истории продаж.** Подтвердите 12 месяцев для первой загрузки реализаций.
  - Зачем: более старые реализации POS не загружает. От глубины зависят объём и время первой загрузки.
21. **Q-010. Состав OData для запасного пути.** Можно ли добавить в публикацию OData справочник валют и разрешить `$orderby=Ref_Key`?
  - Зачем: чтобы определять валюту вида цены и устойчиво читать списки постранично, если API задержится.
