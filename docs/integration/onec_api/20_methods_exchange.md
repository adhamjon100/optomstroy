# Группа А. Служебные методы, план обмена и справочники

В этом разделе описаны методы HTTP-сервиса расширения «OptomstroyPOS», через которые система POS узнаёт о состоянии 1С и получает из 1С справочники, документы и события: проверка доступности, выгрузка изменений плана обмена «POS» и её подтверждение, полная перерегистрация, первая загрузка справочников, картинки товаров, перечень объектов, созданных из POS, и (по желанию) карточка товара одним вызовом.

Все методы группы А **только читают** данные учёта. Ни один из них не создаёт, не изменяет и не проводит документы и справочники типовой конфигурации. Единственные записи, которые они делают, — служебные: нумерация и снятие регистрации изменений узла «POS», запись в журнал запросов расширения.

Имена объектов типовой конфигурации приведены для «Управление торговлей 11» (они же в основном совпадают с «Комплексная автоматизация 2» и ERP) и помечены «типово — уточнить»: конфигурация вашей базы нам пока не известна (вопрос Q-010 — какая конфигурация, релиз и платформа). Если в вашей базе объект называется иначе, используйте свой объект и сообщите нам имя — формат JSON при этом не меняется.

## А.1. Общие правила для методов группы

### Адрес, аутентификация и заголовки

- Базовый адрес: `https://<сервер-1С>/<публикация>/hs/pos/v1/…` (сегмент `hs` — типово, зависит от публикации). Только HTTPS (TLS 1.2 и выше), доступ только из локальной сети магазина с адреса сервера POS или из подсети VPN-туннеля.
- Аутентификация: пользователь информационной базы `pos_hs` с ролью `POS_ИнтеграцияPOS` (Basic, либо JWT, если его поддерживает ваша платформа — выбираем вместе при приёмке) **и** заголовок `X-POS-Client-Key` с ключом клиента. Без ключа или с неверным ключом — `401` даже при верном пароле.
- Заголовок запроса `X-Request-Id` (UUID в нижнем регистре) приходит в **каждом** запросе. Расширение записывает его в журнал `POS_ЖурналЗапросовPOS` и возвращает в заголовке ответа `X-Request-Id` и в поле `requestId` тела ошибки. При повторе того же запроса POS отправляет тот же `X-Request-Id`.
- Заголовок ответа `X-POS-API-Version: 1` — во всех успешных ответах.
- Заголовок `Idempotency-Key` в методах группы А не используется: методы чтения безопасны при повторе по своей природе, а подтверждение `/changes/ack` идемпотентно по номеру сообщения.
- Тела запросов и ответов — `application/json; charset=utf-8` (кроме `/images` — двоичный файл).

### Формат значений

| Что | Формат | Пример |
|---|---|---|
| Ссылка 1С (`ref`, `…Ref`) | GUID ссылки (`УникальныйИдентификатор()`) строкой в нижнем регистре | `"a1b2c3d4-0000-4000-8000-000000000001"` |
| `externalId` | UUID, присвоенный в POS, строкой в нижнем регистре | `"0192f5a0-7c2e-7d3b-9a1f-3c4d5e6f7a8b"` |
| Деньги, проценты | строка с точкой и двумя знаками | `"16007.50"`, `"5.00"` |
| Количество, коэффициент | строка с точкой и тремя знаками | `"2.000"`, `"6.000"` |
| Дата и время | ISO 8601 со смещением `+06:00` (Бишкек) | `"2026-10-21T14:05:00+06:00"` |
| Валюта | код ISO 4217; в первой версии — только `KGS` | `"KGS"` |
| Необязательное поле без значения | `null` (обязательные поля `null` не принимают) | `"sku": null` |
| Неизвестные поля | получатель игнорирует; добавлять поля можно без смены версии | — |

### Ошибки — общий формат

Тело ошибки всегда одно и то же:

```json
{
  "code": "POS_E_MAINTENANCE",
  "message": "Идёт обновление конфигурации",
  "requestId": "0192f5c3-0000-7000-8000-000000000001"
}
```

Поле `details` добавляется только там, где оно описано. `message` — текст для журнала **без персональных данных** (без телефонов, ИНН, сумм долга).

Временные ошибки (POS повторяет запрос позже): `POS_E_LOCKED`, `POS_E_INTERNAL`, `POS_E_MAINTENANCE`. Ошибки данных (POS не повторяет): `POS_E_BAD_REQUEST`, `POS_E_VALIDATION`. Ошибки доступа (`POS_E_UNAUTHORIZED`, `POS_E_FORBIDDEN`) POS не повторяет до исправления учётных данных или прав и сразу сообщает администратору.

Ответы `401` и `503 POS_E_MAINTENANCE` возможны в любом методе.

### Как POS повторяет запросы чтения

- Клиент POS повторяет запрос `GET` при временной ошибке (нет связи, таймаут, `500`, `503`) до трёх раз подряд с короткой паузой (около 0,5 и 1 с).
- Если и это не помогло, задание синхронизации завершается с ошибкой и повторяется ещё дважды с паузами 1 и 2 минуты; затем — по обычному расписанию. После трёх неудачных заданий подряд или если 1С недоступна дольше 10 минут, администратор POS получает уведомление.
- При `401` и `403` POS не делает повторов, уведомляет администратора и обращается к 1С снова не раньше чем через 15 минут.
- Одновременно от POS — не более 2 соединений и не более 10 запросов в секунду. Методы `/changes` никогда не вызываются параллельно (одно задание на узел).

## А.2. Методы

### GET /pos/v1/health — проверка доступности и состояния обмена

#### Назначение

Метод показывает, что расширение установлено и работает, и сообщает версии (API, расширения, платформы, конфигурации) и состояние очереди изменений узла «POS». POS использует его для мониторинга связи с 1С, для собственной проверки готовности, перед каждым циклом обмена (чтобы продолжить с последнего подтверждённого номера сообщения) и после ошибки `POS_E_ACK_OUT_OF_ORDER` (чтобы выровнять номер сообщения). Если `apiVersion` несовместима с ожидаемой (`1`), POS приостанавливает обмен и сообщает администратору.

#### Когда вызывается и как часто

- Раз в 1–5 минут для мониторинга.
- Перед каждым циклом чтения `/changes` (по умолчанию раз в 5 минут).
- После ответа `409 POS_E_ACK_OUT_OF_ORDER` на подтверждение.
- Вручную при приёмке (контрольный пример, шаг КП-1: с ключом и без ключа).

#### Запрос

- Метод и путь: `GET /pos/v1/health`.
- Заголовки: `Authorization`, `X-POS-Client-Key`, `X-Request-Id`, `Accept: application/json`.
- Параметров и тела нет.

#### Ответ

Код `200` — расширение доступно. Заголовки ответа: `X-POS-API-Version: 1`, `X-Request-Id`.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `apiVersion` | строка | да | версия API из константы `POS_НастройкиPOS.ВерсияAPI`; для этой версии — `"1"` |
| `extensionVersion` | строка | да | версия расширения «OptomstroyPOS» |
| `platform` | строка | да | версия платформы 1С:Предприятие |
| `configuration` | строка | да | имя конфигурации, например `УправлениеТорговлей` |
| `configurationVersion` | строка | да | релиз конфигурации |
| `serverTime` | дата-время | да | текущее время сервера 1С с `+06:00`; POS по нему контролирует расхождение часов |
| `exchangeNode` | строка | да | имя узла плана обмена — `POS` |
| `registrationBacklog` | целое ≥ 0 | да | число записей регистрации изменений узла «POS» во всех таблицах изменений состава |
| `lastAckMessageNumber` | целое ≥ 0 | да | последний подтверждённый номер сообщения (см. `/changes/ack`); до первого подтверждения — `0` |
| `status` | строка | да | `ok`; `warning`, если есть не подтверждённые сообщения старше 24 часов или записей регистрации больше 100 000 |

POS проверяет, что `apiVersion` — строка, а `lastAckMessageNumber` — число; иначе ответ считается не соответствующим контракту.

#### Ошибки

| HTTP-код | Код ошибки | Когда | Что делает POS |
|---|---|---|---|
| 401 | `POS_E_UNAUTHORIZED` | нет аутентификации, неверный пароль или JWT, нет или неверен `X-POS-Client-Key` | уведомляет администратора; следующий запрос не раньше чем через 15 минут |
| 403 | `POS_E_FORBIDDEN` | у роли нет прав на метод | как при 401 |
| 500 | `POS_E_INTERNAL` | исключение встроенного языка | считает 1С временно недоступной, повторяет позже |
| 503 | `POS_E_MAINTENANCE` | расширение отключено или идёт обновление конфигурации | считает 1С временно недоступной, повторяет позже |

Без аутентификации ответ — только `401` в формате ошибки, **без каких-либо сведений о системе** (версий, имени конфигурации, числа записей).

#### Правила на стороне 1С

- Метод только читает данные; ничего не создаёт и не проводит.
- `registrationBacklog` — количество записей в таблицах изменений (`<Объект>.Изменения`) с отбором по узлу «POS» по всем объектам состава плана обмена (см. раздел А.3).
- `lastAckMessageNumber` — номер, переданный в последнем успешном `/changes/ack`. Как хранить его (реквизит узла, константа расширения) — на ваше усмотрение; важно, чтобы после ответа `200` на подтверждение метод `/health` сразу возвращал новый номер.
- `status = warning` выставляется, если самое старое не подтверждённое сообщение выдано более 24 часов назад или `registrationBacklog` больше 100 000.
- Вызов записывается в `POS_ЖурналЗапросовPOS` (момент, метод, код ответа, длительность) с `X-Request-Id`.

#### Пример запроса

```text
GET https://host-1c/publication/hs/pos/v1/health
Authorization: Basic <base64 от «pos_hs:пароль»>
X-POS-Client-Key: <ключ клиента>
X-Request-Id: 0192f5c3-0000-7000-8000-000000000001
Accept: application/json
```

#### Пример ответа

```json
{
  "apiVersion": "1",
  "extensionVersion": "1.0.3",
  "platform": "8.3.25.1000",
  "configuration": "УправлениеТорговлей",
  "configurationVersion": "11.5.20.50",
  "serverTime": "2026-10-21T14:05:00+06:00",
  "exchangeNode": "POS",
  "registrationBacklog": 142,
  "lastAckMessageNumber": 5120,
  "status": "ok"
}
```

Пример ответа без ключа (`401`):

```json
{
  "code": "POS_E_UNAUTHORIZED",
  "message": "Неверный X-POS-Client-Key",
  "requestId": "0192f5c3-0000-7000-8000-000000000001"
}
```

#### Требования к скорости

Отдельной цели по времени не задано. Таймаут POS — 5 с на соединение и 30 с на ответ. Метод вызывается часто, поэтому подсчёт `registrationBacklog` должен выполняться одним запросом к таблицам изменений без чтения самих объектов.

### GET /pos/v1/changes — выгрузка страницы сообщения обмена плана «POS»

#### Назначение

Основной канал получения данных из 1С. Через план обмена «POS» расширение передаёт все изменения нужных POS объектов: создание, изменение, установку и снятие пометки удаления, физическое удаление. POS не перечитывает каталог целиком, а получает только то, что изменилось. Одно **сообщение обмена** с номером `N+1` выдаётся постранично; после применения всех страниц POS подтверждает его методом `/changes/ack`. Состав объектов и поля каждого типа элемента — в разделе А.3.

#### Когда вызывается и как часто

- Одним заданием POS на узел, по умолчанию раз в 5 минут; параллельных вызовов `/changes` от POS не бывает.
- Каждый цикл: `GET /changes?since=N` без `cursor`, затем страницы того же сообщения по `cursor`, пока `hasMore=true`.
- Вручную администратором POS (внеочередной цикл) и после `/changes/reregister`.
- Обычно — одна страница за цикл; после массовых изменений в 1С — несколько.

#### Запрос

- Метод и путь: `GET /pos/v1/changes?since={N}&limit={M}&cursor={c}`.
- Заголовки: `Authorization`, `X-POS-Client-Key`, `X-Request-Id`, `Accept: application/json`.
- Тела нет.

| Параметр | Тип | Обязательно | Описание |
|---|---|---|---|
| `since` | целое ≥ 0 | да | последний **подтверждённый** номер сообщения `N`; ответ — сообщение `N+1`. POS перед циклом сверяет своё значение с `lastAckMessageNumber` из `/health` и берёт большее |
| `limit` | целое ≥ 1 | нет | число элементов на странице; по умолчанию 1000, максимум 5000; большее значение расширение молча ограничивает до 5000. POS по умолчанию передаёт 1000 |
| `cursor` | строка | нет | непрозрачный ключ продолжения из предыдущей страницы того же сообщения; POS передаёт его без изменений |

#### Ответ

Код `200` — страница сообщения. Заголовки ответа: `X-POS-API-Version: 1`, `X-Request-Id`.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `messageNumber` | целое ≥ 1 | да | номер выдаваемого сообщения, всегда `since + 1`; одинаков на всех страницах сообщения |
| `hasMore` | булево | да | `true`, пока после курсора есть элементы; на последней странице — `false` |
| `cursor` | строка | да (может быть `null`) | ключ следующей страницы; при `hasMore=true` — обязательно непустая строка; на последней странице — `null` |
| `generatedAt` | дата-время | да | момент формирования страницы |
| `items` | массив элементов | да | не более `limit` и не более 5000 элементов; может быть пустым. Каждый элемент — объект с полем `type`; состав полей по типам — раздел А.3 |

Если регистраций нет, ответ — `messageNumber = N+1`, `items = []`, `hasMore = false`, `cursor = null`. Пустое сообщение POS не подтверждает. Как ведёт себя `ПланыОбмена.ВыбратьИзменения` при отсутствии регистраций на вашей платформе, проверяется при приёмке.

#### Ошибки

| HTTP-код | Код ошибки | Когда | Что делает POS |
|---|---|---|---|
| 400 | `POS_E_BAD_REQUEST` | `since` не целое или отрицательное, неверный `limit`, неизвестный или чужой `cursor` | откатывает всё сообщение, записывает ошибку в журнал синхронизации, автоматически не повторяет |
| 401 | `POS_E_UNAUTHORIZED` | неверные учётные данные или ключ | откатывает сообщение, уведомляет администратора, следующий запрос не раньше чем через 15 минут |
| 403 | `POS_E_FORBIDDEN` | нет прав роли | как при 401 |
| 500 | `POS_E_INTERNAL` | исключение встроенного языка | откатывает сообщение, повторяет позже; следующий цикл начинает сообщение заново (без `cursor`) |
| 503 | `POS_E_LOCKED` | база в монопольном режиме или данные заблокированы | как при 500 |
| 503 | `POS_E_MAINTENANCE` | расширение отключено, идёт обновление | как при 500 |

Любая ошибка на любой странице (в том числе таймаут и ответ не по контракту, например `hasMore=true` без `cursor` или разные `messageNumber` на страницах одного сообщения) приводит к откату **всего** сообщения на стороне POS; подтверждение не отправляется, и следующий цикл запрашивает то же сообщение с начала.

#### Правила на стороне 1С

1. **Начало сообщения.** Запрос **без** `cursor` начинает (или начинает заново) сообщение `N+1`: расширение вызывает `ПланыОбмена.ВыбратьИзменения(УзелPOS, N+1)`, и платформа присваивает номер `N+1` **всем** ещё не пронумерованным регистрациям узла, а не только первым `limit` (поведение нумерации — типово, проверить на вашей платформе).
2. **Страницы.** Страницы формируются из таблиц регистрации узла (`<Объект>.Изменения` с отбором «узел = POS, номер сообщения ≤ N+1» — включая не снятые записи прежних номеров) в **устойчивом порядке**: тип объекта, затем ссылка или ключ набора записей. `cursor` — непрозрачный ключ последнего выданного элемента (например, тип и ссылка, закодированные в Base64); POS его не разбирает.
3. **Повторная выдача.** Пока нет подтверждения, повторный `GET /changes?since=N` без `cursor` выдаёт сообщение с тем же номером `N+1` и всеми элементами первой попытки (плюс то, что успело зарегистрироваться и пронумероваться заново).
4. **Текущее состояние.** Объект выгружается в **текущем** состоянии на момент формирования страницы, а не «каким он был при регистрации». Промежуточные версии не нужны.
5. **Изменение после нумерации.** Если объект изменён в 1С после нумерации, платформа регистрирует его заново без номера: он выпадает из ещё не выданных страниц сообщения `N+1` и в любом случае приходит в сообщении `N+2`. Изменения не теряются.
6. **Удаления.** Пометка удаления — обычный элемент с `deletionMark: true`. Физическое удаление объекта или очистка набора записей регистра — элемент `ObjectDeletion` (раздел А.3).
7. **Объекты, созданные из POS.** Для заказов, платежей, клиентов и заявок, созданных через API, элемент содержит `externalId` из регистра `POS_ВнешниеИдентификаторыPOS` — по нему POS сопоставляет объект, даже если ответ на создание был потерян.
8. **Только чтение.** Метод не записывает объекты учёта и не проводит документы. Чтение таблиц изменений выполняет код общего модуля `POS_Сервер` в привилегированном режиме после проверки ключа; роли `POS_ИнтеграцияPOS` прямые права на объекты не нужны. Динамический код по входным данным (`Выполнить()`, сборка текста запроса из параметров) не используется.
9. **Блокировки.** Чтение не должно ставить длительных управляемых блокировок и мешать работе пользователей 1С.
10. **Журнал.** В `POS_ЖурналЗапросовPOS` фиксируются номер сообщения, число элементов страницы, длительность и `X-Request-Id`.

Известный риск: в некоторых версиях платформы `ВыбратьИзменения` для документов, заимствованных в расширение, работает с ошибкой — проверьте на тестовой копии и сообщите нам результат.

### POST /pos/v1/changes/ack — подтверждение полного применения сообщения

#### Назначение

POS сообщает 1С, что сообщение обмена с указанным номером полностью получено и записано в базу POS. Только после этого расширение снимает регистрацию изменений. Так ни одно изменение не теряется: если POS не смог применить сообщение, регистрации остаются, и сообщение будет выдано повторно.

#### Когда вызывается и как часто

- Один раз на каждое непустое сообщение — после применения **всех** его страниц (последняя страница — `hasMore=false`) и фиксации транзакции в базе POS.
- Для пустого сообщения (`items` пусты на всех страницах) подтверждение не отправляется.
- Если POS получил сообщение с номером, не большим уже применённого (например, после сбоя подтверждения), данные повторно не применяются, но подтверждение этого номера отправляется.
- Если подтверждение не прошло (таймаут, временная ошибка), POS не отправляет его повторно отдельно: следующий цикл получает то же сообщение и применяет его ещё раз без побочных эффектов, затем подтверждает.

#### Запрос

- Метод и путь: `POST /pos/v1/changes/ack`.
- Заголовки: `Authorization`, `X-POS-Client-Key`, `X-Request-Id`, `Content-Type: application/json; charset=utf-8`.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `messageNumber` | целое ≥ 1 | да | номер полностью применённого сообщения (`N+1` из `/changes`) |

#### Ответ

Код `200` — сообщение подтверждено (или уже было подтверждено раньше).

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `messageNumber` | целое ≥ 1 | да | подтверждённый номер |
| `removedRegistrations` | целое ≥ 0 | нет | число снятых записей регистрации — для журнала; если считать дорого, поле можно не возвращать |

#### Ошибки

| HTTP-код | Код ошибки | Когда | Что делает POS |
|---|---|---|---|
| 400 | `POS_E_BAD_REQUEST` | неверный JSON, нет `messageNumber`, номер не целое положительное | записывает ошибку, автоматически не повторяет; сообщение будет выдано повторно |
| 409 | `POS_E_ACK_OUT_OF_ORDER` | подтверждается номер больше последнего выданного | читает `/health.lastAckMessageNumber`, выравнивает свой номер по нему и продолжает со следующего сообщения |
| 401, 403 | `POS_E_UNAUTHORIZED`, `POS_E_FORBIDDEN` | доступ | уведомляет администратора; данные уже применены, сообщение придёт повторно |
| 500 | `POS_E_INTERNAL` | исключение | данные уже применены; следующий цикл получает то же сообщение и подтверждает его заново |
| 503 | `POS_E_LOCKED`, `POS_E_MAINTENANCE` | блокировка, обслуживание | как при 500 |

Пример ответа `409`:

```json
{
  "code": "POS_E_ACK_OUT_OF_ORDER",
  "message": "Номер сообщения 5130 не выдавался",
  "requestId": "0192f5c3-0000-7000-8000-000000000001"
}
```

#### Правила на стороне 1С

1. Регистрация снимается **только по номеру**: `ПланыОбмена.УдалитьРегистрациюИзменений(УзелPOS, N+1)` — удаляются записи узла с номером сообщения не больше подтверждённого.
2. Снимать регистрацию по отдельным объектам (`УдалитьРегистрациюИзменений(УзелPOS, <ссылка>)`) **запрещено**: так удалилась бы и регистрация изменения, сделанного между выборкой и подтверждением.
3. Объекты, изменённые после выборки, номера не имеют и остаются зарегистрированными — они придут в следующем сообщении.
4. Повтор подтверждения уже подтверждённого (или меньшего) номера — `200` без каких-либо действий.
5. Номер больше последнего выданного — `409 POS_E_ACK_OUT_OF_ORDER`, регистрации не трогаются.
6. После ответа `200` номер становится `lastAckMessageNumber` в `/health`.
7. В `POS_ЖурналЗапросовPOS` фиксируются подтверждённый номер и число снятых регистраций.
8. Объекты учёта не изменяются; запись выполняет только `POS_Сервер` в привилегированном режиме.

#### Пример запроса

```json
{
  "messageNumber": 5121
}
```

#### Пример ответа

```json
{
  "messageNumber": 5121,
  "removedRegistrations": 2500
}
```

#### Требования к скорости

Отдельной цели не задано; таймаут POS — 30 с. Для больших сообщений снятие регистрации должно укладываться в этот таймаут.

### POST /pos/v1/changes/reregister — полная перерегистрация состава плана обмена

#### Назначение

Регистрирует в узле «POS» **все** объекты состава плана обмена, чтобы POS мог заново получить полный набор данных через `/changes`. Нужна при первом подключении (если первая загрузка идёт через план обмена), для полной перезагрузки данных по решению администратора и после того, как в POS подключена обработка новых типов элементов.

#### Когда вызывается и как часто

- Редко и только вручную: администратор POS или при приёмке (контрольный пример, шаг КП-2).
- Автоматических повторов нет.

#### Запрос

- Метод и путь: `POST /pos/v1/changes/reregister`.
- Заголовки: `Authorization`, `X-POS-Client-Key`, `X-Request-Id`.
- Тело не требуется (пустое).

#### Ответ

Код `202` — перерегистрация принята; работа может идти в фоне. Тела нет. Заголовки ответа: `X-POS-API-Version: 1`, `X-Request-Id`.

#### Ошибки

| HTTP-код | Код ошибки | Когда | Что делает POS |
|---|---|---|---|
| 401, 403 | `POS_E_UNAUTHORIZED`, `POS_E_FORBIDDEN` | доступ | показывает ошибку администратору |
| 500 | `POS_E_INTERNAL` | исключение | показывает ошибку администратору; повтор — вручную |
| 503 | `POS_E_LOCKED`, `POS_E_MAINTENANCE` | блокировка, обслуживание | как при 500 |

#### Правила на стороне 1С

- Для каждого объекта состава (раздел А.3) вызывается `ПланыОбмена.ЗарегистрироватьИзменения(УзелPOS, Метаданные.<Объект>)`; для регистров сведений регистрируются все наборы записей.
- Работа может выполняться фоновым заданием (например, через механизм длительных операций БСП): метод возвращает `202`, не дожидаясь окончания. Пока регистрация идёт, `/changes` выдаёт то, что уже зарегистрировано; остальное придёт следующими сообщениями.
- Повторный вызов безопасен: регистрируется тот же состав.
- Вызов (и итог фоновой регистрации) записывается в `POS_ЖурналЗапросовPOS`.
- Объекты учёта не изменяются.
- Перерегистрация документов охватывает все документы состава. POS применяет реализации только за последние `N` месяцев (по умолчанию 12, вопрос Q-123 — глубина истории продаж), более старые пропускает, поэтому объём сообщений может быть большим — по возможности запускайте её вне рабочего времени.

#### Пример запроса

```text
POST https://host-1c/publication/hs/pos/v1/changes/reregister
Authorization: Basic <base64 от «pos_hs:пароль»>
X-POS-Client-Key: <ключ клиента>
X-Request-Id: 0192f5c3-0000-7000-8000-000000000003
Content-Length: 0
```

#### Пример ответа

```text
HTTP/1.1 202 Accepted
X-POS-API-Version: 1
X-Request-Id: 0192f5c3-0000-7000-8000-000000000003
```

#### Требования к скорости

Ответ `202` — в пределах таймаута POS (30 с); сама регистрация — в фоне без ограничения по времени, но без длительных блокировок, мешающих пользователям.

### Первая (полная) загрузка справочников — отдельного метода нет

#### Назначение

При первом подключении POS должен получить весь каталог, клиентов, цены, остатки и долги. Отдельных методов выгрузки «снимков» в HTTP-сервисе нет: первая загрузка выполняется одним из двух способов. От специалиста 1С нужно подготовить один из них (лучше — первый).

#### Когда вызывается и как часто

- Один раз при подключении; повторно — по решению администратора POS (полная перезагрузка) и еженедельно ночью в режиме сверки (без перезаписи неизменённых строк).
- История продаж и картинки — только ночью, в окне 01:00–06:00 по Бишкеку.

#### Запрос

**Способ 1 (основной) — стандартный OData только на чтение.**

- Отдельный пользователь `pos_integration`: только чтение перечисленных ниже объектов и «Удалённый доступ через OData»; роль `POS_ИнтеграцияPOS` ему **не** назначается. Под `pos_integration` запросы к `/hs/pos/v1/*` и любые `POST`, `PATCH`, `DELETE` к OData должны отклоняться; под `pos_hs` должны отклоняться запросы к OData.
- Состав публикации OData задаётся списком разрешённых объектов («Настройки стандартного интерфейса OData» БСП или `УстановитьСоставСтандартногоИнтерфейсаOData`). Ничего сверх списка не публикуется (в частности, регистр бухгалтерии не публикуется).
- POS читает страницами (`$top` по 1000, не более 2000; `$skip` или ключевая пагинация), не более 2 соединений, с `$format=json`, и после каждой сущности сверяет количество с `$count`.
- Порядок загрузки: единицы → категории (группы номенклатуры) → номенклатура и упаковки → характеристики → свойства → штрихкоды → склады → виды цен и цены → остатки → клиенты и телефоны → долги → скидки → история продаж (за 12 месяцев, ночью) → картинки.

**Способ 2 (если OData публиковать нельзя) — через план обмена.**

1. `POST /pos/v1/changes/reregister`.
2. Чтение `GET /pos/v1/changes` страницами до `hasMore=false`, подтверждение `POST /pos/v1/changes/ack`; повторять циклы, пока `registrationBacklog` не станет равным 0.
3. Остатков, цен по видам цен и долгов план обмена не содержит. Если вы выбираете этот способ — сообщите нам до начала работ.

#### Ответ

Для способа 1 — стандартные ответы OData (`$format=json`, значения по платформе). Для способа 2 — ответы методов `/changes`, `/changes/ack`, `/changes/reregister`.

| 401, 403 (OData) | ошибка платформы | нет доступа пользователя `pos_integration` к коллекции | загрузка сущности завершается с ошибкой, администратору — уведомление |
| 404 (OData) | ошибка платформы | коллекции нет в публикации или в конфигурации | для необязательных объектов шаг пропускается, для обязательных — ошибка загрузки |
| 5xx, таймаут | ошибка платформы | сбой или перегрузка сервера | повтор страницы; прерванная загрузка продолжается без дублей |
| — | расхождение `$count` | число загруженных записей не совпало с `$count` | загрузка помечается как частичная, список расхождений — администратору; объекты, не встреченные в загрузке, не помечаются удалёнными |

#### Правила на стороне 1С

- Публикация OData — **только на чтение** и только с составом из таблицы выше; запись через OData не используется ни в каком режиме.
- На тестовой копии нужно проверить и сообщить: работает ли `Balance` без параметра `Period` (или нужно передавать текущее время), поддерживается ли серверная пагинация (`$top`/`$skip`) и сортировка по `Ref_Key`.
- Повторное использование сеансов веб-сервера (`reuseSessions`, `sessionMaxAge`, `poolSize` в `default.vrd` — типово) желательно включить.
- Пометка удаления в 1С отражается в POS пометкой, а не удалением; ключ сопоставления всех объектов — только `Ref_Key` (не код, не артикул, не наименование).

#### Пример запроса

```text
GET https://host-1c/publication/odata/standard.odata/Catalog_Склады?$select=Ref_Key,DataVersion,DeletionMark,IsFolder,Code,Description&$top=1000&$skip=0&$format=json
GET https://host-1c/publication/odata/standard.odata/Catalog_Склады/$count
```

#### Пример ответа

```json
{
  "value": [
    {
      "Ref_Key": "d4e5f6a7-0000-4000-8000-000000000001",
      "DataVersion": "AAAAAQAAAAA=",
      "DeletionMark": false,
      "IsFolder": false,
      "Code": "000000001",
      "Description": "Основной склад"
    }
```

#### Требования к скорости

- Ориентир полной загрузки для 50 000 позиций (без картинок и истории) — не более 30 минут на клиент-серверной базе; уточняется замером на тестовой копии.
- Полный срез остатков (около 200 000 строк при 4 складах) — до 120 с, срез одного склада — до 30 с; уточняется замером. Если срез остатков дольше 30 с или растут блокировки, POS увеличивает интервалы опроса; для файловой базы остатки — не чаще раза в 15 минут.
- Работа пользователей 1С не должна ухудшаться.

### GET /pos/v1/images/{ref} — файл картинки товара

#### Назначение

Отдаёт байты присоединённого файла номенклатуры (картинки товара). POS узнаёт о файлах из элементов `Catalog_НоменклатураПрисоединенныеФайлы` выгрузки `/changes` (или из списка OData при первой загрузке), а сами байты скачивает этим методом, проверяет, сжимает в WebP трёх размеров и хранит у себя.

#### Когда вызывается и как часто

- Ночью раз в сутки (окно 01:00–06:00 по Бишкеку) и после появления новых товаров.
- Только по новым и изменившимся файлам: POS сравнивает версию файла (дата модификации и размер) с уже скачанной; ночной прогон без изменений к 1С не обращается.
- Первичная выгрузка всех картинок может занять несколько ночей.

#### Запрос

- Метод и путь: `GET /pos/v1/images/{ref}`.
- Заголовки: `Authorization`, `X-POS-Client-Key`, `X-Request-Id`, `Accept: image/*, application/octet-stream, application/json`, необязательный `If-None-Match`.

| Параметр | Где | Тип | Обязательно | Описание |
|---|---|---|---|---|
| `ref` | путь | строка (GUID) | да | ссылка присоединённого файла: `imageFileRef` товара или `ref` элемента `Catalog_НоменклатураПрисоединенныеФайлы` |
| `If-None-Match` | заголовок | строка | нет | значение `ETag` из предыдущего ответа |

#### Ответ

| Код | Смысл | Тело и заголовки |
|---|---|---|
| 200 | файл отдан | тело — байты файла; `Content-Type` по расширению (`image/jpeg`, `image/png`, иначе `application/octet-stream`), `Content-Length`, `ETag`, `X-POS-API-Version`, `X-Request-Id` |
| 304 | файл не изменился (`If-None-Match` совпал с текущим `ETag`) | тела нет; заголовок `ETag` |

| Заголовок | Описание |
|---|---|
| `ETag` | `"<sha256>"` — SHA-256 содержимого файла в шестнадцатеричном виде, в кавычках. Если хеширование SHA-256 на вашей платформе недоступно — `"<ДатаМодификацииУниверсальная>-<Размер>"`, тогда хеш считает POS |
| `Content-Length` | размер тела в байтах |
| `Content-Type` | тип по расширению файла |

#### Ошибки

| HTTP-код | Код ошибки | Когда | Что делает POS |
|---|---|---|---|
| 404 | `POS_E_NOT_FOUND` | файла с такой ссылкой нет | помечает картинку как недоступную, товар показывается с заглушкой |
| 401, 403 | `POS_E_UNAUTHORIZED`, `POS_E_FORBIDDEN` | доступ | уведомляет администратора, прекращает прогон |
| 500 | `POS_E_INTERNAL` | исключение | повторяет позже (в следующем ночном прогоне) |
| 503 | `POS_E_MAINTENANCE` | обслуживание | повторяет позже |

#### Правила на стороне 1С

- Байты читаются программным интерфейсом присоединённых файлов БСП (типово — например, получение двоичных данных файла через модуль работы с файлами) — из информационной базы или из тома, где бы файл ни хранился (вопрос Q-022 — где хранятся картинки и сколько их).
- **Путь к файлу на диске сервера 1С в ответе запрещён** — ни в теле, ни в заголовках.
- `If-None-Match` сравнивается с текущим `ETag` буквально; при совпадении — `304` без тела.
- `ETag` должен быть одинаковым при повторных запросах неизменённого файла.
- Метод только читает; файл и справочник не изменяются.
- POS принимает как картинки файлы с расширениями `jpg`, `jpeg`, `jpe`, `jfif`, `png`, `webp`, `gif`, `tif`, `tiff`, `heic`, `heif`; прочие присоединённые файлы (PDF, документы) в фото не попадают. Файл больше 10 МБ POS не обрабатывает (ошибка позиции).

#### Пример запроса

```text
GET https://host-1c/publication/hs/pos/v1/images/a1b2c3d4-0000-4000-8000-0000000000f1
Authorization: Basic <base64 от «pos_hs:пароль»>
X-POS-Client-Key: <ключ клиента>
X-Request-Id: 0192f5c3-0000-7000-8000-000000000004
If-None-Match: "9f2c4e7a1b3d5f6e8a0c2e4f6a8b0c1d3e5f7a9b1c3d5e7f9a1b3c5d7e9f1a3b"
```

#### Пример ответа

```text
HTTP/1.1 200 OK
Content-Type: image/jpeg
Content-Length: 184320
ETag: "5d41402abc4b2a76b9719d911017c5925d41402abc4b2a76b9719d911017c592"
X-POS-API-Version: 1
X-Request-Id: 0192f5c3-0000-7000-8000-000000000004

<двоичные данные файла>
```

Если файл не изменился:

```text
HTTP/1.1 304 Not Modified
ETag: "9f2c4e7a1b3d5f6e8a0c2e4f6a8b0c1d3e5f7a9b1c3d5e7f9a1b3c5d7e9f1a3b"
```

#### Требования к скорости

Таймаут POS — 120 с на файл. Вызовы идут ночью, последовательно, не более 2 соединений.

### GET /pos/v1/external-ids — записи регистра внешних идентификаторов

#### Назначение

Возвращает записи регистра `POS_ВнешниеИдентификаторыPOS` — какие документы и справочники 1С созданы через API из POS и с каким `externalId`. Нужен в двух случаях: восстановить связи заказов, платежей, клиентов и заявок после аварийного восстановления сервера POS из резервной копии; найти «Заказ клиента» по номеру документа 1С при ручной привязке заказа администратором POS. Метод желательный: он не является условием первого запуска.

#### Когда вызывается и как часто

- Только при восстановлении после аварии (параметр `since` — дата резервной копии) и при ручной привязке заказа к документу 1С.
- При ручной привязке POS читает записи типа `Заказ` страницами по 500, не более 20 страниц.

#### Запрос

- Метод и путь: `GET /pos/v1/external-ids?since={дата}&type={тип}&limit={n}&cursor={c}`.
- Заголовки: `Authorization`, `X-POS-Client-Key`, `X-Request-Id`, `Accept: application/json`.

| Параметр | Тип | Обязательно | Описание |
|---|---|---|---|
| `since` | дата-время с `+06:00` | да | вернуть записи, созданные начиная с этого момента (по `ДатаСоздания` записи регистра) |
| `type` | строка | нет | тип объекта: `Заказ`, `Платеж`, `Клиент` или `ЗаявкаНаВозврат` (значения перечисления `POS_ТипыВнешнихОбъектов`) |
| `limit` | целое 1–1000 | нет | записей на странице, по умолчанию 1000 |
| `cursor` | строка | нет | непрозрачный ключ продолжения из предыдущей страницы |

Уточняется: при ручной привязке заказа POS может вызвать метод без `since` (нужны записи типа `Заказ` с начала). Как поступать в этом случае — согласуем при утверждении API.

#### Ответ

Код `200` — страница записей.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `items` | массив записей | да | не более `limit` и не более 1000 |
| `hasMore` | булево | да | `true`, если есть следующая страница |
| `cursor` | строка | да (может быть `null`) | ключ следующей страницы; `null` на последней |

Запись `items[]`:

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `externalId` | строка (UUID) | да | `ВнешнийИд` записи регистра |
| `objectType` | строка | да | `ТипОбъекта`: `Заказ`, `Платеж`, `Клиент`, `ЗаявкаНаВозврат` |
| `ref` | строка (GUID) | да | ссылка на документ или элемент справочника (`Объект`) |
| `number` | строка | да (может быть `null`) | номер документа или код справочника |
| `date` | дата-время | да (может быть `null`) | дата документа; для справочника — `null` |
| `deletionMark` | булево | да | пометка удаления объекта |

#### Ошибки

| HTTP-код | Код ошибки | Когда | Что делает POS |
|---|---|---|---|
| 400 | `POS_E_BAD_REQUEST` | неверный формат `since`, неизвестный `type`, `limit` вне диапазона, неверный `cursor` | сообщает администратору, не повторяет |
| 401, 403 | `POS_E_UNAUTHORIZED`, `POS_E_FORBIDDEN` | доступ | уведомляет администратора |
| 500 | `POS_E_INTERNAL` | исключение | повтор вручную |
| 503 | `POS_E_MAINTENANCE` | обслуживание | повтор вручную; при ручной привязке — «1С не ответила» |

#### Правила на стороне 1С

- Метод только читает регистр `POS_ВнешниеИдентификаторыPOS` и реквизиты связанных объектов (номер, дата, пометка удаления).
- Записи регистра не удаляются при пометке документа на удаление, поэтому помеченные объекты тоже возвращаются с `deletionMark: true`.
- Порядок выдачи — устойчивый (например, по `ДатаСоздания`, затем по `ВнешнийИд`), чтобы курсор не пропускал и не повторял записи.
- Полнота при приёмке: запрос с `since` = начало теста возвращает все объекты, созданные в ходе контрольного примера.

```text
Authorization: Basic <base64 от «pos_hs:пароль»>
X-POS-Client-Key: <ключ клиента>

```

При ручной привязке заказа на **все** страницы у POS есть не более 6 с, поэтому страница должна формироваться быстро (запрос к регистру с индексом по `ВнешнийИд` и отбором по типу). При восстановлении — таймаут 30 с на страницу.

### GET /pos/v1/catalog/{ref} — карточка товара одним вызовом (по желанию)

#### Назначение

Возвращает всё о товаре одним вызовом: реквизиты, характеристики, упаковки, штрихкоды, цены по видам цен и остатки по складам. Метод необязательный: делается после всех остальных методов и не является условием приёмки первой версии. Он полезен, если OData не публикуется (тогда это единственный способ получить цены и остатки по товару). Если метода нет, расширение отвечает `404`, и POS читает те же данные через OData.

По запросу — для одного товара (уточнение карточки). Регулярного опроса нет.

- Метод и путь: `GET /pos/v1/catalog/{ref}`.
- Заголовки: `Authorization`, `X-POS-Client-Key`, `X-Request-Id`, `Accept: application/json`.

| Параметр | Где | Тип | Обязательно | Описание |
|---|---|---|---|---|
| `ref` | путь | строка (GUID) | да | ссылка номенклатуры (`Ref_Key`) |

## А.3. Состав плана обмена «POS» и типы элементов выгрузки /changes

### Состав плана обмена и события регистрации

План обмена «POS» создаётся в расширении (один узел-получатель `POS`; «этот узел» — база 1С). Для всех объектов состава включена **авторегистрация**: изменения регистрирует сама платформа, обработчики событий типовой конфигурации расширение не переопределяет.

| Объект 1С (типово — уточнить) | Авторегистрация | Какие события регистрируются | Тип элемента в `/changes` |
|---|---|---|---|

### Правила выгрузки

1. **Ключ объекта.** У справочников и документов — `ref` = GUID ссылки в нижнем регистре. У набора записей регистра сведений — ключ набора (для штрихкодов — значение штрихкода). У `QrPaymentStatus` — `externalId` платежа (ключ записи `POS_ОплатыQR`). Коды, номера, артикулы и наименования ключами не являются.
2. **`dataVersion`.** Передаётся значение `ВерсияДанных` объекта «как есть», строкой. POS сравнивает его только на «равно / не равно» и не использует для упорядочивания. Если версия изменилась, а реплицируемые поля — нет, POS ничего не перезаписывает.
3. **Пометка удаления.** Установка и снятие пометки — обычный элемент типа объекта с `deletionMark: true` или `false`. POS ничего не удаляет физически: помеченный объект исчезает из каталога и поиска, но остаётся в истории заказов. Снятие пометки возвращает объект.
4. **Физическое удаление** объекта или очистка набора записей — элемент `ObjectDeletion` с типом объекта и ссылкой (ключом набора).
5. **Текущее состояние.** Объект выгружается целиком в текущем состоянии. Вложенные наборы (свойства `attributes`, телефоны `phones`, строки документов `lines`) передаются **полностью**, а не изменённой частью: POS заменяет набор целиком.
6. **Порядок.** Порядок внутри сообщения устойчивый: тип объекта, затем ссылка (ключ набора). Ссылки между объектами одного сообщения POS разрешает в любом порядке (неразрешённые откладывает до конца сообщения). Рекомендуемый порядок типов: единицы → склады → виды цен → номенклатура (группы и элементы) → характеристики → упаковки → штрихкоды → файлы картинок → документы установки цен → удаления → партнёры → контрагенты → соглашения → скидки → заказы → реализации → платёжные документы → возвраты → события QR.
7. **Размер страницы и номер сообщения.** Не более `limit` элементов (по умолчанию 1000, максимум 5000) и не более 20 с на формирование страницы; номер сообщения одинаков на всех страницах; курсор действует только внутри своего сообщения.
8. **Подтверждение только после применения.** POS применяет все страницы сообщения в одной транзакции и только после её фиксации вызывает `/changes/ack`. Регистрация снимается только по номеру (см. `/changes/ack`).
9. **Повторная выдача.** До подтверждения сообщение может выдаваться многократно; повторное применение безопасно (POS применяет данные по `ref` и пропускает неизменённое).
10. **Неизвестный тип.** Элемент неизвестного POS типа записывается в журнал синхронизации как предупреждение и пропускается; остальные элементы применяются. Новые типы добавляются только через согласованное изменение контракта.
11. **Типы без обработчика.** Если в POS обработка какого-то типа ещё не подключена, элемент пропускается, но подтверждение всё равно снимет его регистрацию. Поэтому после подключения обработки новых типов POS вызывает `/changes/reregister`.
12. **Форматы** — по разделу А.1: деньги и количества строками, даты с `+06:00`, GUID в нижнем регистре. Значение не по формату POS записывает как ошибку позиции и не применяет.
13. **Значения перечислений** (статусы заказов, виды штрихкодов и т. п.) передаются фактическими значениями вашей конфигурации (имя значения перечисления); пришлите их перечень — по нему POS строит соответствие.

### Товары и категории — `Catalog_Номенклатура`

Один тип элемента для товаров (`isFolder: false`) и групп номенклатуры (`isFolder: true`). Группы POS использует как **категории витрины** (дерево по `parentRef`); вид номенклатуры (`kindRef`) категорией не является.

| Поле | Тип | Обязательно | Описание | Объект 1С (типово) |
|---|---|---|---|---|
| `type` | строка | да | `Catalog_Номенклатура` | — |
| `ref` | строка (GUID) | да | ссылка | `Ссылка.УникальныйИдентификатор()` |
| `dataVersion` | строка | да | версия данных | `ВерсияДанных` |
| `deletionMark` | булево | да | пометка удаления | `ПометкаУдаления` |
| `isFolder` | булево | да | `true` — группа (категория) | `ЭтоГруппа` |
| `code` | строка | нет | код | `Код` |
| `description` | строка | да | наименование | `Наименование` |
| `fullName` | строка | нет | полное наименование | `НаименованиеПолное` |
| `sku` | строка | нет | артикул | `Артикул` |
| `parentRef` | строка (GUID) | нет | родительская группа (категория) | `Родитель` |
| `baseUnitRef` | строка (GUID) | нет | единица хранения | `ЕдиницаИзмерения` |
| `kindRef` | строка (GUID) | нет | вид номенклатуры | `ВидНоменклатуры` |
| `descriptionText` | строка | нет | описание простым текстом (форматированный текст — без разметки) | `Описание` |
| `imageFileRef` | строка (GUID) | нет | основная картинка; байты — `GET /pos/v1/images/{ref}` | `ФайлКартинки` |
| `isWeighted` | булево | нет | весовой товар | `Весовой` |

### Остатки — срез, в план обмена не входят

Регистры накопления остатков в план обмена **не включаются**: регистрация движений дала бы лавину записей. Остатки POS получает так:

- полный срез `Balance` по всем активным складам раз в 5–10 минут (по умолчанию 10) через OData: `ТоварыНаСкладах` (в наличии) и `СвободныеОстатки` (в резерве, в резерве под заказ) в разрезе «номенклатура, характеристика, склад» (типово — уточнить; вопрос Q-020 — допустимая свежесть данных и нагрузка на 1С);
- синхронную проверку `POST /pos/v1/check` при каждом подтверждении заказа (описана в группе методов заказа);
- при желании — `GET /pos/v1/catalog/{ref}` по одному товару.

Строка среза, которую ожидает POS: склад, номенклатура, характеристика (или пусто), в наличии, в резерве, свободный остаток (если 1С его не считает — POS считает «в наличии минус резерв»). Если ведётся учёт по сериям или назначениям, сообщите (вопрос Q-120): POS агрегирует остатки по складу и характеристике.

### Взаиморасчёты (долги клиентов) — срез, в план обмена не входят

Регистры взаиморасчётов (типово `РасчетыСКлиентами`, `РасчетыСКлиентамиПоДокументам`, `РасчетыСКлиентамиПоСрокам`) в план обмена **не включаются**. Долг клиента POS получает методом `GET /pos/v1/customers/{ref}/receivables` (описан в группе методов клиентов): раз в 30 минут по активным клиентам и по запросу при продаже в долг; запасной путь — `Balance` регистра взаиморасчётов через OData. Документы, которые меняют долг (реализации, оплаты, возвраты), при этом приходят в `/changes` как документы — для истории продаж, а не для расчёта долга.

Строка документа (`lines[]`, общая для реализаций и возвратов):

| Поле | Тип | Обязательно | Описание | Объект 1С (типово) |

| `variantRef` | строка (GUID) | нет | характеристика | `Характеристика` |
| `packagingRef` | строка (GUID) | нет | упаковка | `Упаковка` |

| `amount` | строка-деньги | нет | сумма строки | `Сумма` |
| `discountAmount` | строка-деньги | нет | сумма скидки строки | сумма автоматических и ручных скидок |
| `returnedQuantity` | строка-количество | нет | уже возвращено по строке (для реализации) | по документам возврата |

### Правила скидок — `Catalog_СкидкиНаценки`

В первой версии автоматические скидки рассчитывает **1С** (при проверке корзины и создании заказа); POS показывает перечень правил для справки (вопрос Q-015 — есть ли автоматические и накопительные скидки).

| Поле | Тип | Обязательно | Описание | Объект 1С (типово) |
|---|---|---|---|---|
| `type` | строка | да | `Catalog_СкидкиНаценки` | — |
| `ref` | строка (GUID) | да | ссылка | ссылка скидки |
| `dataVersion` | строка | да | версия данных | `ВерсияДанных` |
| `deletionMark` | булево | да | пометка удаления; помеченное правило POS считает неактивным | `ПометкаУдаления` |
| `code` | строка | нет | код | `Код` |
| `description` | строка | да | наименование («Скидка 3% от 50 000 сом») | `Наименование` |

Дополнительные поля (предложение, ждут согласования; POS их читает, если они есть, иначе показывает только наименование):

| Поле | Тип | Описание |
|---|---|---|
| `kind` | строка | `percent` (процент), `fixed_amount` (сумма) или `price_list` (вид цены) |
| `value` | строка | значение скидки: процент или сумма с точкой («3.00») |
| `isActive` | булево | правило действует |
| `appliesAutomatically` | булево | применяется автоматически |
| `validFrom`, `validTo` | дата-время | период действия |
| `conditions` | объект | условия: `minTotal` (строка-деньги, минимальная сумма заказа), `partnerRefs` (массив GUID партнёров) |

```json
{
  "type": "Catalog_СкидкиНаценки",
  "ref": "c3d4e5f6-0000-4000-8000-0000000000d1",
  "dataVersion": "AAAAAQAAAAA=",
  "deletionMark": false,
  "code": "000000003",
  "description": "Скидка 3% от 50 000 сом"
}
```

### Статусы QR-платежей — `QrPaymentStatus`

Событие оплаты по QR — изменение записи регистра расширения `POS_ОплатыQR`. POS применяет его по тем же правилам, что и ответ метода статуса QR (описан в группе методов оплаты); повторная доставка того же статуса ничего не меняет.

| Поле | Тип | Обязательно | Описание | Объект 1С |
|---|---|---|---|---|
| `type` | строка | да | `QrPaymentStatus` | — |
| `ref` | строка (UUID) | да | ключ записи — `externalId` платежа POS | `POS_ОплатыQR.ВнешнийИдПлатежа` |
| `externalId` | строка (UUID) | да | `externalId` платежа POS (то же значение) | `ВнешнийИдПлатежа` |
| `status` | строка | да | `pending`, `paid`, `expired` или `cancelled` | `Статус` |
| `reference` | строка | да | идентификатор QR или операции у банка, выданный при создании QR | `Референс` |

| `paidAt` | дата-время | нет | момент оплаты | `МоментОплаты` |
| `bankReference` | строка | нет | референс банка по зачислению | `РеференсБанка` |

### Удаления — `ObjectDeletion`

Физическое удаление объекта любого типа состава или очистка набора записей регистра сведений.

| Поле | Тип | Обязательно | Описание | Объект 1С (типово) |
|---|---|---|---|---|
| `type` | строка | да | `ObjectDeletion` | — |
| `objectType` | строка | да | тип удалённого объекта в нотации OData: `Catalog_…`, `Document_…`, `InformationRegister_…` (те же значения, что поле `type` элементов) | имя объекта метаданных |
| `ref` | строка | да | GUID ссылки удалённого объекта или ключ набора записей (для штрихкодов — значение штрихкода) | ссылка (из записи регистрации удаления) или ключ набора |

```json
{
  "type": "ObjectDeletion",
  "objectType": "Catalog_ХарактеристикиНоменклатуры",
  "ref": "a1b2c3d4-0000-4000-8000-000000000777"
}
```

### Что от вас нужно по плану обмена — кратко

1. Создать план обмена «POS» в расширении с составом из таблицы выше и авторегистрацией; узел-получатель `POS`.
2. Реализовать `/changes`, `/changes/ack`, `/changes/reregister` строго по правилам этого раздела (нумерация через `ВыбратьИзменения`, снятие регистрации только по номеру).
3. Сериализовать каждый тип элемента по таблицам полей; отсутствующие в вашей конфигурации реквизиты передавать как `null` и сообщить нам.
4. Проверить на тестовой копии: нумерацию `ВыбратьИзменения` для всех непронумерованных регистраций, доступ к таблицам изменений из запроса, работу `ВыбратьИзменения` для документов, заимствованных в расширение, поведение при отсутствии регистраций.
5. Прислать: перечень значений статусов заказов и состояний выполнения, выбранный вариант регистрации заказов (только из POS или все), признак того, можно ли включить `POS_ОплатыQR` в план обмена, сведения о характеристиках (индивидуальные или общие) и упаковках.
