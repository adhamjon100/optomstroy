# Приёмка: тестовая копия, контрольный пример, комплект поставки

## Тестовая копия базы и тестовые данные

### Что нужно

1. **Разработка и приёмка — только на копии рабочей базы.** Копия делается выгрузкой `.dt` или резервной копией СУБД и публикуется под отдельным именем, например `<база>-test`. Рабочая база не используется до подписания акта приёмки.
2. **Отдельные технические пользователи для копии** — тестовые `pos_hs` и `pos_integration` с другими паролями и другим ключом `X-POS-Client-Key`, чем в рабочей базе.
3. **Публикация копии по HTTPS** с доступом с тестового сервера POS: по локальной сети или через VPN-туннель.
4. **Для QR — тестовый режим банка,** если он есть (вопрос QR-2). Если его нет — пробная оплата минимальной суммы по отдельному согласованию с заказчиком.
5. **Копию обновляйте вместе с рабочей базой.** Каждое обновление типовой конфигурации сначала проверяется на копии (см. «Регрессия после обновлений типовой конфигурации» ниже).

### Обезличивание

- **Имена, телефоны и ИНН клиентов** в копии заменяются тестовыми, например «ООО Пример 1», `+996700000001`.
- **Исключение — 3–5 тестовых клиентов** с телефонами сотрудников заказчика, согласованными заранее. Они нужны для проверки поиска по телефону.
- **Данные плательщиков** из банковской интеграции, банковские реквизиты и персональные данные сотрудников в образцах, которые вы присылаете нам, не передаются.
- **Пароли и ключи** в протоколы, скриншоты и переписку не попадают.

### Какие данные должны быть в копии

| Что нужно в копии | Для чего |
|---|---|
| товары с характеристиками и без, с упаковками; весовые или метражные, если они у вас есть | первая загрузка и `/changes` (КП-2), проверка корзины (КП-7) |
| не менее 30 товаров с остатком и один товар, количество которого заведомо больше остатка | КП-7 |
| не менее двух складов и не менее двух видов цен | КП-3, КП-7 |
| тестовая характеристика, которую можно удалить | КП-3 |
| товар или клиент с автоматической скидкой 1С | КП-9 |
| клиенты с долгом и просрочкой, с лимитом долга, без отсрочки | КП-7, КП-14, проверка долга |
| клиент с долгом по двум и более документам | КП-14 |
| один клиент с двумя карточками на одном телефоне | проверка защиты от дублей клиентов (КП-5, КП-6) |
| телефоны тестовых клиентов в разных форматах (`0700…`, `+996700…`) | КП-5 |
| проведённые реализации по заказам | заявка на возврат (КП-16, КП-17) |
| картинки товаров | КП-18 |
| возможность провести реализацию по тестовому заказу и согласовать заказ и заявку | КП-10, КП-16, КП-17 |

Для наших автотестов пришлите обезличенные образцы (Q-040: образцы данных 1С):

- `$metadata`;
- 50–100 карточек номенклатуры с характеристиками;
- прайс;
- остатки;
- 10–20 клиентов.

## Порядок работ и этапы

| Этап | Что делает специалист 1С | Что делаем мы | Критерий завершения |
|---|---|---|---|
| 1. Сведения | отвечает на анкету и вопросы QR-1…QR-9, присылает `$metadata` и образцы | заменяем типовые имена на фактические, присылаем уточнённый контракт | согласован перечень объектов, полей и значений перечислений |
| 2. Подготовка | готовит тестовую копию, публикацию по HTTPS, пользователей, сеть до сервера POS | готовим тестовый сервер POS и набор запросов | `GET /health` с сервера POS отвечает 200 (КП-1) |
| 3. Чтение | план обмена, `/changes`, `/changes/ack`, `/changes/reregister`, `/check`, статусы заказов, поиск клиентов, долги, `/images`, `/health`; OData только на чтение | подключаем модуль интеграции, выполняем первую загрузку | каталог, цены, остатки, клиенты загружены, количество записей совпадает с 1С; КП-1…КП-5, КП-7, КП-18 пройдены |
| 4. Запись | `/orders`, `/orders/{uuid}/cancel`, `/customers`, `/payments`, `/returns`, регистр внешних идентификаторов, журнал запросов | проверяем защиту от дублей и обработку ошибок | КП-6, КП-8…КП-10, КП-14…КП-17, КП-19, КП-20 пройдены |
| 5. QR | `/payments/qr`, `/payments/{externalId}/status`, `/payments/{externalId}/qr/cancel`, регистр `POS_ОплатыQR` в плане обмена — если ваша интеграция с банком это умеет | проверяем оплату и отмену | КП-11…КП-13 пройдены |
| 6. Приёмка | передаёт комплект поставки | ставим расширение на копию строго по вашей инструкции, прогоняем весь контрольный пример, критерии по методам и замер нагрузки | подписан протокол приёмки |
| 7. Перенос в рабочую базу | устанавливает расширение в рабочую базу в окно обслуживания | переключаем сервер POS на рабочую базу | `GET /health` рабочей базы отвечает 200, первый заказ создан |

Методы QR включаются в POS только после того, как КП-11…КП-13 пройдены. До этого кассир подтверждает оплату по QR вручную.

## Контрольный пример

Контрольный пример выполняется на тестовой копии. Каждый шаг фиксируется в протоколе:

- запрос;
- ответ;
- что видно в 1С: номер документа, статус, скриншот формы.

Шаги КП-1, КП-2, КП-5, КП-18 и КП-19 выполняются **автоматически** нашей программой приёмки. Остальные шаги требуют действий в 1С или записи документов. Их выполняют запросами из нашего набора, а после подключения POS — сквозными сценариями из приложения.

| № | Что проверяем | Шаги | Ожидаемый результат |
|---|---|---|---|
| КП-1 | доступность и аутентификация | `GET /health` с верными пользователем и ключом; затем тот же запрос без `X-POS-Client-Key`. Автоматически | 200 со всеми полями (версии, `registrationBacklog`, `lastAckMessageNumber`, `serverTime`); без ключа — 401 без сведений о системе |
| КП-2 | полная выгрузка по плану обмена | `POST /changes/reregister`; чтение `/changes` всеми страницами до `hasMore=false`; два `GET` без подтверждения; `POST /changes/ack`; повтор подтверждения. Автоматически | все объекты состава пришли; два `GET` без подтверждения дают один `messageNumber`; повтор подтверждения — 200; после подтверждения `registrationBacklog` = 0 |
| КП-3 | изменение и удаление | изменить в 1С цену товара документом установки цен; удалить тестовую характеристику; затем `/changes` | изменение цен и элемент `ObjectDeletion` по характеристике — в следующем сообщении |
| КП-4 | изменение во время чтения | прочитать первую страницу; изменить в 1С товар с этой страницы; дочитать сообщение и подтвердить | изменённый товар приходит в **следующем** сообщении с новыми данными; изменение не потеряно |
| КП-5 | поиск клиента по телефону | `GET /customers?phone=…` в форматах `0700000001` и `+996700000001` для одного тестового клиента. Автоматически | обоими запросами найдена одна и та же карточка |
| КП-6 | создание клиента без дублей | `POST /customers` нового клиента; повтор с тем же `externalId`; затем другой `externalId` с тем же телефоном | 201; 200 без второй карточки; 409 `POS_E_DUPLICATE` с кандидатами |
| КП-7 | проверка корзины | `POST /check` по корзине из 30 строк, в одной строке количество больше остатка, `paymentMethod=credit`, клиент с долгом | 200 не дольше 3 с; в строке замечание `STOCK_INSUFFICIENT`; блок `receivables` с долгом и лимитом |
| КП-8 | создание заказа и защита от дублей | `POST /orders`; повтор того же запроса; затем 10 одновременных запросов с новым `externalId` | 201, заказ «Не согласован», без резерва, в комментарии `POS <uuid>`; повтор — 200 с тем же документом; на 10 запросов — один документ |
| КП-9 | автоматическая скидка | заказ с товаром или клиентом, на которые действует автоматическая скидка 1С | `recalculated=true` и суммы 1С в ответе |
| КП-10 | статус заказа | согласовать заказ из КП-8 в 1С; затем `GET /orders/{uuid}/status` и `/changes` | статус «согласован» в обоих ответах, без задержки на кэш |
| КП-11 | создание QR и оплата | `POST /payments/qr` по заказу; повтор; пробная оплата; `GET /payments/{externalId}/status`; `/changes` | 201; повтор — 200 с тем же `reference`; статус `paid` с суммой, временем и референсом банка; элемент `QrPaymentStatus` в `/changes` |
| КП-12 | один платёжный документ по QR | `POST /payments` для оплаченного платежа из КП-11, `kind=qr_bakai` | 200 «уже существует», если интеграция создала документ сама, иначе 201; в 1С ровно один документ поступления |
| КП-13 | отмена QR | второй QR; `/qr/cancel`; статус; повторная отмена | `cancelled`; статус `cancelled`; повтор отмены — 200 |
| КП-14 | оплата долга | `POST /payments` наличными в счёт долга с `allocations` по двум документам; повтор | ПКО с расшифровкой ровно по двум документам и суммам; повтор не создаёт второй ПКО |
| КП-15 | отмена заказа | создать второй заказ; `POST /orders/{uuid}/cancel` | 200, заказ отменён в 1С по вашим правилам |
| КП-16 | отказ в отмене отгруженного заказа | провести реализацию по первому заказу; затем `/orders/{uuid}/cancel` | 409 `POS_E_STATE`, документ в 1С не изменён |
| КП-17 | заявка на возврат | `POST /returns` на 1 шт. по реализации из КП-16; затем заявка на количество больше отгруженного; согласовать первую заявку в 1С и запросить статус | 201 `submitted`; 409 `POS_E_STATE`; после согласования — `accepted` |
| КП-18 | картинка товара | `GET /images/{ref}`; повтор с `If-None-Match`. Автоматически | 200 с `ETag`; повтор — 304 без тела |
| КП-19 | перечень объектов из POS | `GET /external-ids?since=<начало теста>`. Автоматически | все объекты КП-6…КП-17 с их `externalId`, ссылками и номерами |
| КП-20 | блокировка и неверный запрос | заблокировать заказ в 1С другим сеансом и вызвать `/orders/{uuid}/cancel`; отправить неверный JSON | 503 (или 423) `POS_E_LOCKED`; 400 `POS_E_BAD_REQUEST`; оба — в едином формате ошибки |

## Критерии приёмки по методам

| Метод | Критерий |
|---|---|
| `/health` | без аутентификации — только 401; с аутентификацией — все поля ответа |
| аутентификация | без `X-POS-Client-Key` — 401 при верном пароле; под пользователем OData запросы к HTTP-сервису отклоняются (401 или 403); под `pos_hs` запросы к OData отклоняются |
| `/changes`, `/changes/ack` | два `GET` без подтверждения дают один номер и все элементы; повтор подтверждения — 200 без изменений; 2 500 изменений читаются тремя страницами по 1000 и одним подтверждением, после него очередь пуста; `limit=10000` возвращает не более 5000 элементов |
| состав плана обмена | создание, изменение, пометка и удаление каждого объекта состава приходят в `/changes`; удаление тестовой характеристики приходит как `ObjectDeletion` |
| `/check` | корзина из 100 строк — не дольше 3 с; `STOCK_INSUFFICIENT` при количестве больше свободного остатка |
| `/orders` | 10 параллельных запросов — один документ; заказ открывается в 1С без ошибок проверки заполнения; резерва нет; поиск по `POS <uuid>` находит заказ; автоскидка даёт `recalculated=true`; после пометки удаления повтор — 200 и `deletionMark=true` |
| `/orders/{uuid}/cancel` | заказ с проведённой реализацией — 409 `POS_E_STATE`, документ не изменён; без реализаций — 200 |
| `/orders/status` | смена статуса в 1С сразу видна в ответе |
| `/customers` | поиск по разным форматам номера находит одну карточку; создание с телефоном существующего клиента — 409 с кандидатами; в 1С не попадают поля профиля приложения (год рождения, сфера деятельности, согласия) |
| `/customers/{ref}/receivables` | сальдо совпадает с отчётом «Задолженность клиентов» на тот же момент |
| `/payments` | повтор не создаёт второй документ; сумма документа равна `amount`; `allocations` отражены в расшифровке платежа; документ другого клиента или сумма больше остатка долга — 422 |
| `/payments/qr` | повтор при действующем QR — тот же `reference`; после истечения срока — новый; при недоступном банке — 503 `POS_E_QR_UNAVAILABLE` |
| `/payments/{externalId}/status` | после пробной оплаты — `paid` с суммой, временем и референсом; неизвестный `externalId` — 404; p95 не более 1 с на 100 вызовах |
| событие QR в `/changes` | оплата даёт элемент `QrPaymentStatus` в ближайшем сообщении; в 1С ровно один документ поступления |
| `/payments/{externalId}/qr/cancel` | отмена действующего QR — `cancelled`; отмена оплаченного — 200 `paid`; повтор — 200 |
| `/returns` | заявка на 3 шт. при отгруженных 2 — 409; согласование заявки в 1С даёт `accepted` |
| `/images` | повтор с `If-None-Match` — 304 без тела |
| формат | даты с `+06:00`; деньги и количества — строки по шаблонам; UUID в нижнем регистре; лишние поля не мешают |
| ошибки | временные ошибки и ошибки данных различаются кодом и HTTP-статусом |
| безопасность | код расширения не использует `Выполнить()` и запросы, собранные из входных данных |
| поставка | расширение устанавливается по вашей инструкции без консультаций |

## Нагрузка

Замер выполняется на тестовой копии после этапа «Чтение».

| Замер | Как | Порог |
|---|---|---|
| полный срез остатков | 5 повторов, p50 и p95 | не более 120 с; срез одного склада — не более 30 с |
| срез цен | 5 повторов, p50 и p95 | фиксируется в протоколе |
| страница номенклатуры | 5 повторов, p50 и p95 | фиксируется в протоколе |
| `POST /check` на 30 строк | 5 повторов, p50 и p95 | не более 3 с |
| `GET /payments/{externalId}/status` | 100 вызовов | p95 не более 1 с |

Для каждого замера в протокол записываются загрузка процессора сервера 1С и максимальная длительность блокировок. Если срез остатков идёт дольше 30 секунд или растут блокировки, интервалы опроса увеличиваются (для файловой базы остатки — не чаще раза в 15 минут). Итоговые интервалы записываются в протокол.

## Регрессия после обновлений типовой конфигурации

1. **Заказчик заранее сообщает об обновлении** — предлагаем за 3 рабочих дня (Q-126: обновления и окно обслуживания). На время обновления POS принимает `POS_E_MAINTENANCE` и `POS_E_LOCKED` как временные ошибки и повторяет запросы позже.
2. **Обновление сначала применяется на тестовой копии.** Затем проверяется:
  - расширение применяется без ошибок применимости;
  - `GET /health` отвечает, `configurationVersion` — новый релиз;
  - `/changes` возвращает тестовое изменение;
  - `POST /orders` создаёт тестовый заказ;
  - `POST /check` отвечает.
3. **Только после успешной проверки обновляется рабочая база.** Если расширение после обновления не применяется, обновление рабочей базы откладывается до исправления расширения.
4. **Если расширение пришлось изменить,** выпускается новая версия `.cfe` с записью в журнале изменений, а `extensionVersion` в `/health` увеличивается.

## Комплект поставки

1. **Файл расширения `.cfe`** и его версия. Она совпадает с `extensionVersion` в `/health`.
2. **Инструкция простым языком с ожидаемыми результатами:**
  - установка расширения;
  - публикация HTTP-сервиса и OData;
  - создание пользователей и роли;
  - заполнение констант `POS_НастройкиPOS`;
  - проверка `curl`-запросом к `/health`.
3. **Описание API в вашей реализации:** перечень фактических имён объектов, реквизитов и значений перечислений. Перечисления: статусы заказов, состояния выполнения, статусы заявок на возврат, хозяйственные операции платёжных документов. Здесь же — описание отличий от контракта, если они есть.
4. **Журнал изменений расширения.** Для каждой версии: номер, дата, что изменено, совместима ли версия с API `v1`.
5. **Набор тестовых запросов** (наш, дополненный вами) и заполненный протокол контрольного примера.

## Что мы предоставим специалисту

1. **Этот документ.**
2. **Машинный контракт `onec-http-service.v1.yaml`** (OpenAPI 3.0): все 21 операция, схемы запросов и ответов, коды ошибок, правила защиты от дублей и повторов по каждому методу. Версия 1.0.0 — черновик для согласования. Части с пометкой `x-status: proposed` — предмет согласования с вами: их не реализуют как окончательные, пока они не утверждены. После ваших ответов на анкету мы выпустим уточнённую версию.
3. **Примеры запросов и ответов** — набор файлов `fixtures/*.json`: успешные ответы и ошибки по каждому методу на синтетических данных. Каждый пример проверен по схеме контракта.
4. **Перечень объектов и полей для OData** только на чтение — `odata-allowlist.yaml`.
5. **Стенд-эмулятор HTTP-сервиса** — программа, которая отвечает на `/pos/v1/*` так, как ожидает POS, на тех же синтетических данных. Что на нём видно:
  - защита от дублей по `externalId`;
  - смена статусов заказа;
  - QR от `pending` до `paid`;
  - поиск и создание клиентов, долги, заявки на возврат;
  - по нему удобно сверять поведение вашей реализации; эмулятор работает только в тестовом режиме.
6. **Тестовая программа приёмки** (`scripts/onec_acceptance.ts`). Она выполняет автоматические шаги КП-1, КП-2, КП-5, КП-18 и КП-19 против вашей тестовой копии через тот же клиент, которым пользуется сервер POS. Протокол пишется в Markdown в виде «запрос → ответ → ожидание → итог», без паролей и ключей. Шаги, которые требуют действий в 1С, попадают в протокол как «вручную» с ожидаемым результатом. Запись в план обмена тестовой копии (перерегистрация в КП-2) программа выполняет только с явного разрешения.
