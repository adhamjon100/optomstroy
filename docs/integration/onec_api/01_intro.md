# Введение: что нужно сделать в 1С

Документ адресован программисту 1С заказчика. Он отвечает на вопрос «что вам нужно и какие API сделать» для кассовой системы «Оптомстрой POS». Магазин оптовый: сантехника и стройматериалы, Кыргызстан, валюта — сом (KGS).

Конфигурация 1С заказчика нам пока неизвестна (вопрос Q-010: конфигурация, релиз, платформа, тип базы). Поэтому имена объектов 1С в документе даны так, как они называются в типовых «Управление торговлей 11», «Комплексная автоматизация 2» и ERP. Такие имена помечены «типово — уточнить». Если в вашей базе объект называется иначе, сообщите фактическое имя (см. раздел «Анкета: что нам нужно знать о вашей 1С»). Доступа к вашей базе у нас нет, и в ней мы ничего не проверяли.

## Краткое содержание

**Что нужно сделать на стороне 1С:**

1. **Ответить на анкету** о вашей 1С (раздел «Анкета: что нам нужно знать о вашей 1С») до начала разработки. От ответов зависят имена объектов во всех методах.
2. **Подготовить тестовую копию базы** с обезличенными данными. Опубликовать её по HTTPS под отдельным именем и создать двух технических пользователей: для HTTP-сервиса и для OData только на чтение.
3. **Сделать расширение конфигурации «OptomstroyPOS»**: назначение «Адаптация», префикс объектов `POS_`. Типовая конфигурация не меняется и остаётся на поддержке.
4. **Создать в расширении HTTP-сервис** `POS_HTTPСервисPOS` с корневым URL `pos` и методами `/pos/v1/*`: 21 операция по 20 адресам, перечень — ниже.
5. **Создать план обмена «POS»** с авторегистрацией изменений нужных объектов. Изменения выдаются страницами, регистрация снимается только после подтверждения POS.
6. **Создать служебные объекты расширения:**
  - регистр сведений `POS_ВнешниеИдентификаторыPOS` — защита от дублей;
  - регистр сведений `POS_ОплатыQR` — оплаты по QR;
  - журнал запросов `POS_ЖурналЗапросовPOS` (желательно);
  - роль `POS_ИнтеграцияPOS`;
  - константы `POS_НастройкиPOS`;
  - общий модуль `POS_Сервер`.
7. **Опубликовать стандартный OData только на чтение** с ограниченным составом объектов. Он нужен для первой загрузки справочников и для регулярного чтения срезов цен и остатков. Если вы сделаете для срезов отдельные методы HTTP-сервиса, OData для них не понадобится (Q-319). Если OData публиковать нельзя, сообщите.
8. **Пройти приёмку на тестовой копии** по контрольному примеру из 20 шагов и критериям по каждому методу (раздел «Приёмка»).
9. **Передать комплект поставки:**
  - файл расширения `.cfe`;
  - инструкцию по установке и публикации;
  - перечень фактических имён объектов и значений перечислений;
  - журнал изменений расширения.

### Перечень методов HTTP-сервиса

Базовый адрес — `https://<сервер-1С>/<публикация>/hs/pos/v1/…`. Сегмент `hs` типовой — уточнить по вашей публикации.

| № | Метод и путь | Что делает | Важность |
|---|---|---|---|
| 1 | `GET /pos/v1/health` | проверка доступности, версии API и расширения, очередь регистраций | обязательно |
| 2 | `GET /pos/v1/changes` | страница сообщения обмена по плану обмена «POS» | обязательно |
| 3 | `POST /pos/v1/changes/ack` | подтверждение полного применения сообщения, снятие регистрации по номеру | обязательно |
| 4 | `POST /pos/v1/changes/reregister` | полная перерегистрация состава плана обмена | обязательно |
| 5 | `POST /pos/v1/check` | проверка корзины: цена, свободный остаток, долг и лимит клиента | обязательно |
| 6 | `POST /pos/v1/orders` | создать «Заказ клиента» в статусе «Не согласован», без резерва | обязательно |
| 7 | `POST /pos/v1/orders/{uuid}/cancel` | отменить заказ, созданный из POS | обязательно |
| 8 | `GET /pos/v1/orders/{uuid}/status` | статус одного заказа | обязательно |
| 9 | `POST /pos/v1/orders/status` | статусы до 200 заказов одним запросом | обязательно |
| 10 | `GET /pos/v1/customers?phone=…` | поиск клиентов по телефону | обязательно |
| 11 | `POST /pos/v1/customers` | создать клиента без дублей по телефону | обязательно (правила создания — Q-025) |
| 12 | `GET /pos/v1/customers/{ref}/receivables` | долг клиента: сальдо, просрочка, документы, лимит и отсрочка | обязательно |
| 13 | `POST /pos/v1/payments` | создать ПКО или поступление безналичных | обязательно |
| 14 | `POST /pos/v1/payments/qr` | создать динамический QR через вашу интеграцию с банком | обязательно, если интеграция с банком это позволяет (Q-014) |
| 15 | `GET /pos/v1/payments/{externalId}/status` | статус оплаты по QR | обязательно, если интеграция с банком это позволяет (Q-014) |
| 16 | `POST /pos/v1/payments/{externalId}/qr/cancel` | отменить действующий QR | обязательно, если интеграция с банком это позволяет (Q-014) |
| 17 | `POST /pos/v1/returns` | создать заявку на возврат на основании реализации | обязательно, если 1С принимает такие заявки (Q-018) |
| 18 | `GET /pos/v1/returns/{uuid}/status` | статус заявки на возврат | обязательно, если 1С принимает такие заявки (Q-018) |
| 19 | `GET /pos/v1/images/{ref}` | файл картинки товара с `ETag` и ответом 304 | обязательно |
| 20 | `GET /pos/v1/external-ids` | перечень объектов, созданных из POS (для восстановления после сбоя сервера POS) | желательно |
| 21 | `GET /pos/v1/catalog/{ref}` | карточка товара одним вызовом | опционально, после всех остальных; не условие приёмки |

`{uuid}` в путях заказов и заявок на возврат — это `externalId` объекта POS. `{externalId}` в путях оплат — `externalId` платежа POS. `{ref}` — ссылка объекта 1С (GUID в нижнем регистре).

Точные пути, поля, типы и коды ответов заданы в машинном контракте `onec-http-service.v1.yaml` (формат OpenAPI 3.0). Он передаётся вместе с этим документом и является источником истины. Версия контракта 1.0.0 — черновик для согласования с вами. Части с пометкой `x-status: proposed` мы согласуем вместе с вами до того, как вы начнёте их реализовывать.

## Как устроена система

### Схема

```text
  Продавец, кассир,                      Покупатель
  администратор магазина                 (мобильное приложение)
  (касса Windows, планшет, телефон)
            |                                   |
            +-----------------+-----------------+
                              |  HTTPS, API приложения
                              v
          +---------------------------------------------+
          |  Сервер POS (backend)                       |
          |  - модуль интеграции с 1С                   |
          |  - очередь отправки в 1С (outbox)           |
          |  - копия данных 1С только для чтения        |
          +---------------------------------------------+
                              |
                              |  HTTPS (TLS 1.2+), только из локальной
                              |  сети магазина или через VPN.
                              |  Все вызовы начинает backend.
                              v
          +---------------------------------------------+
          |  1С заказчика                               |
          |  - расширение «OptomstroyPOS»:              |
          |    HTTP-сервис /hs/pos/v1/*,                |
          |    план обмена «POS», регистры POS_*        |
          |  - стандартный OData, только чтение         |
          |  - ваша интеграция с банком (QR)            |
          +---------------------------------------------+
```

### Кто инициирует вызовы

- **Вызывает API 1С только backend** (сервер POS) под отдельным пользователем 1С. Приложения на кассах и телефонах к 1С не обращаются никогда. Люди API напрямую тоже не вызывают.
- **1С не вызывает POS.** В основном варианте 1С только отвечает на запросы backend. Исключение — отдельный вариант «1С вызывает POS» (описан ниже), он в этот запрос не входит.
- **База 1С не публикуется в интернет.** HTTP-сервис и OData должны быть доступны только с адреса сервера POS:
  - в локальной сети магазина;
  - или из подсети VPN-туннеля, который поднимает сторона магазина.

| Поток данных | Кто начинает | Как и как часто |
|---|---|---|
| Каталог, характеристики, упаковки, штрихкоды, склады, виды цен, клиенты, соглашения, скидки, документы продаж и оплат из 1С в POS | backend | `GET /changes` по плану обмена, по умолчанию раз в 5 минут. После применения всех страниц — `POST /changes/ack` |
| Первая загрузка справочников, срезы цен и остатков | backend | стандартный OData только на чтение, страницами по 1000 записей. Тяжёлые выгрузки — ночью |
| Проверка корзины при оформлении заказа | backend | `POST /check` синхронно, пока продавец ждёт ответа |
| Заказы, оплаты, новые клиенты, заявки на возврат из POS в 1С | backend, из очереди отправки | `POST /orders`, `/payments`, `/customers`, `/returns`. При недоступности 1С — повтор позже с тем же `externalId` |
| Статусы заказов и заявок на возврат | backend | `POST /orders/status` пакетами до 200 раз в 5 минут, плюс изменения из `/changes` |
| Оплата по QR | backend | создание и отмена QR — синхронно. Статус — опрос каждые 5 секунд, пока QR на экране, плюс событие в `/changes` |
| Картинки товаров | backend | `GET /images/{ref}` ночью, только изменившиеся файлы |

### Где истина

- **1С — источник истины** для каталога, характеристик, цен, складов, остатков, клиентов, соглашений, долгов, реализаций и возвратов. Backend держит их копию только для чтения.
- **В POS создаются** заказы, оплаты, новые клиенты и заявки на возврат. После записи в 1С истиной становится документ 1С: его статус, суммы и пометка удаления.
- **Заказ продавца и заказ покупателя.** Покупатель может оформить заказ сам в приложении. Для 1С это тот же метод `POST /orders` и тот же «Заказ клиента» в статусе «Не согласован», который согласует магазин.

### Вариант «1С вызывает POS» (не входит в этот запрос)

Этот вариант нужен, только если ни локальная сеть, ни VPN-туннель невозможны (вопрос Q-031: как связать сервер POS и 1С). Тогда направление вызовов меняется:

- Регламентное задание расширения (имя по нашему предложению — `POS_ОбменСPOS`) по расписанию само обращается к серверу POS. Адрес — `https://api.<домен>/api/v1/integrations/onec/*`.
- Методы этого варианта: `changes`, `snapshots/{entity}`, `order-status`, `outbox`, `outbox/{outboxId}/ack`, `ping`.
- Аутентификация — отдельный технический токен в заголовке `Authorization: Bearer`.
- Содержимое объектов то же, что в методах этого документа. Меняется только направление вызова и обёртка пакета.

Ограничения варианта:

- синхронная проверка корзины невозможна, поэтому все заказы оформляются по последним загруженным данным;
- ручной запуск синхронизации из POS недоступен.

Если этот вариант понадобится, мы пришлём для него отдельное описание.

## Что API должно делать

1. **Отдавать изменения** нужных объектов по плану обмена «POS»: создание, изменение, пометку удаления и физическое удаление. Изменения отдаются страницами. Регистрация снимается только по номеру подтверждённого сообщения.
2. **Быстро проверять корзину** (метод ничего не записывает):
  - актуальную цену по виду цены или соглашению клиента;
  - свободный остаток по складу с учётом резервов;
  - долг и лимит клиента;
  - по запросу — итог с автоматическими скидками 1С.
3. **Создавать «Заказ клиента»** типовыми процедурами заполнения: статус «Не согласован», строки «К обеспечению», без резерва. Документ проводится в той же транзакции. Если суммы пересчитаны, ответ сообщает об этом.
4. **Отменять заказ**, если по нему нет проведённых реализаций. Отдавать статусы заказов без кэширования.
5. **Искать клиентов по телефону** с нормализацией номера. Создавать клиента, только если другого клиента с тем же телефоном нет.
6. **Отдавать долг клиента**: сальдо, просрочку, детализацию по документам, лимит и отсрочку. Сальдо должно совпадать с отчётом «Задолженность клиентов».
7. **Создавать платёжные документы**: ПКО для наличных, поступление безналичных для QR. Основание — заказ или долг клиента; оплата долга распределяется по документам.
8. **Через вашу интеграцию с банком**:
  - создавать динамический QR на сумму заказа;
  - сообщать об оплате;
  - отменять QR;
  - не создавать второй платёжный документ, если интеграция при зачислении уже создала свой.
9. **Создавать заявку на возврат** на основании реализации и сообщать её статус.
10. **Отдавать файлы картинок товаров** с `ETag`. Если файл не изменился — отвечать 304.
11. **Защищать каждую запись от дублей** по `externalId`. Повтор запроса возвращает уже созданный объект и не создаёт второй (раздел «Общие требования к API»).
12. **Отдавать ошибки в едином формате** и различать временные ошибки и ошибки данных.

## Чего API делать не должно

- **Не менять справочники и цены 1С.** Номенклатура, характеристики, цены, склады и скидки — только чтение. Единственное исключение — создание нового клиента.
- **Не создавать документы, которые оформляют сотрудники в 1С**: реализации, документы возврата товаров, возврат денег, корректировки долга.
- **Не ставить резерв при создании заказа.** Резерв ставит менеджер при согласовании.
- **Не принимать от вызывающей стороны произвольные имена объектов, полей или текст запросов.** Никакой «универсальной записи», никаких `Выполнить()` и запросов, собранных из входных данных.
- **Не давать пользователям интеграции прямых прав записи.** Запись выполняет только код расширения в привилегированном режиме, после проверки ключа клиента и схемы входных данных.
- **Не передавать персональные данные плательщика** из банковской интеграции: имя, счёт, телефон.
- **Не проверять права пользователей POS.** Кто из сотрудников что может делать, проверяет backend. Повторное подтверждение сотрудником (step-up) тоже выполняет backend, например при ручном подтверждении оплаты. Для 1С все вызовы приходят от одного технического пользователя.
- **Не публиковать базу в интернет.** Не публиковать веб-клиент наружу и не открывать входящие порты из интернета.

## Объём работ по этапам

| Этап | Что делает специалист 1С | Что делаем мы | Результат |
|---|---|---|---|
| 1. Сведения | отвечает на анкету и вопросы по QR, присылает `$metadata` и обезличенные образцы данных | заменяем типовые имена на фактические, присылаем уточнённый контракт | согласованный перечень объектов и полей |
| 2. Подготовка | готовит тестовую копию, публикацию по HTTPS, пользователей, сеть до сервера POS | готовим тестовый сервер POS и набор запросов | `GET /health` отвечает с сервера POS |
| 3. Чтение | план обмена, `/changes`, `/changes/ack`, `/changes/reregister`, `/check`, статусы заказов, поиск клиентов, долги, `/images`, `/health`; публикация OData только на чтение | подключаем модуль интеграции, выполняем первую загрузку | каталог, цены, остатки и клиенты загружены, количества сходятся с 1С |
| 4. Запись | `/orders`, `/orders/{uuid}/cancel`, `/customers`, `/payments`, `/returns`, регистр внешних идентификаторов, журнал запросов | проверяем защиту от дублей и обработку ошибок | заказы и оплаты создаются без дублей |
| 5. QR | `/payments/qr`, `/payments/{externalId}/status`, `/payments/{externalId}/qr/cancel`, регистр `POS_ОплатыQR` в плане обмена — если ваша интеграция с банком это умеет | проверяем оплату и отмену | пробная оплата проходит |
| 6. Приёмка | передаёт комплект поставки | прогоняем контрольный пример, критерии по методам и замер нагрузки | подписанный протокол приёмки |
| 7. Перенос в рабочую базу | устанавливает расширение в рабочую базу в окно обслуживания | переключаем сервер POS на рабочую базу | запуск |

Методы `/external-ids` и `/catalog/{ref}` делаются после основных. `/external-ids` желателен к запуску, `/catalog/{ref}` — нет.

**Если интеграция с банком не умеет нужного.** Если она не умеет создавать динамический QR или не узнаёт о зачислении (вопросы QR-3, QR-4), методы QR не делаются. Тогда POS показывает статический QR магазина, а кассир подтверждает оплату вручную. Платёжный документ в обоих случаях создаёт метод `/payments`.

**Если API задерживается.** Режим «только чтение через OData, заказы вводятся в 1С вручную» в текущей версии POS не выбран и не реализован. Если API задерживается, владелец магазина решает одно из двух:

- ждать API (запуск сдвигается);
- заказать доработку такого временного режима.

Стандартный OData только на чтение в любом случае остаётся способом первой загрузки и чтения срезов.
