# Программа проверки API 1С: инструкция программисту 1С

**Оптомстрой POS · версия 1.1 от 20.11.2026 · программа проверки 1.1.0 · контракт `onec-http-service` 1.2.0, «Требования к API 1С» 1.2.1 (требования — как в 1.2)**

**Кому.** Программисту 1С магазина «Оптомстрой», который делает расширение «OptomstroyPOS» по «Требованиям к API 1С» и контракту `onec-http-service` 1.2.0.

**Коротко.** Программа сама вызывает методы вашего HTTP-сервиса на тестовой копии базы, сверяет каждый ответ с контрактом и «Требованиями» и пишет протокол «запрос → ответ → результат». В протоколе нет паролей и ключа, персональные данные скрыты. Протокол — вам и нам: по нему видно, что уже сделано по контрольному примеру (раздел 8.3 «Требований»).

## 1. Зачем эта программа

1С — главная учётная система. Сервер POS работает с ней днём, в момент продажи: создаёт «Заказ клиента», проводит оплаты (в том числе QR через 1С), создаёт заявки на возврат, проверяет цены и остатки корзины (`/check`), получает каталог по плану обмена «POS» (`/changes`), читает долги клиентов, картинки и перечень своих объектов (`/external-ids`). Если 1С недоступна, POS копит запросы записи в очереди и отправляет их позже с тем же `externalId`.

Программа показывает, правильно ли ваше расширение отвечает, ещё до совместной приёмки. Ошибки формата (BOM, GUID, даты, деньги, тело ошибки) и ошибки защиты от дублей видны сразу, с подсказкой, что исправить в 1С.

Что проверяется:

- **обязательные методы** контракта 1.2.0 и «Требований» (раздел 6): связь и доступ, `/health`, план обмена (`/changes`, `/changes/ack`, `/changes/reregister`), проверка корзины `/check`, заказы (создание, статус, статусы пакетом, отмена), клиенты (поиск по телефону, создание, долг), оплаты `/payments`, картинки. Нет такого метода — **ОШИБКА** «МЕТОДА НЕТ … метод обязателен» с разделом «Требований» и этапом работ (раздел 8.2): если этап ещё не начат, ошибка уйдёт, когда метод появится;
- **QR-оплата через 1С** (`/payments/qr`, статус, отмена) — только если ваша интеграция с банком умеет создавать QR и узнавать о зачислении («Требования» 7.13). Нет метода — «МЕТОДА НЕТ», это не ошибка;
- **заявки на возврат** (`/returns`, статус заявки) — обязательны, если 1С принимает такие заявки извне (таблица раздела 6 «Требований», Q-018, вопрос 77 раздела 10). Нет метода — «МЕТОДА НЕТ», не ошибка; если 1С их не принимает — сообщите ответом на вопрос 77: передача заявок в POS останется выключенной;
- **по желанию**: карточка товара `/catalog/{ref}` и перечень `/external-ids` (он желателен к запуску — нужен для ручной привязки заказа). Нет метода — «МЕТОДА НЕТ», не ошибка; если метод есть — он проверяется полностью.

Что программа не проверяет: код расширения (`Выполнить()`, запросы из входных данных), установку по вашей инструкции, OData, нагрузку по разделу 8.5 (программа только записывает время ответа). Шаги контрольного примера, которые требуют действий в 1С (согласовать заказ, провести реализацию, пробная оплата QR в банке), программа перечисляет в конце протокола — их выполняют вручную.

## 2. Что в архиве

Архив `Optomstroy_Proverka_API_1C_1.1.0.zip` (около 33 МБ). Внутри одна папка `Optomstroy_Proverka_API_1C_1.1.0`:

| Файл или папка | Что это |
|---|---|
| `Proverka_API_1C.cmd` | запуск проверки (без записи в базу) |
| `Proverka_API_1C_zapis.cmd` | запуск проверки с записью тестовых объектов (раздел 7) |
| `ЧИТАЙ_МЕНЯ.txt` | краткая памятка на одну страницу |
| `nastrojki.primer.json` | пример файла настроек |
| `SHA256SUMS.txt` | контрольные суммы всех файлов папки |
| `runtime\node.exe` | Node.js v24.11.1 — официальная сборка с цифровой подписью OpenJS Foundation |
| `runtime\LICENSE`, `runtime\ИСТОЧНИК_ЛИЦЕНЗИИ.txt` | лицензия Node.js и откуда взят её текст |
| `programma\` | сама программа (текст на JavaScript — его можно открыть и прочитать), контракт 1.2.0 и 59 образцов JSON для демо |

Ничего устанавливать не нужно. Программа не пишет в реестр, не ходит в интернет, не обновляется сама и никуда не отправляет данные: она обращается только к адресу вашей публикации. Целостность файла можно проверить командой `certutil -hashfile runtime\node.exe SHA256` и сравнить с `SHA256SUMS.txt`.

## 3. Где запускать

- **Только против тестовой копии базы** с опубликованным расширением («Требования» 8.1). Режим записи (`--allow-write`) на рабочей базе запускать нельзя: он создаёт объекты и подтверждает сообщения плана обмена.
- **Компьютер с Windows 10 или 11 в сети магазина**, с адреса которого разрешён доступ к тестовой публикации. По «Требованиям» (раздел 4.2) публикация доступна только из локальной сети магазина, с адреса сервера POS или из подсети VPN-туннеля. Поэтому запускайте программу на компьютере тестовой системы POS или на компьютере, адрес которого вы на время проверки разрешили для тестовой публикации.
- Для проверки «с другого компьютера доступа нет» нужен второй компьютер сети магазина — на нём программа запускается отдельно (раздел 8, M2).

Что нужно подготовить:

- адрес тестовой публикации до `/hs`, например `https://srv-1c/ut_test/hs`;
- пользователь `pos_hs` и его пароль (или JWT), ключ клиента `X-POS-Client-Key`;
- если сертификат публикации выдан внутренним центром — файл корневого сертификата в формате PEM (текст, начинается с `-----BEGIN CERTIFICATE-----`);
- для полной проверки — данные копии из раздела 8.1 «Требований»: товары с остатком, склад, вид цены, клиент с долгом и соглашением в долг, картинка товара. Программа берёт их из `/changes`; можно указать GUID в разделе `refs` файла `nastrojki.json`.

## 4. Первый запуск по шагам

1. Если архив пришёл по почте или из интернета: щёлкните его правой кнопкой → «Свойства» → отметьте «Разблокировать» (если такая отметка есть) → «ОК». Так Windows не будет останавливать запуск.
2. Распакуйте архив: правая кнопка → «Извлечь все…». Папка может быть любой, пробелы и русские буквы в пути допустимы. Не запускайте программу из окна просмотра архива — сначала распакуйте.
3. Для знакомства можно сначала запустить демо: откройте папку, в адресной строке Проводника наберите `cmd` и нажмите Enter, в открывшемся окне наберите `Proverka_API_1C.cmd --demo`. Демо занимает несколько секунд: встроенный имитатор на образцах JSON, без сети и паролей, протокол помечен «ДЕМО». Это не ваша 1С.
4. Дважды щёлкните `Proverka_API_1C.cmd`.
5. При первом запуске программа задаст вопросы (Enter — значение в квадратных скобках):

```
Проверка API 1С (расширение OptomstroyPOS) 1.1.0 — контракт 1.2.0, «Требования к API 1С» 1.2.1; сборка 0123456789ab
Файл настроек не найден. Ответьте на вопросы (Enter — значение в скобках).
1) Адрес публикации до /hs, например https://srv-1c/ut_test/hs:
2) Пользователь [pos_hs]:
3) Вход: 1 — пароль (Basic), 2 — JWT [1]:
4) Файл корневого сертификата (.pem), если сертификат выдан внутренним центром; Enter — не нужен:
Пароль пользователя pos_hs (ввод скрыт):
Ключ клиента X-POS-Client-Key (ввод скрыт):
Сохранить настройки (без пароля и ключа) в nastrojki.json? [Д/н]:
Режим: только чтение. Проверку записи запускайте с --allow-write (или Proverka_API_1C_zapis.cmd).
```

6. Путь к файлу сертификата можно вставить как есть, в кавычках («Копировать как путь» в Проводнике): кавычки программа снимет. Сертификат действует уже в этом запуске. При вводе пароля и ключа символы на экране не видны — так и должно быть. Ключ и JWT — латиницей: если набрать их в русской раскладке, программа сразу скажет об этом (код 2).
7. Программа выполняет проверки и показывает ход на экране. Иногда она задаёт вопросы или просит сделать действие в 1С (раздел 8).
8. В конце — итог («Итог: ошибок нет» или «Итог: ошибки — N»), пути к файлам протокола и просьба нажать любую клавишу.
9. Откройте протокол `.html` в браузере, прочитайте раздел «Что исправить», исправьте и запустите проверку снова.

Следующие запуски берут адрес и пользователя из `nastrojki.json`; пароль и ключ спрашиваются каждый раз. Изменить настройки — откройте `nastrojki.json` в Блокноте или удалите его: тогда вопросы будут заданы снова.

**Пароль, ключ и JWT.** В командной строке они не принимаются — только скрытый ввод или файл. Чтобы не вводить их каждый раз, положите каждый секрет в отдельный текстовый файл (одна строка) и укажите **путь к файлу** в `nastrojki.json`: `passwordFile`, `clientKeyFile`, `tokenFile` (сам пароль туда не пишется). В путях пишите прямую черту или две обратные: `"C:/proverka/parol.txt"` или `"C:\\proverka\\parol.txt"` — одна обратная черта в JSON — ошибка. Храните такие файлы вне папки программы, не пересылайте их и удалите после проверки. Программа сама секреты на диск не пишет, на экран и в протокол не выводит; в сообщениях об ошибках настроек она не повторяет то, что вы ввели.

## 5. Режимы и флаги

| Режим | Как запустить | Что делает |
|---|---|---|
| Только чтение | `Proverka_API_1C.cmd` | только запросы GET; в базе ничего не меняется |
| С записью | `Proverka_API_1C_zapis.cmd` (то же, что `Proverka_API_1C.cmd --allow-write`) | создаёт тестовые объекты «ПРОВЕРКА POS», вызывает `/check` и подтверждает сообщения плана обмена; перед первой записью просит подтверждение (раздел 7) |
| Демо | `Proverka_API_1C.cmd --demo` | прогон против встроенного имитатора на образцах JSON — посмотреть, как выглядит проверка и протокол |
| Нет доступа с другого компьютера | `Proverka_API_1C.cmd --expect-no-access` на другом компьютере сети | пароль и ключ не нужны; «ПРОЙДЕНО» — доступа нет, как требует раздел 4.2 «Требований» |

Флаги (все — `Proverka_API_1C.cmd --help`):

- `--checks A,C,PAY` — только эти группы или проверки (`A1,C2`); нужные для них проверки добавятся сами (например, для `PAY1` — создание тестового клиента K1, для `K8` — чтение `/changes`). Если все выбранные проверки оказались «ПРОПУЩЕНО», итог — «ничего не проверено», код 2;
- `--list` — каталог всех проверок;
- `--ca файл.pem` — корневой сертификат внутреннего центра (добавляется к доверенным сертификатам Windows);
- `--config файл` — другой файл настроек; `--out папка` — другая папка для протоколов;
- `--no-manual` — не задавать вопросов и не просить действий в 1С (такие проверки будут «ПРОПУЩЕНО»);
- `--verbose` — подробнее на экран (пароль и ключ всё равно не выводятся);
- `--insecure` — не проверять сертификат; `--allow-http` — разрешить адрес без шифрования. Оба — только для осознанного тестового стенда: программа громко предупреждает об этом на экране и в протоколе, а по «Требованиям» (4.2) публикация — только по HTTPS.

## 6. Что проверяется

У каждой проверки есть номер (S1, A2, C7…). Номер, название, результат и источник правила (контракт, раздел «Требований», шаг контрольного примера) видны в протоколе.

| Проверки | Что это значит для 1С | Типичное исправление |
|---|---|---|
| **S1–S3** связь | публикация доступна по HTTPS с этого компьютера, сертификат выдан на имя из адреса, TLS 1.2 или новее, расширение опубликовано, обмен не приостановлен. Если соединения нет совсем (отказ, имя не найдено), S2 — «ПРОПУЩЕНО», причина — в S3 | адрес до `/hs`; сертификат — на тот адрес, по которому обращается сервер POS; выключить константу `ОбменПриостановлен` |
| **A1–A8** доступ | `/health` с ключом — 200; без ключа, с неверным ключом, с неверным паролем, без `Authorization` — 401; ключ проверяется в **каждом** методе — и без ключа, и с неверным ключом (код, который проверяет только «заголовок заполнен», не пройдёт); ответ 401 — ни в теле, ни в заголовках (`WWW-Authenticate` и др.) — не выдаёт версии платформы, расширения и конфигурации и «пользователь не найден»; пароль не короче 16 символов | проверять `X-POS-Client-Key` в начале каждого обработчика, до разбора запроса; при отказе — 401 с телом `POS_E_UNAUTHORIZED`; убрать версии из `realm` веб-сервера |
| **H1–H3** `/health` | все обязательные поля, `apiVersion` = `"1"`, `serverTime` с `+06:00` и не расходится с часами больше 5 минут, `status` = `ok` | заполнить все поля `Health`; проверить часы и часовой пояс сервера 1С |
| **C1–C14** план обмена | до `ack` повтор отдаёт то же сообщение **целиком** (тот же номер и все элементы), у каждого объекта в повторе та же ссылка `ref`; страницы по `cursor` без повторов — ни на разных страницах, ни на одной; не больше 5000 элементов; каждый элемент — по схеме своего типа; у набора штрихкодов `ref` — само значение штрихкода; если `/health` показывает регистрации (`registrationBacklog` > 0), сообщение не пустое; неверный `since` — 400; `ack`, повтор `ack`, `ack` невыданного номера — 409; после `ack` сообщение пустое; изменённый товар приходит в следующем сообщении; удаление — `ObjectDeletion`; объекты, созданные программой, приходят в следующем сообщении с нашим `externalId` (C14): клиент — `Catalog_Партнеры`, заказ — `Document_ЗаказКлиента` с тем же `ref`, пробный QR — `QrPaymentStatus` со статусом `cancelled` и тем же `reference` | номер сообщения не растёт до `ack`; `ref` — ссылка самого объекта, не новый GUID при каждой выгрузке; курсор ведёт к следующей странице; авторегистрация объектов раздела 5.1 в плане обмена «POS», в том числе заказов, созданных из POS, и регистра `POS_ОплатыQR`; `externalId` — из регистра `POS_ВнешниеИдентификаторыPOS` |
| **I1–I3** картинки (обязательный метод) | `ETag` — SHA-256 файла в кавычках, `Content-Length` = размер, на `If-None-Match` — 304 без тела **с тем же `ETag`**, несуществующая картинка — 404 с телом ошибки; пути к файлу на диске 1С нет ни в заголовках (`Content-Disposition`…), ни в тексте ошибки | считать `ETag` от двоичных данных файла; при совпадении `If-None-Match` отвечать 304; имя файла — без пути |
| **X1–X5** `/external-ids` (желательный метод) | ответ по схеме, страницы не больше `limit` (X2 просит `limit=10`), фильтр по типу; один `externalId` — один объект 1С (одна запись, без повторов); каждый объект, созданный программой, есть в списке с тем же `ref` и номером, `deletionMark` — `false`, а у заказа, который программа отменила пометкой удаления, — `true` (X4); без `since` с `type=Заказ&limit=500` — как при ручной привязке заказа (второй запрос КП-19) — заказы этого прогона первыми на странице, новые раньше старых (X5) | запись регистра `POS_ВнешниеИдентификаторыPOS` — в одной транзакции с объектом, поиск под управляемой блокировкой; выдача — `УПОРЯДОЧИТЬ ПО ДатаСоздания УБЫВ, ВнешнийИд` |
| **K1–K10** клиенты и долги | новый клиент — 201; повтор с тем же `externalId` — 200 и тот же клиент: тот же `ref`, код и контрагент (`contractorRef`); 10 одновременных запросов — один клиент с одним кодом и контрагентом; дубль по телефону — 409 `POS_E_DUPLICATE` с кандидатом; при `failOnDuplicate=false` — 201 и **новая** карточка; неверный телефон — 400 или 422; поиск K7 — `+996…` и `0XXXXXXXXX` дают одних и тех же кандидатов, у каждого последние 9 цифр номера совпадают с запросом; долг клиента K8–K9 — по схеме, правила приёма POS, снимок `snapshotAt` — на момент запроса (раньше него не больше чем на 5 минут), срок `dueDate` без значения — `null`, не пустая дата 1С | поиск по `ВнешнийИд` до создания под управляемой блокировкой; на повтор ничего не создавать; ошибка данных — 400 или 422, не 500 |
| **PAY1–PAY6** оплаты | наличные 1.00 KGS без заказа по тестовому клиенту — 201 и **приходный кассовый ордер** (для `cash` — ПКО, для `qr_bakai` — поступление безнала или эквайринг); программа шлёт `post=false` — документ не проводится (`posted=false`); повтор и 10 одновременных — один документ с тем же номером и датой; несуществующий заказ — 422 (не 404); распределение больше суммы — 422; неверный JSON — 400 (не 500). Если 1С отклоняет оплату без заказа клиенту без долга (409 или 422) — «ЗАМЕЧАНИЕ»: «Требования» (6.13) это допускают, тогда повтор проверьте по КП-14 | как у клиентов; при ошибке данных документ не создавать |
| **O0–O9** заказы (обязательные методы) | статус неизвестного заказа — 404 (ответ 200 на неизвестный `externalId` — ОШИБКА, «Требования» 8.4); заказ розничного покупателя (`customer.ref = null`) — 201, не 400, документ проведён (`posted=true`), не согласован (`approved=false`, статус не `Согласован`, `КВыполнению`, `Закрыт`), в ответе тот же `externalId`; повтор — 200 и тот же документ (номер, дата); 10 одновременных — один документ; статус своего заказа — тот же `externalId`, `ref`, номер и дата, что в ответе создания (и в пакете, и в ответе отмены, и в повторе отмены); пакетный статус: свой — в `items` и не в `notFound`, случайный — в `notFound`, ответ 200; отмена — 200 и заказ **отменён**: статус отмены (типово `Закрыт`) или `deletionMark=true`, а статус и пакетный статус сразу после отмены показывают то же (без кэша); статус отмены, которого POS не знает, — «ЗАМЕЧАНИЕ»: пришлите его (вопрос 51); повтор отмены — 200 с тем же состоянием; отмена неизвестного — 404; неверный JSON — 400 | раздел 6.6–6.9 «Требований» |
| **R0–R1** заявки на возврат (если 1С принимает их извне — Q-018, вопрос 77) | статус неизвестной заявки — 404 (200 — ОШИБКА); заявка по несуществующей реализации — 422 (не 404); нет методов — «МЕТОДА НЕТ» | раздел 6.17–6.18 |
| **Q0–Q8** QR через 1С (если интеграция с банком умеет) | статус неизвестного платежа — 404 (200 — ОШИБКА); пробный QR — 201 на сумму запроса (1.00 сом, не тыйыны), в ответе `qrPayload` или `qrImagePng`; повтор при действующем QR — тот же QR: `qrPayload` (или картинка), `reference`, `expiresAt`, сумма; статус `pending` с тем же `reference`, суммой и сроком (и после отмены, и в каждом из 20 опросов); отмена — `cancelled`, повтор отмены — 200; пока оплаты нет (`pending`, `cancelled`), `paidAmount` и `paidAt` — `null`, а не `0.00` и не пустая дата, и пустая строка вместо `null` — ошибка; статус 20 раз — p95 не больше 1 с | раздел 6.14–6.16 и 7 |
| **CK1–CK4, CC1** проверка корзины (обязательный метод) и карточка товара (по желанию) | корзина из 2 строк — 200 не дольше 3 с, `receivables` и `totals` — `null`; количество 999999.000 — `STOCK_INSUFFICIENT`, `isAvailable=false`; 101 строка — 400; корзина в долг (`paymentMethod=credit`) с клиентом — блок `receivables` с долгом и лимитом по правилам метода долга, снимок — на момент проверки (`snapshotAt` рядом с `checkedAt`); карточка товара — по схеме | раздел 6.5 и 6.21 |
| **E1–E12** сквозные правила, для каждого ответа | заголовок `X-POS-API-Version: 1`; `X-Request-Id` ответа = запроса; JSON в UTF-8 без BOM, закодирован один раз, строки без «половинок» символов; правило GUID, пустая ссылка `00000000-…` вместо `ref` — ошибка; форматы денег, количества, дат (и дата существует в календаре: 30 февраля — ошибка; пустая дата 1С `0001-01-01T00:00:00+06:00` — ошибка: нет значения — `null`), телефона (`+996` и ровно 9 цифр), валюты; обязательные ключи и `null`, пустой список `[]`; единое тело ошибки и код ↔ HTTP-статус (тело ошибки со статусом 200 — ОШИБКА); текст ошибки без персональных данных; время ответа (таймаут POS; `/check` — не дольше 3 с, страница `/changes` — не дольше 20 с); ошибка данных — не 5xx | таблица «Частые находки» ниже |
| **M1–M11** ручные шаги | действия и сверки, которые программа не может сделать сама | раздел 8 |
| **L1–L2** время и объём | время ответа каждого метода, скорость полного чтения `/changes` | сведения для нас; нарушения сроков — в E10 |

**Частые находки и как исправить в 1С.**

| Что видно в протоколе | Как исправить |
|---|---|
| «МЕТОДА НЕТ — … метод обязателен (Требования к API 1С §6.x; делается на этапе N раздела 8.2)» | добавить шаблон URL и обработчик в HTTP-сервис `POS_HTTPСервисPOS`; ответ 405 — шаблон есть, а обработчика этого HTTP-метода (GET или POST) нет |
| «тело начинается с BOM» | JSON — в UTF-8 без BOM: `HTTPСервисОтвет.УстановитьТелоИзСтроки(Текст, КодировкаТекста.UTF8, ИспользованиеByteOrderMark.НеИспользовать)` |
| «JSON закодирован дважды» | структуру пишите в ответ через `ЗаписатьJSON` один раз; уже готовую строку JSON отдавайте телом как есть |
| ссылка в верхнем регистре, с фигурными скобками, не GUID; пустая ссылка `00000000-…` | `НРег(Строка(Ссылка.УникальныйИдентификатор()))` — 36 символов, не код и не представление; нет значения — `null` |
| дата без `+06:00`, с долями секунды или с `Z`; «такой даты нет в календаре» | `Формат(Дата, "ДФ=yyyy-MM-ddTHH:mm:ss") + "+06:00"` от настоящей даты, а не склейка строк |
| деньги или количество переданы числом | строка: деньги — `Формат(Сумма, "ЧДЦ=2; ЧРД=.; ЧГ=0; ЧН=0.00")`, количество — `Формат(Количество, "ЧДЦ=3; ЧРД=.; ЧГ=0; ЧН=0.000")` |
| нет обязательного поля; пустой список передан как `null` | обязательный ключ передаётся всегда; нет значения — `null` (где контракт разрешает), пустой список — `[]` |
| ключ не проверяется в методе; «с неверным ключом ответ 200 — ключ не сверяется» (A6) | проверка `X-POS-Client-Key` — в каждом методе: сравнить значение с ключом из безопасного хранилища, а не только «заголовок заполнен»; ответ 401 с телом `POS_E_UNAUTHORIZED` («Требования» 4.4 п. 3) |
| «на случайный GUID (неизвестный externalId) ответ 200» (O0, R0, Q0) | искать объект в регистре (`POS_ВнешниеИдентификаторыPOS`, для QR — `POS_ОплатыQR`); записи нет — 404 `POS_E_NOT_FOUND`, а не ответ по `ПолучитьСсылку(uuid)` или пустой ссылке («Требования» 8.4) |
| «в заголовке www-authenticate ответа 401 сведения о системе» | убрать версии платформы, расширения и конфигурации из `realm` и других заголовков веб-сервера |
| ошибка данных отдана как 500 | неверный запрос — 400 `POS_E_BAD_REQUEST`, ошибка заполнения — 422 `POS_E_VALIDATION`; 500 — только сбой 1С |
| текст ошибки с текстом исключения 1С или с телефоном; «не по-русски», «похож на кыргызский» (ЗАМЕЧАНИЕ) | `message` — понятный текст для журнала без телефонов, ИНН, имён и сумм долга («Требования» 4.6); журнал POS разбирают по-русски — проверьте язык пользователя `pos_hs` и `НСтр()` |
| «в тексте ошибки имя клиента» (ФИО с отчеством, «уулу»/«кызы», «Фамилия И. О.», «Фамилия Имя» после слова «клиент», «партнёр»…) или «сумма долга» (в любом виде: `15 300,00`, `15300.00`, `850.00` рядом со словами «долг», «задолженность», «лимит», «сальдо»…) | в `message` — общий текст («Клиент не найден», «Превышен лимит»); ссылку на клиента и суммы — в `details` или не передавать («Требования» 4.6). Наименование товара в тексте можно: «долговечная», «2.70 кг», «3х2.50», «Розничный покупатель» ошибкой не считаются |
| «после +996 должно быть 9 цифр; похоже, к +996 приписан номер с ведущим 0» | из номера — только цифры, `Прав(Цифры, 9)`, спереди `+996`: из `0700 000 001` — `+996700000001` («Требования» 4.3: E.164); такой номер POS иначе отбросит |
| «кандидат с другим телефоном — поиск не фильтрует по номеру» (K7) | отбирать партнёров по последним 9 цифрам номера из контактной информации «Телефон» (контракт `GET /customers`); `phone` кандидата — найденный номер |
| «ref набора штрихкодов — значение штрихкода, не GUID» (C3) | ключ набора записей `ШтрихкодыНоменклатуры` — сам штрихкод: `ref` = `barcode`; удаление штрихкода — `ObjectDeletion` с тем же `ref` |
| «повтор до ack с тем же номером выдал не всё» (C1) | повтор без `cursor` до `ack` — то же сообщение целиком: `ВыбратьИзменения(Узел, НомерСообщения)` с тем же номером, регистрации до `ack` не снимать и не отбирать |
| «дважды на странице» (C2, X1) | один объект — один элемент страницы; не складывайте в страницу две выборки |
| «registrationBacklog = N, а сообщение пустое» (C2) | выдавать в `/changes` все регистрации узла; тип, который POS не нужен, убрать из состава плана обмена, а не из выдачи |
| «один externalId — два объекта 1С» (X1) | повтор с тем же `externalId` должен находить объект в регистре под управляемой блокировкой, а не создавать второй |
| «повтор вернул другого контрагента», «ref один, а code (number) — N разных значений» (K2, K3, PAY3, O3) | на повтор вернуть найденный объект: тот же `ref`, номер (код), дату и контрагента; ничего не создавать и не перенумеровывать («Требования» 4.7) |
| «при failOnDuplicate=false вернулся существующий клиент» (K5) | при `failOnDuplicate=false` поиск дублей по телефону не выполняется — создать новую карточку (201) |
| «оплата наличными оформлена документом …» (PAY1) | для `kind=cash` — `Документ.ПриходныйКассовыйОрдер` (типово — уточнить), для `qr_bakai` — поступление безнала или эквайринг («Требования» 6.13 п. 3) |
| «документ проведён, хотя post=false» (PAY1) | проводить только при `post=true` и `РазрешитьПроведениеПлатежей = Истина`; иначе записать без проведения, `posted=false`. На повтор (PAY2) `posted=true` — «ЗАМЕЧАНИЕ»: верно, если документ провёл бухгалтер |
| «заказ розничного покупателя (customer.ref = null) отклонён» (O1) | подставить розничного контрагента и соглашение по умолчанию и создать заказ («Требования» 1.2 п. 4, 6.6) |
| «posted = false», «заказ уже согласован или закрыт», «externalId ответа …, а в запросе …» (O1, O2) | создание, проведение и запись в `POS_ВнешниеИдентификаторыPOS` — одна транзакция; статус нового заказа — «Не согласован» (или эквивалент); `externalId` ответа — из запроса («Требования» 6.6) |
| «отмена ответила 200, а заказ не отменён»; «после отмены GET /orders/{uuid}/status (POST /orders/status) отдаёт …» (O6) | отменить по правилам базы — статус «Закрыт» или пометка удаления — и вернуть состояние после записи; методы статуса читают документ заново, без кэша («Требования» 6.7–6.9). «Такой статус POS не знает» — «ЗАМЕЧАНИЕ»: пришлите статус отмены вашей конфигурации (вопрос 51) |
| «number «9», а при создании (O1) «ЗК00-000009»», «date …», «externalId …, а запрошен … — это ссылка документа» (O4–O7) | во всех методах заказа — один и тот же документ: полный номер `Ссылка.Номер` (не `НомерНаПечать()`), `Ссылка.Дата`, `externalId` — `ВнешнийИд` из регистра, а не `УникальныйИдентификатор()` ссылки («Требования» 6.8, 6.20) |
| «наш заказ … и в items, и в notFound», «в notFound, а документ в 1С есть» (O5, O6) | каждый запрошенный `externalId` — ровно в одном списке: найден в регистре — в `items`, нет — в `notFound`; отмена и пометка удаления — не повод для `notFound` («Требования» 6.9) |
| «snapshotAt … раньше момента запроса: снимок не на момент расчёта» (K8, CK4) | `snapshotAt` — `ТекущаяДатаСеанса()` в момент расчёта ответа, а не дата последнего движения регистра и не время сохранённого результата; часы сервера 1С — верные. Снимок старше 60 минут POS для продажи в долг не принимает («Требования» 6.12) |
| «пустая дата 1С … вместо null» (E5), «dueDate … пустая дата 1С» (K8), «оплаты не было, эти поля null» (Q3–Q8) | пустую дату (`ЗначениеЗаполнено(Дата) = Ложь`), нулевую сумму оплаты и пустую строку не форматируйте: передайте `null`, где контракт его разрешает («Требования» 4.3, 6.12, 6.15) |
| «первыми идут старые записи», «нет на первой странице» (X5) | `/external-ids` — `УПОРЯДОЧИТЬ ПО ДатаСоздания УБЫВ, ВнешнийИд`, и с `since`, и без него: первыми — новые записи («Требования» 6.20) |
| «заказ из O1 не пришёл … элементом Document_ЗаказКлиента», «externalId = null» (C14) | `Документ.ЗаказКлиента` — в составе плана обмена «POS» с авторегистрацией; в элементе — `externalId` из `POS_ВнешниеИдентификаторыPOS` («Требования» 5.1, 6.2 правило 8, 6.6) |
| «QR из Q1 не пришёл … элементом QrPaymentStatus», «status … а QR отменён», «reference …» (C14) | регистр `POS_ОплатыQR` — в составе плана обмена «POS», элемент — текущая запись: `ref` и `externalId` = `ВнешнийИдПлатежа`, `status`, `reference` выданного QR («Требования» 5.7, 6.14 п. 9, 7.10). Если включить регистр в план обмена нельзя — сообщите (вопрос 70) |
| «amount … а QR запрошен на 1.00 KGS», «покупателю нечего показать» (Q1) | QR — на сумму `amount` в сомах, `amount` ответа — та же сумма; строку QR — в `qrPayload` (или картинку — в `qrImagePng`) («Требования» 6.14) |
| «повтор при действующем QR: … другие — похоже, банк вызван снова» (Q2); «reference …, а QR выдан с reference …», «срок действия выданного QR не пересчитывается» (Q3, Q6, Q8) | на повтор при `pending` с неистёкшим сроком — сохранённые `qrPayload`, `reference`, `expiresAt`, к банку не обращаться; статус читает запись `POS_ОплатыQR`: `reference` — выданного QR (номер операции банка — в `bankReference`), `amount` и `expiresAt` — как при создании («Требования» 6.14 п. 2, 6.15, 7.3 п. 7) |
| «при paymentMethod=credit … нужен блок receivables» (CK4) | заполнить блок долга клиента в ответе `/check` («Требования» 6.5) |
| «страница больше limit — 1С не ограничивает страницу» (X2) | `ВЫБРАТЬ ПЕРВЫЕ &limit …`, остаток — по `cursor` с `hasMore=true` |
| «ошибка отдана со статусом 200» | ошибку — с HTTP-кодом из приложения А.1 «Требований»: `Новый HTTPСервисОтвет(404)` для `POS_E_NOT_FOUND` и т. д.; ответ 200 POS примет за обычный |
| «ссылка объекта меняется от чтения к чтению» | `ref` = `НРег(Строка(Ссылка.УникальныйИдентификатор()))` самого объекта, а не `Новый УникальныйИдентификатор()`: POS узнаёт объект только по `ref` |
| «путь к файлу на диске 1С» (I1–I3) | имя файла — без пути; текст 404 — «Файл картинки не найден» без пути |
| «304 с другим ETag» (I2) | в ответе 304 — тот же `ETag`, что у файла |
| `X-Request-Id` ответа не совпадает с запросом | вернуть заголовок `X-Request-Id` из запроса и тот же `requestId` в теле ошибки |

**Результаты в протоколе.**

| Результат | Что значит | Влияет на итог |
|---|---|---|
| ПРОЙДЕНО | всё как требуют контракт и «Требования» | нет |
| ОШИБКА | нужно исправить в 1С (в том числе «МЕТОДА НЕТ» у обязательного метода) | да |
| ЗАМЕЧАНИЕ | не мешает работе, но стоит посмотреть (например, ответ медленнее цели или текст ошибки не по-русски) | нет |
| СВЕДЕНИЯ | информация для нас | нет |
| ПРОПУЩЕНО | проверка не выполнялась; причина указана (нет записи, нет данных, вы пропустили, нет обязательного метода, проверка прервана) | нет, но итог тогда «проверка неполная» |
| МЕТОДА НЕТ | веб-сервер или платформа ответили 404 (адреса нет) или 405 (шаблон есть, а этого HTTP-метода нет) у метода, который делается по желанию или при условии: QR через 1С, заявки на возврат (если 1С их не принимает), карточка товара, `/external-ids` | нет |
| ВРУЧНУЮ: ДА / ВРУЧНУЮ: НЕТ | ваш ответ на вопрос программы | «НЕТ» — да; у необязательного шага «нет» — ЗАМЕЧАНИЕ |

| КП-6 клиент без дублей | K1 (201), K2 (повтор — 200, тот же клиент), K4 (дубль — 409 с кандидатами), K3, K5 |
| КП-7 проверка корзины | CK1–CK4 (2 строки, нехватка остатка, 101 строка, корзина в долг — блок `receivables`); время — E10 (не дольше 3 с); корзина из 30 строк — вручную |
| КП-8 заказ и защита от дублей | O1 (заказ розничного покупателя `customer.ref = null` — 201, проведён, «Не согласован»), O2 (повтор), O3 (10 одновременных — один документ); заказ в `/changes` с `externalId` — C14 |
| КП-10 статус заказа | O4, O5 (статус своего заказа, пакетом: тот же номер, дата и `externalId`); «согласован» после согласования в 1С — вручную |
| КП-11, КП-13 QR | Q1–Q8 (если метод есть): создание на сумму запроса, повтор — тот же QR, статус с тем же `reference` и сроком, отмена, повтор отмены; запись QR в `/changes` (`QrPaymentStatus`) — C14; пробная оплата — вручную |
| КП-14 оплата | PAY1–PAY3 (наличные без заказа, повтор, 10 одновременных), PAY5 (распределение больше суммы — 422); распределение по двум документам долга — вручную |
| КП-15 отмена заказа | O6 (заказ отменён; статус и пакетный статус после отмены — то же), O7 |
| КП-17 заявка на возврат | R0, R1 (если 1С принимает заявки извне: статус неизвестной — 404; несуществующая реализация — 422); заявка по проведённой реализации — вручную |
| КП-18 картинка | I1, I2 (`ETag`, 304 без тела), I3 |
| КП-19 перечень объектов | X1–X4 (если метод есть; объекты прогона — X4), X5 (второй запрос без `since`: `type=Заказ&limit=500`, заказы от новых к старым) |
| КП-20 неверный запрос и блокировка | PAY6, O9 (неверный JSON — 400 в едином формате); блокировка заказа — вручную (M11) |

Шаги КП-9, КП-12, КП-16 и ручные части шагов выше требуют действий в 1С: они перечислены в конце протокола в разделе «Шаги контрольного примера вручную».

## 7. Чтение и запись

**Без флагов программа только читает:** все её запросы — GET, в базе ничего не меняется. Сообщения плана обмена она читает, но не подтверждает (`ack` не отправляет).

**С записью** (`Proverka_API_1C_zapis.cmd` или флаг `--allow-write`) перед первым изменением программа показывает предупреждение, сервер, публикацию и конфигурацию и просит ввести имя публикации (например `ut_test`; если имени в адресе нет — слово «ДА»). Если имя не похоже на тестовую копию, программа предупредит. Другой ответ — запись отменена, проверка чтения продолжается.

Что создаётся за один прогон (не больше):

- 3 клиента «ПРОВЕРКА POS клиент ЧЧММСС (удалить)» с телефонами `+996000…` (такой код оператора не выдаётся — с настоящими клиентами не совпадёт);
- 2 непроведённые оплаты наличными по 1.00 KGS без заказа;
- 2 заказа розничного покупателя на 1 шт. по 1.00 (первый программа сразу отменяет);
- 1 пробный QR на 1.00 KGS — только если метод QR у вас есть и вы ответили «да» на отдельный вопрос.

У всех объектов `externalId` начинается с `5e1f7e57-`. Клиенты называются «ПРОВЕРКА POS клиент …», у заказа «ПРОВЕРКА POS» — в комментарии. В запросе оплаты комментария нет: оплаты ищите по `externalId` в регистре `POS_ВнешниеИдентификаторыPOS` (1С пишет в комментарий документа `POS <uuid>`, «Требования» 4.7 п. 4). Оплаты привязываются **только к тестовому клиенту** «ПРОВЕРКА POS», которого программа создала в этом же прогоне (K1); не создался — проверки оплат «ПРОПУЩЕНО». Клиента базы программа берёт для записи, только если вы сами указали его в `refs.customerRef` — тогда он назван (ссылка и код) в предупреждении перед записью. Для проверки корзины в долг (CK4) клиент из `/changes` или `refs.customerRef` используется только в `/check` — этот метод ничего не записывает («Требования» 4.7).

Остальные запросы записи новых объектов не создают: неверный JSON, повтор, ссылка на несуществующий документ, проверка корзины, отмена своих же тестовых заказа и QR. Запросы **без ключа** и **с неверным ключом** (A6) программа отправляет с заведомо неразбираемым телом: правильная 1С отвечает 401 до разбора, а 1С без проверки ключа споткнётся о разбор и ничего не сделает. Перерегистрацию без ключа и с неверным ключом программа вызывает, только если вы сами ответили «да» на перерегистрацию (C6). Если 1С всё же ответила «успешно» на запрос, который ничего не должен был менять (без ключа, `ack` невыданного номера, ошибочные данные), это видно на экране («ВНИМАНИЕ …») и в протоколе: в «Созданных объектах» — «возможно, создан объект», в изменениях плана обмена — что могло измениться. Запрос, который может создать объект, попадает в протокол ещё до отправки: если ответа не было (обрыв, таймаут, Ctrl+C), объект указан как «результат неизвестен» — найдите его по `externalId`.

Отдельные вопросы, по умолчанию «нет»:

- **перерегистрация** (`/changes/reregister`) — регистрирует все объекты для узла «POS», нагружает 1С на несколько минут;
- **пробный QR** — если на копии настроен настоящий банк, QR появится в банке (деньги не списываются, пока никто не оплатит).

**Подтверждение (`ack`).** Программа подтверждает прочитанные сообщения плана обмена. Если к копии подключена тестовая система POS, подтверждённые изменения она не получит — скажите нам, и мы запустим в ней полную выгрузку.

**Как удалить созданное.** В протоколе — таблица «Созданные объекты»: вид, `externalId`, ссылка, номер, проверка и как удалить. Пометьте объект на удаление и удалите помеченные; запись регистра `POS_ВнешниеИдентификаторыPOS` удалите вместе с объектом. Для пробного QR — запись регистра `POS_ОплатыQR`. Ниже таблицы — список изменений плана обмена (перерегистрация, подтверждённые номера сообщений).

## 8. Ручные шаги

Некоторые проверки программа не может сделать сама. Тогда она задаёт вопрос или просит сделать действие в 1С.

- На вопрос отвечайте `д` (да), `н` (нет) или `п` (пропустить) и Enter. Что значит каждый ответ, написано в скобках после вопроса. **Enter без ответа — «пропустить»** (в подсказке `[д/н/П]` заглавная буква — ответ на Enter). «Нет» на обязательный шаг — «ВРУЧНУЮ: НЕТ», это ошибка; «нет» на необязательный шаг — «ЗАМЕЧАНИЕ», на итог не влияет.
- Отвечайте русскими буквами. Если включена латинская раскладка, программа примет «l» как «д» и «g» как «п», а на «y» (это клавиша «н») и другую латиницу переспросит: «Похоже, включена латинская раскладка». Английское «y» ответом «да» не считается.
- На просьбу «сделайте в 1С … и нажмите Enter» сначала сделайте действие, потом нажмите Enter. Если сейчас сделать его нельзя — введите `п` и Enter: шаг будет «ПРОПУЩЕНО» (не ошибка), программа пойдёт дальше. Ответ `н` (или `нет`, `n`) значит «не сделал»: программа попросит ещё раз, после трёх таких ответов шаг будет «ПРОПУЩЕНО». Чтобы пропустить все ручные шаги сразу, запустите проверку с флагом `--no-manual`.

| № | Что просит программа | Что сделать |
|---|---|---|
| C11 | изменить описание названного товара (код и ссылка на экране) | изменить и записать товар, Enter; программа проверит, что он пришёл в следующем сообщении (КП-4) |
| C12 | необязательно: удалить на копии объект состава обмена **совсем** — например, тестовую характеристику: пометить на удаление и выполнить «Удаление помеченных объектов» | удалить и ответить; программа проверит, что в следующем сообщении пришёл `ObjectDeletion`. Пришёл только объект с `deletionMark=true` — «СВЕДЕНИЯ»: пометка передана, `ObjectDeletion` будет после удаления помеченных («Требования» 5.7 «Удаления») |
| C13 | только после перерегистрации (режим записи, ответ «да» на C6): сверить числа товаров, групп, характеристик, упаковок, штрихкодов, картинок, складов, видов цен, партнёров, контрагентов, соглашений | сравнить с 1С. Без перерегистрации программа не спрашивает: в сообщении лишь накопившиеся изменения, не вся база («Требования» 8.2, этап 3) |
| K10 | сверить долг клиента: на экране код клиента (если он пришёл в `/changes`) и сальдо; имя клиента не показывается | найти клиента по коду и сравнить с отчётом «Задолженность клиентов» («Требования» 8.4) |
| M1 | включить константу `ОбменПриостановлен`, затем выключить | включить, Enter; программа проверит, что методы отвечают 503 `POS_E_MAINTENANCE` («Требования» 4.6, 8.6); выключить, Enter. Нельзя сейчас — `п`: тогда выключать ничего не надо, программа об этом не спросит |
| M2 | проверка с **другого** компьютера сети | скопировать на другой компьютер **всю папку программы вместе с `nastrojki.json`** и запустить `Proverka_API_1C.cmd --expect-no-access`; пароль и ключ не нужны. Адрес должен находиться на этом компьютере так же, как на сервере POS (лучше IP-адрес): если имя сервера не найдено, программа скажет «проверка не выполнена» (код 2), а не «доступа нет». «ПРОЙДЕНО» — только отказ в соединении, нет соединения за отведённое время, сброс соединения или 403 |
| M3 | «Публикация закрыта из интернета?» | открыть адрес с телефона по мобильному интернету; `д` — не открылся (так и нужно, «Требования» 4.2), `н` — открылся (ошибка) |
| M8 | найти в 1С созданные объекты (после записи) | найти карточки «ПРОВЕРКА POS…», заказы и оплаты по `externalId` в регистре `POS_ВнешниеИдентификаторыPOS` (в комментарии документа — `POS <uuid>`); на 10 одновременных запросов — одна карточка, один заказ и один ордер |
| M9 | необязательно: найти запрос в журнале `POS_ЖурналЗапросовPOS` | найти запрос с показанным `X-Request-Id`; «нет» — замечание |
| M10 | «Пользователи 1С работали без замедления во время полного чтения?» | спросить пользователей копии (если они работали); не знаете — `п` («Требования» 8.5) |

Шаг КП-20 «блокировка заказа другим сеансом» (M11) и другие шаги контрольного примера, которые требуют действий в 1С, программа не выполняет и о них не спрашивает: они перечислены в конце протокола в разделе «Шаги контрольного примера вручную».

## 9. Протокол: где он и что отправить нам

**Где.** Папка `protokoly` рядом с `Proverka_API_1C.cmd`. Если писать туда нельзя — папка `Proverka_API_1C_protokoly` в папке пользователя Windows (программа скажет об этом). Каждый прогон — три файла с одним именем `protokol_proverki_API_1C_ГГГГ-ММ-ДД_ЧЧ-ММ`:

- `.html` — для чтения, открывается в любом браузере без интернета (без скриптов);
- `.json` — для нас: по нему мы сверяем результаты;
- `.md` — то же, что `.html`, простым текстом.

**Что отправить.** Файлы `.html` и `.json` — разработчикам POS, тем же путём, каким вы получили архив. Программа в конце напоминает про `.html`; нам нужен и `.json`, поэтому проще отправить все три файла. Пароль, ключ, JWT и файлы с ними не отправляйте никогда: в протоколе их нет, и нам они не нужны.

**Что в протоколе:** итог («Ошибок нет», «Ошибок нет, проверка неполная», «Ошибки: N» или «Проверка прервана — итог неполный») и строка полноты — сколько обязательных проверок выполнено и что не проверено (запись, ручные шаги, M2 на другом компьютере); сводная таблица; «Что исправить» — простыми словами, где и почему, с подсказкой для 1С; созданные объекты и как их удалить; ваши ответы на вопросы; подробности по каждой проверке с источником правила («запрос → ответ → результат», тело ответа — до 8 КБ); время ответа; шаги контрольного примера, которые выполняются вручную. В шапке — дата и время по Бишкеку, версии программы, контракта и «Требований», отпечаток сборки (sha256 файлов программы — тот же, что показывает `--version`), имя сервера и порт, пользователь, режим, версия расширения и конфигурации из `/health`. Если программу запустили не через `Proverka_API_1C.cmd`, а на компьютере задана переменная `NODE_EXTRA_CA_CERTS`, в шапке — пометка, что её корневые сертификаты участвовали в проверке TLS (запускатели `.cmd` эту переменную очищают).

**Чего в протоколе нет:** паролей, ключа и JWT (заголовки показаны как `Authorization: Basic ***`, `X-POS-Client-Key: ***`). Телефоны во всех видах (`+996…`, `0555-12-34-56`, `555 12 34 56` → `+996 *** ** 56`), ИНН, e-mail, имена клиентов и контактных лиц, адреса — скрыты: в полях с любыми именами, в том числе по-русски и транслитом (`address`, `legalAddress`, `КонтактноеЛицо`, `Ответственный`, `Менеджер`, `Покупатель`, `Получатель`, `adresDostavki`, контактная информация); в любом тексте — ФИО с отчеством, «уулу»/«кызы», «Фамилия И. О.», адреса с «г.», «ул.», «мкр.», «кв.»; в тексте ошибок — ещё имя после слов «клиент», «контрагент», «партнёр», «ФИО»… и «Фамилия Имя». **Поля, которых нет в контракте 1.2.0** (их POS не читает, в протоколе есть находка «поле … нет в контракте»), показаны с именем, но значение скрыто целиком — остаются только GUID, даты и числа. Тело ответа, которое не удалось разобрать как JSON, в протокол не пишется: только размер, `Content-Type`, место ошибки (строка и столбец) и «скелет» — ключи, скобки и числа, текст скрыт; у HTML-страницы — только заголовок. Наименования и коды товаров, коды и номера 1С (`00-00001234`, `0000-000123`), количества и суммы остаются — они нужны для сверки.

**Код выхода** (для запуска из своих скриптов): 0 — ошибок нет; 1 — есть ошибки (ОШИБКА или «ВРУЧНУЮ: НЕТ»); 2 — проверка не выполнена (настройки, связь, отмена, сбой программы, «ничего не проверено»). Если проверка началась (программа соединилась с публикацией), протокол пишется во всех случаях, при прерывании — с пометкой «ПРОВЕРКА ПРЕРВАНА» и причиной; незаконченная проверка — «ПРОПУЩЕНО». **При ошибке настроек** (файл настроек, адрес, сертификат, файл пароля, отмена ввода пароля) протокол не пишется — причина только на экране.

## 10. Если что-то не так

| Что видно | Что делать |
|---|---|
| «сертификат … не от доверенного центра; укажите корневой сертификат» | запустите с `--ca файл.pem` или укажите путь в `caFile`; файл — корневой сертификат вашего центра в Base64 (оснастка «Сертификаты» → «Экспорт» → «Файлы X.509 (.CER) в кодировке Base64»). Можно вместо этого установить его в «Доверенные корневые центры сертификации» Windows |
| «сертификат выдан на другое имя (…), а адрес — …» | сертификат публикации должен быть выдан на тот адрес, по которому к ней обращается сервер POS («Требования» 4.2); укажите адрес как в сертификате или перевыпустите сертификат |
| «срок действия сертификата истёк» или «ещё не действует» | замените сертификат; проверьте дату на сервере и на этом компьютере |
| хочется только посмотреть без сертификата | `--insecure`: проверка S2 будет «ЗАМЕЧАНИЕ», в протоколе — «СЕРТИФИКАТ НЕ ПРОВЕРЯЛСЯ». Для сдачи так не годится |
| «отказал в соединении (ECONNREFUSED) — по этому адресу и порту ничего не слушает» (S3; S2 при этом «сертификат не проверен») | до сертификата дело не дошло: проверьте адрес и порт, что веб-сервер 1С работает, что публикация разрешена с адреса этого компьютера («Требования» 4.2), сетевой экран |
| «имя не найдено», «не ответил за отведённое время на соединение», «соединение сброшено» | проверьте адрес и DNS; что веб-сервер отвечает по HTTPS на этом порту; сетевой экран |
| в начале 401: «неверный пользователь, пароль или ключ клиента» | проверьте пароль `pos_hs`, ключ клиента, роль `POS_ИнтеграцияPOS`, способ входа (Basic или JWT). Программа останавливается, код 2. Учтите: в проверке A4 программа один раз отправляет неверный пароль |
| в начале 404: «неверный адрес публикации или расширение не опубликовано» | адрес — до `/hs` включительно (адрес вида `…/hs/pos/v1/health` программа сама сокращает до `…/hs`); опубликуйте HTTP-сервисы расширения |
| в начале 503 `POS_E_MAINTENANCE` | выключите константу `ОбменПриостановлен` и запустите снова |
| «временная ошибка (503 `POS_E_LOCKED`) — ответ получен с 2-й попытки» (СВЕДЕНИЯ), «ответ получен только с последней, 3-й попытки» (ЗАМЕЧАНИЕ), «временная ошибка во всех 3 попытках» | на чтении (GET) программа, как и POS, повторяет запрос при временной ошибке — сеть, таймаут, 5xx, `POS_E_LOCKED`, `POS_E_MAINTENANCE` — до 3 попыток с паузами 0,5 и 1 с (контракт, `x-get-retry`). Одна-две такие ошибки — не ошибка 1С; если ответ пришёл только с последней попытки или не пришёл вовсе — сократите блокировки и длинные транзакции в 1С, проверьте загрузку сервера. Запросы записи (POST) не повторяются |
| «нет ответа за N с — POS считает результат неизвестным» | метод отвечал дольше, чем ждёт POS по контракту («Требования» 4.9: например `/health` — 30 с, страница `/changes` — 60 с, `/orders`, `/check`, поиск клиента, долг клиента, QR — 6 с, создание клиента и оплаты — 30 с, картинка — 120 с). Ускорьте запрос: индексы, меньше лишних данных; проверьте загрузку сервера. `/check` дольше 3 с и страница `/changes` дольше 20 с — «ЗАМЕЧАНИЕ» |
| «ПРОПУЩЕНО: нет данных … укажите refs» | на копии нечего взять для проверки (товар, склад, вид цены, клиент, картинка). Укажите GUID в разделе `refs` файла `nastrojki.json` или запустите с записью и перерегистрацией |
| вместо русских букв «кракозябры» | запускайте через `Proverka_API_1C.cmd` (он включает UTF-8 командой `chcp 65001`). Если запускаете `runtime\node.exe` напрямую — сначала выполните `chcp 65001`. В старой консоли выберите шрифт Consolas или Lucida Console |
| антивирус или «Windows защитила ваш компьютер» | `node.exe` — официальный Node.js: «Свойства» → «Цифровые подписи» → OpenJS Foundation; суммы файлов — в `SHA256SUMS.txt`. Разблокируйте архив до распаковки (раздел 4, шаг 1); если антивирус удаляет `node.exe`, попросите администратора разрешить папку программы |
| «Ошибка настроек: …» | исправьте `nastrojki.json` (JSON, ключи латиницей) или удалите его, чтобы ответить на вопросы заново; файл секрета — одна строка. «Ошибка JSON в строке N, столбце M» — откройте файл в Блокноте и посмотрите это место: значения — в кавычках, после последнего значения запятой нет, в путях — `/` или `\\` |
| «файл, указанный в passwordFile, не найден — там должен быть ПУТЬ…» | в `passwordFile`, `clientKeyFile`, `tokenFile` пишется путь к файлу с секретом, а не сам секрет |
| «в ключе клиента есть русские буквы…» | ключ и JWT — латиница, цифры и знаки; переключите раскладку клавиатуры и введите снова |
| «Итог: ошибок нет, но проверка неполная» | ошибок нет, но часть обязательных проверок не выполнялась — список в строке «Проверено обязательных N из M; не проверено: …»: запустите `Proverka_API_1C_zapis.cmd`, пройдите ручные шаги, M2 — на другом компьютере |
| окно сразу закрылось | запустите из окна `cmd` (раздел 4, шаг 3), чтобы увидеть сообщение. Если программа остановилась на настройках, протокол не записан — причина только на экране |

Ctrl+C прерывает проверку: протокол записывается с пометкой «ПРОВЕРКА ПРЕРВАНА», код 2. Если вопрос не решается — пришлите протокол, разберёмся.
