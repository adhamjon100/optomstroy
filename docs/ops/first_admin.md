# Первый администратор на пустой базе (staging / prod)

**Назначение.** Процедура для эксплуатации: как на новом контуре появляется первый пользователь с ролью `admin`.
Приглашать сотрудников по 11 SEC-136 может только `admin`, а на пустой БД его нет. Seed пользователей не создаёт
(D_spec_questions INT-02, D_authentication_report DQ-27).

**Основание:** 16_DEPLOYMENT_PLAN (первичное развёртывание, DEPLOY-042; секреты — §4.3, §4.4, только `*_FILE`),
11_SECURITY_PRIVACY (SEC-136 — кто приглашает; §7.2 — аудит), 09_AUTH_SMS_BIOMETRICS §4.3 (первый вход по
приглашению), D-48 (PIN обязателен для staff).

**Код:** `pos-api/src/admin/bootstrap/first-admin.ts` (логика), `first-admin.cli.ts` (CLI),
`pos-api/scripts/bootstrap-admin.ts` (запуск из исходников).
**Тесты:** `pos-api/test/admin/bootstrap-admin.admin-spec.ts`, сквозной вход —
`pos-api/test/e2e/auth/auth-refinements.e2e-spec.ts` («INT-02»).

---

## 1. Что делает команда

Команда создаёт **приглашение** с ролью `admin` для номера телефона, который назвал заказчик. Она не создаёт
пользователя с паролем и не выпускает токен. Учётная запись появляется при первом входе с этого номера по OTP:
срабатывает ветка «приглашение», то же самое происходит с любым приглашённым сотрудником.

Сразу после входа приложение требует установить PIN (`nextStep = set_pin`).

| Условие | Результат | Код выхода |
|---|---|---|
| Активного пользователя с ролью `admin` нет, номер свободен | приглашение создано, аудит `user.invited` | 0 |
| Повторный запуск с тем же номером, приглашение ещё действует | ничего не меняется (идемпотентно) | 0 |
| В системе уже есть активный `admin` | ничего не меняется; дальше приглашения выдаёт `admin` в SCR-45 | 0 |
| Действует приглашение `admin` на **другой** номер | отказ | 3 |
| Номер уже принадлежит учётной записи (клиент или сотрудник) | отказ | 3 |
| Неверные аргументы или окружение (номер не мобильный КР, ФИО короче 2 символов, срок вне 1…30 суток) | отказ | 2 |
| Непредвиденная ошибка | транзакция откатывается целиком | 1 |

Все проверки и запись выполняются в одной транзакции под `pg_advisory_xact_lock`, поэтому два параллельных запуска
не создадут два приглашения.

**Техническая запись-автор.** По 07 §5.3 поле `user_invitations.invited_by_user_id` обязательно (`NOT NULL`),
а на пустой БД пользователей нет. Поэтому автором первого приглашения становится техническая запись
«Первичная настройка (оператор)». Её свойства:

- нет телефона;
- `status = deleted`;
- нет ролей.

Войти под ней нельзя, в списке пользователей SCR-45 её нет. Повторные запуски используют ту же запись. Вопрос
владельцу 07 записан в `docs/stages/E_spec_questions.md` (EQ-AUTH-07).

## 2. Перед запуском

1. Миграции применены (`migrate`), `pos-api` проходит `/health/ready`.
2. Заказчик назвал номер и ФИО будущего администратора. Номер должен быть мобильным номером КР и принимать SMS.
   Через PR, чат или тикет номер не передаётся: оператор вводит его только в командной строке на сервере.
3. Доставка SMS работает: см. `docs/integration/smspro_connect.md`.
   - На staging без реальных SMS можно временно использовать тестовый режим OTP (09 §5.8):
     `AUTH_OTP_TEST_MODE=true`, номер администратора добавлен в `AUTH_OTP_TEST_PHONES`.
   - На prod тестовый режим запрещён: сервис с ним не стартует.

## 3. Запуск

Внутри контейнера `pos-api` нужно то же окружение, что у сервиса: секреты подключаются через `*_FILE`. В образе
нет каталога `scripts/`, поэтому команда берётся из `dist/`:

```sh
docker compose exec api \
  node dist/admin/bootstrap/first-admin.cli.js --phone +996XXXXXXXXX --name "Фамилия Имя Отчество" [--days 7]
```

С рабочего места разработчика (dev, локальный стек):

```sh
cd pos-api
APP_ENV=dev MIN_APP_VERSION=android=1.0.0 DATABASE_URL_FILE=<файл со строкой подключения> \
  npx tsx scripts/bootstrap-admin.ts --phone +996XXXXXXXXX --name "Фамилия Имя Отчество"
```

Параметры:

- `--phone` — любая запись номера (`+996…`, `996…`, `0…`, с пробелами). Номер нормализуется к `+996XXXXXXXXX`.
- `--name` — ФИО, от 2 до 150 символов.
- `--days` — срок действия приглашения в сутках. По умолчанию — `INVITATION_TTL_DAYS`, допустимо 1…30.

В выводе нет персональных данных: номер маскирован, ФИО не печатается. Для сверки с аудитом выводятся `invitationId`
и `requestId`, например:

```text
bootstrap-admin: создано приглашение admin 0192…; для +996 7** *** *01, действует до 2026-10-29T…Z; вход — по OTP …
```

## 4. Первый вход администратора

1. Администратор устанавливает приложение (Windows-касса или Android) и вводит свой номер на SCR-01.
2. Вводит код из SMS (SCR-02). Сервер создаёт учётную запись `staff` с ролью `admin` и ФИО из приглашения.
   Приглашение получает статус `accepted`.
3. Приложение сразу открывает установку PIN (SCR-04, `nextStep = set_pin`). Без PIN рабочие разделы недоступны
   (`pin_not_set`).
4. Дальше администратор приглашает сотрудников сам (SCR-45 / `POST /admin/invitations`). Повторный запуск команды
   после этого ничего не делает.

## 5. Проверка и аудит

SQL-запросы ниже выполняются под ролью `pos_readonly` или `pos_app`:

```sql
-- приглашение (без ПДн в выводе)
SELECT id, role, status, expires_at FROM user_invitations WHERE role = 'admin' ORDER BY created_at DESC LIMIT 5;
-- аудит выдачи (actor_user_id = NULL — системный процесс bootstrap, reason = first_admin_bootstrap)
SELECT occurred_at, action, entity_id, reason, severity FROM audit_logs
 WHERE action IN ('user.invited', 'user.created') ORDER BY seq DESC LIMIT 5;
```

## 6. Нештатные ситуации

- **Приглашение истекло, администратор не успел войти.** Повторите команду с тем же номером. Просроченное
  приглашение закрывается (`expired`), создаётся новое. Аудит фиксирует оба.
- **Указан не тот номер, приглашение ещё действует.** Команда откажет с кодом 3. Варианты:
  - дождаться срока (`--days` задаёт его при создании);
  - отозвать приглашение вручную, это делает DBA по заявке:
    `UPDATE user_invitations SET status = 'revoked', revoked_at = now() WHERE id = '<invitationId>'`.

    После отзыва запустите команду снова. Отзыв — исключительная операция, запишите его в журнал работ.
- **Все администраторы заблокированы или уволены.** Если активного `admin` нет, команда снова разрешена. Номер
  должен быть новым: номер существующей учётной записи даёт отказ. Восстановление доступа заблокированному
  `admin` — отдельная процедура владельца 11, вне этой команды.
- **SMS не приходит.** Смотрите `docs/integration/smspro_connect.md` §6. Код в БД хранится только как HMAC: узнать
  его из базы нельзя, так задумано.
