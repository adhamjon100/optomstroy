# Контракт 1С (RM-B-004): заметки, решения, расхождения

Задача RM-B-004 (13 §3.2) — контракт HTTP-сервиса расширения 1С «OptomstroyPOS», allow-list OData и фикстуры.

**Источники.** Канон методов — 05_ONEC_INTEGRATION §6.3–§6.7 (ядро R0 v1.9 §24.3, §24.4). Изложение для программиста 1С — ТЗ `docs/integration/1C_API_requirements.md` (версия 1.1); 18_ONEC_API_REQUEST §3–§5 — исходный запрос. При расхождении прав 05. Владельцы словарей — по ядру §18.1:

- коды ошибок `POS_E_*` — 05 §6.5;
- канонические коды `/api/v1` — 08 §2.4;
- enum `payment_method`, `return_reason`, `return_request_status` — 07 §6;
- переменные окружения — 16 §4.3.

## 1. Состав

| Файл | Что это |
|---|---|
| `onec-http-service.v1.yaml` | OpenAPI 3.0.3: 20 путей `/pos/v1/*`, 21 операция (ровно таблица 05 §6.3), схемы запросов, ответов и ошибок |
| `odata-allowlist.yaml` | allow-list коллекций и полей стандартного OData для `pos_integration` (ONEC-083); формат идентификаторов; временный режим записи ONEC-028 |
| `fixtures/*.json` | 59 фикстур — тестовые данные с полем `"_note": "тестовые данные"`. Из них 48 ответов (успешные и ошибки) и 11 запросов |
| `../../scripts/check_onec_paths.py` | проверка контракта, фикстур и allow-list (ниже) |

## 2. Проверки

```
npx --yes @redocly/cli@2 lint contracts/onec/onec-http-service.v1.yaml
python -I -X utf8 scripts/check_onec_paths.py
```

`check_onec_paths.py` возвращает код 1 при любой ошибке. Сеть не нужна. Что он делает:

1. Разбирает таблицу методов 05 §6.3. Сравнивает пары «метод + шаблон пути» с контрактом: 0 лишних и 0 недостающих. Пути вне `/pos/v1/*` запрещены.
2. По каждой операции сверяет с 05 §6.3:
   - query-параметры из шаблона URL;
   - HTTP-коды и коды `POS_E_*` из столбца «Ответы»;
   - обязательные атрибуты ONEC-071: `x-idempotency`, `x-retry`, `x-access`, `x-error-codes`, `x-onec-requirements`, `x-priority`, а также ответы 2xx и 401.
3. Проверяет, что каждое упоминание `/pos/v1/...` в тексте 05 §6 входит в таблицу §6.3. Имена параметров пути при этом нормализуются.
4. Сверяет словари:
   - `ErrorCode` совпадает с 05 §6.5;
   - `IssueCode` совпадает со строкой «Коды `issues[].code`» 05 §6.4.
5. Проверяет фикстуры: конверт, наличие `_note` и операции в контракте, схему тела. Схема проверяется строго: незаявленные поля запрещены, чтобы ловить опечатки. Каждая операция с JSON-ответом 2xx должна иметь фикстуру.
6. Проверяет allow-list по правилу RM-B-004 п. 3. Каждая OData-коллекция, названная в 05 §5, должна входить в `collections` или в `excluded`.
7. Сверяет таблицу 18 §4.0 с 05 §6.3. Результат — только информация: при расхождении прав 05.

Негативная проверка проведена на копии во временном каталоге. Внесено 17 искажений: лишний и недостающий путь, query-параметр, атрибут, HTTP-код, код ошибки, enum, упоминание в 05, опечатка поля, формат денег и даты, `_note`, неизвестный тип элемента, код в имени файла, покрытие фикстурами, `fallback`, коллекция 05 §5. Скрипт обнаружил все 17 (код выхода 1).

## 3. Решения по неоднозначностям ТЗ

1. **Имя файла.** ONEC-033 и ONEC-071 в 05 и 18 §7.6/§8 называют файл `onec-extension/openapi-pos-v1.yaml`. Дорожная карта 13 (RM-B-004, §5.2, строка «Backend ↔ 1С») называет `contracts/onec/onec-http-service.v1.yaml`. Выбран путь 13: так задана задача, и владелец размещения контрактов — 13 §5.2. **Предложение:** в 05 (ONEC-033, ONEC-071) и 18 §8 заменить имя на `contracts/onec/onec-http-service.v1.yaml`.
2. **Базовый адрес.** `servers.url = https://{host1c}/{publication}/hs`, а пути начинаются с `/pos/v1/`. Так набор путей буквально совпадает с 05 §6.3. Сегмент `hs` — [ТИПОВО] (05 §6.3).
3. **Имена параметров пути — как в таблице 05 §6.3:** `{uuid}` у orders и returns, `{externalId}` у payments, `{ref}` у customers, images и catalog. В 05 §6.4 в таблице проекции возвратов встречается `GET /pos/v1/returns/{externalId}/status`. Это внутреннее расхождение 05; источником взята таблица §6.3. В обоих случаях параметр — externalId заявки.
4. **Общие ответы.**
   - 401 и 503 добавлены во все методы: по 18 §4.0 они возможны в любом методе.
   - 403 `POS_E_FORBIDDEN` и 500 `POS_E_INTERNAL` тоже добавлены во все методы — это коды 05 §6.5 без привязки к методу.
   - 400 `POS_E_BAD_REQUEST` добавлен ко всем методам с телом или query-параметрами.
   - 423 `POS_E_LOCKED` («423/503», 05 §6.5) добавлен к `POST /orders` и `POST /check` — там 05 §6.3 называет `POS_E_LOCKED`.
   - Конкретные коды каждого метода перечислены в `x-error-codes`.
5. **Обязательность полей.** В JSON-схемах `required` означает, что ключ присутствует. `nullable` означает, что значение может быть `null` (05 §6.4: «`null` допустим только для необязательных полей»). Ключи из примеров 05 §6.4/§6.7.2 обязательны. Поля, которые 05 или 18 называют необязательными, в `required` не входят: `allocations`, `removedRegistrations`, альтернатива `qrPayload`/`qrImagePng`, блоки и поля элементов `/changes`, не приведённые в примерах.
6. **Схемы не запрещают дополнительные свойства** (ONEC-058: неизвестные поля игнорируются). Строгость `additionalProperties: false` включает только скрипт и только для фикстур.
7. **Форматы ONEC-058.**
   - UUID — шаблон `^[0-9a-f]{8}-…-[0-9a-f]{12}$`. Это подмножество шаблона ONEC-058 `^[0-9a-f-]{36}$`.
   - Деньги и проценты — `^-?\d+\.\d{2}$`. Процент скидки `"5.00"` в 05 §6.4 записан как деньги.
   - Количества — `^-?\d+\.\d{3}$`.
   - Даты — шаблон `+06:00` ONEC-058.
   - Валюта — `^[A-Z]{3}$` без enum. В R1 используется `KGS`, но 05 не запрещает другие коды на уровне протокола: цены в другой валюте отбрасывает backend, 05 §5.3.
8. **Ошибка 409 `POS_E_DUPLICATE`.** 05 §6.4 пишет «с `candidates: [{ref, name, phone}]`», 18 §4.9 — `details.candidates[]`. Выбрано `details.candidates`: единый формат тела ошибки 05 §6.5 содержит объект `details`. Это не противоречит 05.
9. **Безопасность.** Две альтернативы: `basicAuth + clientKey` и `jwtAuth + clientKey` (ONEC-032; выбор Basic или JWT — при приёмке, чек-лист 05 §2.2 п. 1). `X-Request-Id` — обязательный заголовок запроса (ONEC-088). В ответах возвращаются `X-Request-Id` и `X-POS-API-Version: 1` (ONEC-033).
10. **Детали из 18, которых нет в 05 §6.4.** Помечены `x-status: proposed`. 18 §12 п. 1–2 предлагает внести их в 05 §6.4 как канон:
    - тело ответа `POST /changes/ack`: `{messageNumber, removedRegistrations?}` (18 §4.2);
    - пакетный ответ `POST /orders/status`: `{items, notFound}` (18 §4.7);
    - ответ `POST /orders/{uuid}/cancel` — состояние заказа в формате `OrderStatus` (18 §4.6);
    - кандидат поиска `GET /customers?phone=`: `{ref, contractorRef, code, name, phone, deletionMark}` (18 §4.8);
    - ответ `GET /customers/{ref}/receivables` с `documents[]` (18 §4.10, поля ONEC-047);
    - продолжение страниц `/external-ids` через `cursor`/`hasMore` (18 §4.17, 18 §12 п. 2);
    - значение `status: "warning"` в `/health` (18 §4.1). Enum не вводится: 05 его не задаёт.
11. **Элементы `/changes` без примера в 05.** Примеры в 05 есть для `Catalog_Номенклатура`, `Document_ЗаказКлиента`, `ObjectDeletion` (05 §6.4) и `QrPaymentStatus` (§6.7.2). 18 §4.2 отсылает остальные типы к словарю 05 §5.3. Схемы этих типов выведены из словаря 05 §5.3, карты §5.1 (столбец «Способ чтения») и 07 §5.42–§5.43 (`shipments`, `shipment_items`). Они помечены `x-status: proposed`. Имена полей — camelCase по образцу 05 §6.4: `ref`, `code`, `description`, `ownerRef`, `…Ref`. Поля с меткой [НЕ ПОДТВЕРЖДЕНО] в 05 — nullable (ONEC-106). Соответствие:

    | Тип элемента | Источник полей |
    |---|---|
    | `Catalog_ХарактеристикиНоменклатуры` | 05 §5.1 ONEC-005 (`Code, Description, Owner_Key, Owner_Type`), ONEC-073 (`sku`), §5.3 `variant_attribute_values` |
    | `Catalog_УпаковкиЕдиницыИзмерения` | §5.3 `packagings` (`Owner_Key, ЕдиницаИзмерения_Key, Коэффициент`) |
    | `Catalog_КлассификаторЕдиницИзмерения` | §5.3 `units` |
    | `Catalog_Склады` | §5.3 `warehouses`, ONEC-019 |
    | `Catalog_ВидыЦен` | §5.3 `price_lists`, ONEC-007 (`ИспользоватьПриПродаже`, `ВалютаЦены`, `ЦенаВключаетНДС` — nullable) |
    | `Catalog_Партнеры`, `Catalog_Контрагенты` | §5.3 `customers`, `customer_contacts`; `externalId` у партнёра — 05 §6.4 |
    | `Catalog_СоглашенияСКлиентами` | §5.3 `customers` (вид цены, отсрочка, лимит) |
    | `Catalog_СкидкиНаценки` | только реквизиты справочника. Условия скидок в R1 считает 1С (`/check`, ONEC-039) |
    | `Catalog_НоменклатураПрисоединенныеФайлы` | §5.1 ONEC-006, §5.3 `product_images` (версия = `ДатаМодификацииУниверсальная` + `Размер`) |
    | `InformationRegister_ШтрихкодыНоменклатуры` | §5.3 `barcodes`. Плоский элемент, `ref` = штрихкод (ключ набора, 05 §6.2 п. 1). Удаление — `ObjectDeletion` с `ref` = штрихкод |
    | `Document_УстановкаЦенНоменклатуры` | 05 §6.2: перечитка среза по затронутым видам цен (`priceListRefs`) |
    | `Document_РеализацияТоваровУслуг` | §5.1 ONEC-013, 07 §5.42–§5.43 |
    | `Document_ПриходныйКассовыйОрдер`, `Document_ПоступлениеБезналичныхДенежныхСредств` | §5.1 ONEC-016; `externalId` — ONEC-077 |
    | `Document_ВозвратТоваровОтКлиента` | §5.1 ONEC-015 (`ДокументОснование` — nullable) |

    Набор типов в `ChangeItem.oneOf` закрыт составом плана обмена 05 §6.2. Новый тип — это изменение контракта по процедуре 13 §5.3. Адаптер backend должен записывать неизвестный тип в `sync_errors`, а не останавливать применение. Это реализация этапа E.
12. **`POST /check`.** Форма `totals` при `calculateDiscounts=true` в 05 не задана: в примере `null`. Взята схема `Totals` заказа `{subtotal, discount, total, currency}`. Объект замечания `Issue` содержит только `code`: 05 §6.4 задаёт только `issues[].code`. Остатки по складам `warehouses[]` — по ONEC-070.
13. **`GET /catalog/{ref}`** (could). Форма ответа в 05 не задана, поэтому сборная: элементы в формате `/changes` плюс срезы `prices` и `stock` по 05 §5.3. Помечена `x-status: proposed`.
14. **Статус заявки на возврат.** Enum `status` в ответах HS — `submitted | accepted | rejected | completed`. Значение `draft` канона `return_request_status` расширение не возвращает (таблица проекции 05 §6.4).
15. **QR.** Формат — 05 §6.7.2. Поле `qrImagePng` — [НОВОЕ ИМЯ] 05 (по ответу QR-3), помечено `x-status: proposed`. Ответ отмены: `cancelled`, либо `paid` с полями оплаты (05 §6.7.2).
16. **`x-retry`** кратко пересказывает правила 05 §6.5, §8.1, SYNC-029, SYNC-044, SYNC-077, SYNC-078. Канон остаётся в 05.
17. **Фикстуры.**
    - Конверт: `{_note, description?, operation: "METHOD /pos/v1/...", kind: request|response, status?, headers?, body}`.
    - Имя файла — `<операция>.<HTTP-код>[.<вариант>].json`, запросы — `<операция>.request.json`. Скрипт сверяет код в имени со `status`.
    - Данные синтетические, как в примерах ТЗ для программиста 1С (`docs/integration/1C_API_requirements.md`): «ООО Пример», «Клиент Пример», `+996700000001` / «0700 000 001», номера `ОС00-004512` и т. п. Правдоподобные ФИО и телефоны не используются (с 1.1.0).
    - Пользователь POS в `createdByUserCode` / `cashierUserCode` — UUID `users.id` (или `system`), не логин; сроки QR (`expiresAt`) действующих QR — в будущем (2099 год), у `payments-status.expired.200` — в прошлом; штрихкоды EAN-13 — с верной контрольной цифрой.
    - Обезличенные образцы RM-A-005 (`docs/discovery/onec/samples/`) ещё не получены. После их получения фикстуры дополняются по ним.
    - Тела `GET /images/{ref}` двоичные: фикстур в JSON для них нет.
18. **Allow-list.**
    - Статусы: `[ПОДТВЕРЖДЕНО: $metadata]` (обязателен `confirmedBy`), `[ТИПОВО]` и `[НЕ ПОДТВЕРЖДЕНО]` (обязателен `fallback`).
    - Метка `[НЕ ПОДТВЕРЖДЕНО]` строже, чем `[ТИПОВО]`. Её получили условные объекты ONEC-106 (`ЭквайринговаяОперация`, `ЗаявкаНаВозвратТоваровОтКлиента`). Критерий RM-B-004 п. 3 для них выполняется через `fallback`.
    - `$metadata` не получен, поэтому подтверждённых коллекций 0.
    - `fieldsComplete: false` стоит там, где 05 не перечисляет состав полей (табличные части `_Товары`, `РасчетыСКлиентамиПоСрокам` и т. п.). Состав дополняется по `$metadata`; поля не выдуманы.
    - `AccountingRegister_Хозрасчетный` (только БП) вынесен в `excluded`: его публикация раскрыла бы весь бухгалтерский учёт (ONEC-083). Включается только решением после `$metadata`.
19. **Redocly.** `lint` проходит с 0 ошибок и 1 предупреждением `info-license-strict`: у лицензии нет `url`. Материалы проприетарные, URL лицензии в ТЗ нет — не выдумывается. Файл `redocly.yaml` не создавался: он вне назначенных путей.

## 5. Связи и что вне этой задачи

- **Входящий обмен C-2** (05 §10.1, `/api/v1/integrations/onec/*`) — это пути `pos-api`. Контракт находится в `contracts/openapi/pos-api.v1.yaml` (RM-B-003, 08 §4.21), не здесь. Тело `objects[].data` во входящем обмене совпадает с элементом `items[]` этого контракта, но без `ref`, `dataVersion` и `deletionMark` (05 §10.1). Поэтому схемы `*Change` здесь — источник формы данных для 08 §4.21.
- **Контракт-тест «фикстуры ↔ маппер»** и `FakeOnecGateway` (13 §5.2) — этап E. Фикстуры этого каталога — их вход.
- **Приёмка реализации специалиста 1С** — RM-B-014 и RM-E-016 по 18 §7.3. Расхождения реализации с этим файлом устраняются по ONEC-074: сначала 05 §6, затем 18, затем этот контракт.
