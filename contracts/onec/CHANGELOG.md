# CHANGELOG — контракт HTTP-сервиса расширения 1С (`contracts/onec/onec-http-service.v1.yaml`)

Формат — по [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/); версия — `info.version` контракта (правило
ONEC-033, 05 §6: добавление полей и уточнение описаний — минорная версия в пределах `v1`; удаление, переименование и
смена смысла — только `v2` при параллельной поддержке `v1`). Шаг 16 CI (`contracts-lint`, 13 §5.3 п. 2) требует запись
с новой версией при каждом изменении контракта. Тот же файл ведёт и allow-list OData `contracts/onec/odata-allowlist.yaml`
(поле `version`, сейчас 1): его изменение — отдельная запись вида «odata-allowlist <N>». Подробный журнал версий и
статусы согласования со специалистом 1С — `contracts/onec/NOTES.md` §6.

## [1.3.0] — 2026-11-24 — QR напрямую от банка через сервер POS (P-004, ADR-123)

Минорное изменение: `info.version` 1.2.0 → 1.3.0. Основание — слова владельца 2026-11-23 («sms i bank integratsii
bili u sebya») и ответ пользователя 2026-11-23 (`docs/customer/P-004_OWNER_DECISIONS.md`): QR — напрямую от банка через
наш сервер, 1С получает только документ оплаты; решение — ADR-123 (заменяет ADR-081 в части схемы QR; отменяет
решение 21.11.2026 «QR через 1С» в части QR). Владелец содержания — 05 §6.7, §6.4. Путь `v1`, набор операций и ответы
не менялись (`scripts/check_onec_paths.py` — 0 ошибок); методы не удалены.

### Изменено

- `POST /pos/v1/payments` (`createPayment`): при `QR_PROVIDER=bank` POS **вызывает** метод для каждой оплаты по QR,
  подтверждённой банком или кассиром (`kind = qr_bakai`, `bankReference` — операция банка), через outbox после
  элемента заказа; это единственный документ оплаты по таким QR (второй документ от интеграции банка в 1С — Q-383).
  Для `cash` и при `QR_PROVIDER=onec` — без изменений (метод не вызывается, Q-012).
- `PaymentCreateRequest.customerRef`: `nullable` — `null` только вместе с заказом-основанием (контрагент — из заказа,
  например «Розничный покупатель» без карточки 1С; так же, как `OrderCustomer.ref` в 1.1.0). Для 1С это новое
  допустимое значение входа — его нужно принимать.

### Уточнено (только описания)

- `POST /pos/v1/payments/qr`, `GET /pos/v1/payments/{externalId}/status`, `POST /pos/v1/payments/{externalId}/qr/cancel`
  (`createQrPayment`, `getQrPaymentStatus`, `cancelQrPayment`): «**не нужен при `QR_PROVIDER=bank`**» — в `summary`,
  `description` и `x-priority`; методы остаются в контракте для режима `QR_PROVIDER=onec` (Q-387). Схемы QR не менялись.
- `PaymentCreateRequest.bankReference`: при `QR_PROVIDER=bank` — идентификатор операции зачисления у банка.

### Добавлено

- Фикстура `fixtures/payments-create.request.qr-bank.json` (тестовые данные): документ оплаты QR банка по заказу
  розничного покупателя (`customerRef = null`).

## [1.2.0] — 2026-11-04 — заявка с планшета магазина (P-002, ADR-115)

Минорное изменение: `info.version` 1.1.0 → 1.2.0, только описания. Основание — P-002 «Планшет магазина» редакции 5,
утверждённый владельцем 2026-11-04 («P-002 утверждаю, делай»); решение — ADR-115; владелец содержания — 05 v1.7 §6.8
(ONEC-109, ONEC-110), изложение для специалиста 1С — ТЗ для программиста 1С 1.2, раздел Г.9, вопросы 88–92. Набор
операций, схемы тел, шаблон `x-comment-pattern` и фикстуры не менялись (`scripts/check_onec_paths.py` — 0 ошибок).

### Уточнено

- `OrderCreateRequest.comment`: `x-comment-format` дополнен вариантом заявки с планшета магазина —
  `POS <externalId> · <publicNumber>[ · заявка клиента| · Заявка с планшета «<имя>»][ · <комментарий>]`; описание поля —
  пример `POS <uuid> · POS-2026-000123 · Заявка с планшета «Планшет у входа»` (05 §6.8 п. (1), (6); Q-344, вопрос 89).
  Шаблон `x-comment-pattern` этот вариант уже принимал.
- `OrderCreateRequest.createdByUserCode`: у заявки с планшета — UUID технического пользователя планшета, один на планшет,
  не меняется при подключении заново (05 ONEC-109; Q-343, вопрос 88). Формат поля не меняется.
