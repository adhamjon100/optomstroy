# Веб-демо «Оптомстрой POS» (Netlify, только статика)

Заказчик открывает настоящее приложение в браузере: Flutter (web) + настоящий pos-api, который работает **в браузере**
(module Web Worker `backend/backend.js` на PGlite 0.3.16), с имитатором «1С» вместо 1С. Все данные — тестовые и
хранятся только в браузере заказчика. Сайт: `optomstroy-demo-4fhvb` (решение владельца от 2026-10-29), noindex.

> **Только для показа (ADR-113; P-004: ADR-123, ADR-124).** Веб-демо — путь SMS и QR **не через наш сервер**: pos-api
> работает в браузере, SMS не отправляются (код 246810 для любого номера, `APP_ENV=dev`), QR подтверждает имитатор «1С»
> (`QR_PROVIDER=onec`, `backend/demo-config.mjs`). В рабочем контуре и на стенде этих путей нет: SMS — только
> pos-api → `sms_outbox` → pos-worker → SMSPro, QR — от банка через наш сервер (`QR_PROVIDER=bank`); код 246810 при
> `APP_ENV=staging` и любой тестовый код при `SMS_PROVIDER=smspro` — отказ в старте pos-api. Демо оставлено как есть.

## Данные демо: каталог по макету (WP-DATA-WEB, 2026-10-31; ADR-114)

Каталог собран по прототипу экрана выбора товаров (`docs/specification/visual/prototype/Main.dc.html`). Источник —
спецификация `demo/catalog/design-catalog.json`, она правится вручную. Сборку делает
`pos-api/scripts/design_catalog.ts` через публичный API `SyntheticCatalog`, исходники pos-api не меняются.

- **Дерево.** 8 корней и 33 подкатегории в порядке макета; порядок хранится в `categories.sort_order`.
- **Товары.** 78 тестовых товаров: 26 товаров макета без изменений и 52 наполнителя без марок. В «Сантехнике»
  ровно 12 товаров макета. У неё больше всех товаров среди корней, поэтому каталог сотрудника при первом входе
  открывается на ней: правило «корень с наибольшим productCount».
- **Фото.** 29 PNG макета как есть (`demo/catalog/photos`, происхождение — `demo/catalog/PHOTOS.md`): 8 картинок
  корней, 9 подкатегорий «Сантехники» (`categories.image_id`) и 12 фото её товаров. На сайте это 87 файлов WebP,
  около 0,08 МБ. У остальных товаров фото нет — как в макете.
- **Остальное.** Порог «мало» в демо — 4: в макете 4 шт — «В наличии», 3 — «Мало». «Унитаз-компакт Sanita Luxe
  Classic» (SL1001) в избранном у сотрудников стенда, как `favs` макета. Есть 5 товаров с характеристиками,
  10 с упаковками и 5 в «м»/«м2». 5 товаров «нет в наличии», два из них есть на другом складе. Один товар —
  «Остаток неизвестен» (KT2).
- **Эпоха.** Любая правка спецификации, фото или `design_catalog.ts` меняет ключ эпохи. Браузеры начнут демо
  заново (WEB-KI-06).
- **Проверка.** `node --test demo/web/backend/test/design-catalog.test.mjs` сверяет спецификацию с данными
  прототипа (`CATS`, `P`, `IMG`, `favs`) и ассетами макета. После сборки сайта тест проверяет и ответы воркера.

## Сборка

`TEMP`/`TMP` — на `D:\optomstroy\.tmp`. Нужны Node 24, `pos-api/node_modules`, Flutter SDK (для шага Flutter) и
Python (проверка секретов). Ничего не скачивается.

```
powershell -ExecutionPolicy Bypass -File demo/web/build-web-demo.ps1            # всё
powershell -ExecutionPolicy Bypass -File demo/web/build-web-demo.ps1 -SkipFlutter   # Flutter уже собран в .build/flutter
```

По шагам:

```
node demo/web/backend/build-backend.mjs        # pos-api → backend.js, PGlite, снимок, фото, лицензии (≈ 45 с)
#   flutter build web … -o demo/web/.build/flutter; dart compile js → .build/drift_worker.js; sqlite3.wasm → .build
node demo/web/tools/assemble-site.mjs          # site/: Flutter + страница + бэкенд, demo/build.json, _headers, _redirects
node demo/web/tools/check-site.mjs             # проверки публикации; код 0 — можно выкладывать
```

После любой пересборки бэкенда сайт собирается заново (`assemble-site.mjs`): `demo/build.json` берёт ключ эпохи из
`backend/build.json` (один источник), а `check-site.mjs` сверяет sha бандла.

По умолчанию `smoke.mjs` идёт с `--only boot,ui,f5,frozen`: шаги планшета магазина `kiosk` и `kioskswitch` (P-002
TAB-3-01, TAB-3-02; ADR-115; вне релизных ворот — 12 §3.23) в него не входят, поэтому T-KIOSK-034 и T-KIOSK-051
выполняются только с `--only kiosk,kioskswitch` (или добавленными к прежнему списку). Шагу `kioskswitch` нужен шаг `kiosk`
в том же прогоне и идёт последним; после шага `kiosk` браузер — планшет магазина. Шаг `paste` (вставка на экране входа,
12 T-DEMO-014; вне подсчёта §5.3) в список по умолчанию тоже не входит: он идёт сразу после загрузки, пока вкладка на
SCR-01, — буфер «+996 555 000 906» (разрешения — `Browser.grantPermissions` / `Browser.setPermission`): (а) с
разрешением `clipboard-read` правая кнопка над «+996» → меню приложения → «Вставить» → «555 000 906»; (б) без
разрешения `Ctrl+V` поверх выделенного «77» → «555 000 906»; (в) без разрешения правая кнопка над полем в фокусе — событие
`contextmenu` не отменено (меню браузера), над «+996» «Вставить» меню приложения → подсказка `ds_paste_blocked_hint`,
поле пустое. Само меню браузера headless не рисуется — его «Вставить» проверяется вручную («Как проверить превью»).
Шаг `passkey` (вход по лицу или отпечатку, 12 T-DEMO-017…T-DEMO-019, T-DEMO-022, T-DEMO-023; вне подсчёта §5.3) в список
по умолчанию тоже не входит и идёт последним; что он проверяет и его ограничения — раздел «Вход по лицу или отпечатку
(passkey, ADR-116)» ниже.

## Вход по лицу или отпечатку (passkey, ADR-116)

Только веб-демо (15 ADR-116 п. 1, п. 4, п. 5; 09 §9.2 «Веб-демо», BIO-035, BIO-037, BIO-041; 06 §6.10). Продуктовая
web-сборка (`lib/main.dart`) биометрии не получает (`NoBiometricAuthenticator`, DM-01). Страница `site-src/demo-passkey.js`
даёт `globalThis.__posPasskey` (протокол 1, подключается в `index.html` после `demo-env.js` и до `demo-boot.js`);
приложение подключает `WebPasskeyAuthenticator` четвёртым переопределением демо (`pos-app/lib/app/demo/demo_passkey*.dart`,
`demo_overrides.dart`). Это показ потока и кода настоящего сервера, а не защита: JWT-ключи и база демо лежат в
хранилище того же сайта (ADR-113 п. 3; `docs/known_issues.md` WEB-KI-37). Для заказчика — раздел «Вход по лицу или
отпечатку» `docs/customer/WEB_DEMO_INSTRUCTION.md` и подсказка в «ДЕМО» → «Как войти».

**Режимы.** Режим выбирает приложение по ОС браузера (`browserDevicePlatform`; macOS и iPad браузер определяет как
android — WEB-KI-10), страница платформу сама не определяет.

| Браузер | Режим | SCR-42 «Защита входа» | SCR-08 (холодный старт) |
|---|---|---|---|
| не на Windows | привязка: `biometric_refresh` под AES-256-GCM, ключ — HKDF-SHA-256 из выхода PRF passkey; новый токен перешифровывается без второго диалога (ключ в памяти страницы ≤ 60 с); сервер видит `android` + `class3` | «Вход по отпечатку или лицу» + согласие; без PRF или без платформенного аутентификатора с проверкой пользователя — недоступно | автовызов, один диалог WebAuthn → рабочий экран без PIN |
| Windows: PRF есть и `security.windowsHelloKeyAllowed` | ключ входа (как W2): RSA-2048 WebCrypto, PKCS#8 под ключом из PRF; открытый ключ — `POST /me/biometrics {biometricClass:'windows_hello', helloKey:{source:'webauthn_prf'}}` | «Вход через Windows Hello» + согласие | «Войти через Windows Hello» без автовызова → один `get()` → `POST /auth/unlock/challenge` → `POST /auth/unlock {method:'hello_key'}` → без PIN |
