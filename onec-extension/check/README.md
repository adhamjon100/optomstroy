# Программа проверки API 1С (`onec-extension/check/`)

Для разработчиков POS. Программа проверяет HTTP-сервис расширения 1С «OptomstroyPOS» по контракту
`onec-http-service` **1.2.0**, «Требованиям к API 1С» 1.2.1 (требования — как в 1.2) и контрольному примеру 18 §7.2 (= Требования §8.3): 1С —
главная система, сервер POS работает с ней днём, в момент продажи (заказы → «Заказ клиента», оплаты и QR через 1С,
заявки на возврат, `/check`, каталог по `/changes`, долги, картинки, `/external-ids`). Её запускает программист 1С
магазина против тестовой копии базы. Описание для программиста 1С — `ЧИТАЙ_МЕНЯ.txt` в сборке
(`release/chitai_menya.txt`) и `docs/integration/ONEC_CHECK_TOOL.md`.

Версия 1.1.0 (20.11.2026): проверки ночного обмена убраны — ТЗ 2.3 отозвано 20.11.2026; журнал адаптации —
`.tmp/onec-check/online-adapt.md`.

## Границы

- В сборке — только контракт 1.2.0 (git blob `63995cc4…`, sha256 `a4513f16…`) и 59 образцов JSON из пакета заказчика.
  Каждое правило проверки ссылается на контракт, раздел «Требований» (`ref`), шаг КП (`kp`) или AC-ONEC (`ac`) —
  это проверяет тест `adapt-units`. Черновик контракта 1.3.0 и материал отозванного ТЗ в сборку не попадают:
  `build.mjs` проверяет это двумя стражами (имена черновика минус контракт 1.2.0 и «Требования»; ссылки на ТЗ 2.3,
  «ночной обмен», «1.3.0» и методы срезов — кроме одной строки истории версий в `ЧИТАЙ_МЕНЯ.txt`).
- Обязательные методы (x-priority: must) — «метода нет» = ОШИБКА с разделом и этапом §8.2: заказы (O), проверка
  корзины (CK), поиск клиента и долг (K7–K9), картинки (I). QR (Q, только если интеграция с банком умеет,
  Требования §7.13), заявки на возврат (R, «обязательно, если 1С принимает такие заявки (Q-018)» — таблица раздела 6,
  вопрос 77), карточка товара (CC) и `/external-ids` (X) — «МЕТОДА НЕТ», не ошибка.
- Объекты, которые создаёт программа, проверяются и в `/changes` (C14): клиент K1 — `Catalog_Партнеры`, заказ O1 —
  `Document_ЗаказКлиента` с тем же `externalId` и `ref`, QR Q1 — `QrPaymentStatus` со статусом `cancelled` и
  `reference` выданного QR (Требования §5.1, §6.2 правило 8, §6.6, §6.14 п. 9, §7.10). Имитатор регистрирует
  заказы и записи QR при создании и отмене. Ключ клиента A6 проверяет в каждом методе дважды: без ключа и с неверным
  ключом (§4.4 п. 3).
- Язык текста ошибки в контракте и Требованиях не задан: «не по-русски» — ЗАМЕЧАНИЕ (E8), как и пустой текст.
- Время выполнения — только встроенные модули Node 24. YAML → JSON — при сборке модулем `yaml` из `pos-api`.

## Сборка

```
node build.mjs                 # с runtime/node.exe (только Windows) → .tmp/onec-check/release/
node build.mjs --no-runtime    # без node.exe (для тестов и CI)
node build.mjs --out <папка> --pack <zip заказчика> --draft-contract <yaml>
```

Шаги: Node ≥ 24 → blob и sha256 контракта → 59 образцов по манифесту → YAML → JSON (`meta.json` с sha256) →
раскладка `programma/` (в `src/` — только `.mjs`, иначе стоп) → страж утечки 1.3.0, страж отозванного задания и поиск
секретов → самопроверка `--demo` (код 0, formatVersion 2) → `node.exe` (версия, подпись OpenJS Foundation, sha256
`f13ac3ca…`) и LICENSE (sha256 `b4c7840e…`) → zip (фиксированное время, сортировка — архив побайтно повторяем) и
`SHA256SUMS` → проверка zip: состав точно по плану, бит UTF-8, `node.exe` в архиве = оригинал; распаковка в
`Тест папка (1)\Проверка API 1С`, запуск `Proverka_API_1C.cmd --demo` (код 0, вывод UTF-8), запуск при чужом
`NODE_OPTIONS` (код 0) и запускателя без `runtime\` (сообщение, код 2). Папка `Optomstroy_Proverka_API_1C_<версия>/`
рядом с архивом — распакованная копия для тестов `release`; после сборки выпуска её удаляют (место на D:).

`SHA256SUMS.txt` внутри — стандартный вид (`<sha256> *<путь>`, UTF-8 без BOM, LF): `sha256sum -c SHA256SUMS.txt`.
Запускатели (ASCII, CRLF) очищают `NODE_OPTIONS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_DEBUG`, `NODE_EXTRA_CA_CERTS`
компьютера и без `runtime\node.exe` или `programma\main.mjs` рядом пишут «OSHIBKA: … Raspakujte VES arhiv …» и выходят
с кодом 2. Если программу запустили не через `.cmd`, а `NODE_EXTRA_CA_CERTS` задан, в протоколе — баннер об этом.

Лицензия Node.js: в установке `C:/Program Files/nodejs` (v24.11.1) файла LICENSE нет. `release/node-LICENSE.txt` —
LICENSE, найденный локально рядом с побайтно тем же `node.exe` v24.11.1 (sha256 `f13ac3ca…`) в папке драйвера
Playwright для Go 1.57.0 (`ms-playwright-go/1.57.0/`), sha256 `b4c7840e…`; `build.mjs` проверяет обе суммы. В сборке —
`runtime/LICENSE` и `runtime/ИСТОЧНИК_ЛИЦЕНЗИИ.txt`.

## Флаги разработчика (нет в `--help`)

- `--demo-defect Dnn` — имитатор с дефектом из `src/mock/defects.mjs` (вместе с `--demo`).
- `--timeout-scale 0.001…1` — масштаб таймаутов (для D51 и тестов таймаутов).

## Как добавить проверку

1. Строка в `src/checks/index.mjs` (`def(id, group, kind, R|W, title, {contract, ref, kp, ac}, {deps, optional})`):
   источник обязателен — контракт 1.2.0, раздел «Требований», шаг КП или AC-ONEC.
2. Реализация в модуле группы: `await ctx.run('ID', async (r) => { const ex = await r.call({ op: 'GET /pos/v1/…', path }); … })`.
   `r.call` сам проверяет правила E и схему ответа и повторяет GET при временной ошибке, как POS (`x-get-retry`);
   если ошибка ожидается нарочно (обнаружение метода, неверный `since`, режим обслуживания) — `noRetry: true`
   (`dataError` и неверные пароль/ключ не повторяются и так). Поля ответа вне контракта 1.2.0 в протоколе скрыты
   целиком (`Validator.foreignPaths` → `Masker.maskJson({foreignPaths})`). Находки — `r.fail/warn/info(text, {code, where})`,
   итог — `r.pass(summary)`, особые результаты — `r.skip/absent/infoVerdict`; обязательный метод, которого нет, —
   `absentRequired(ctx, r, id, {what, section, stage})`.
3. Вызов из нужной фазы `src/main.mjs`; запись (`W`) пропускается без `--allow-write` автоматически.
4. Если проверка ловит дефект — дефект в `src/mock/defects.mjs` и поведение имитатора в `src/mock/*.mjs` или сценарий
   фасада в тесте; тест сначала должен падать на сборке без исправления.
